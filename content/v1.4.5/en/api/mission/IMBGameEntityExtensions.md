# IMBGameEntityExtensions

**Namespace:** TaleWorlds.MountAndBlade
**Module:** TaleWorlds.MountAndBlade
**Type:** `internal interface IMBGameEntityExtensions`
**Base:** none
**File:** `bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/IMBGameEntityExtensions.cs`

## Overview

`IMBGameEntityExtensions` is the managed-to-native seam for **two unrelated jobs that both happen to end in "change a `GameEntity`"**. The file is 21 lines with four `[EngineMethod]` bindings: `create_from_weapon` (`IMBGameEntityExtensions.cs:11`) builds a brand-new scene entity from weapon data, while `fade_out`, `fade_in` and `hide_if_not_fading_out` (`IMBGameEntityExtensions.cs:14`, `:17`, `:20`) operate on an entity that already exists.

The wrapper is [`GameEntityExtensions`](../../mission-ext/GameEntityExtensions), a `public static class` (`GameEntityExtensions.cs:6`). This is the important shape for this page: **the bridge is internal, but three of its four members are genuinely reachable from a mod**, because the wrapper turns `FadeOut`, `FadeIn` and `HideIfNotFadingOut` into `this GameEntity` extension methods (`GameEntityExtensions.cs:51`, `:56`, `:61`). You write `someEntity.FadeOut(1f, false)` and never learn an internal type exists.

## Mental Model

### What it is / which layer

- It sits between the managed `GameEntity` object and the native scene entity behind it. Note the direction of ownership: a managed `GameEntity` is a `DotNetObject`-style handle over a native entity, and this interface passes `entityPointer` (`UIntPtr`) down to native while `CreateFromWeapon` hands one back.
- It is **not** a general `GameEntity` extension API. Read it as "the four native calls the engine's own entity helpers needed", which is why instantiation and fading sit in the same interface — there was no more specific home for them.
- Compare with the sibling [`IMBDebugExtensions`](../IMBDebugExtensions), which renders debug geometry. Both take a `scenePointer` or `entityPointer` and hand it to native; neither owns anything.

### The consequence that matters

**Which member you can reach is the whole story of this page.** `FadeOut`, `FadeIn` and `HideIfNotFadingOut` are public extension methods on `GameEntity` and need nothing from you but an entity. `CreateFromWeapon` is exposed as `GameEntityExtensions.Instantiate(Scene, MissionWeapon, bool, bool)` (`GameEntityExtensions.cs:8`), which is also public — but it is a **static factory taking a `Scene` and a `MissionWeapon`**, and internally it does real work you cannot skip: it extracts `WeaponData` and `WeaponStatsData` from the weapon (`GameEntityExtensions.cs:10-13`), calls the bridge (`GameEntityExtensions.cs:14`), then calls `weaponData.DeinitializeManagedPointers()` (`GameEntityExtensions.cs:15`). That last line is the reason you must go through `Instantiate` rather than trying to call the bridge yourself: the weapon data carries managed pointers that native uses during the call and that must be released immediately after.

### When to use / when not

- **Use** `FadeIn`/`FadeOut`/`HideIfNotFadingOut` on any `GameEntity` you own in a mission scene — spawning a projectile mesh that should not pop in, dissolving one that should.
- **Do NOT** call `HideIfNotFadingOut` as a general hide. Read the name literally: it hides only if the entity is *already* fading out, which makes it a "let the fade finish" call rather than a "make it invisible" call. Using it to hide a visible entity does nothing, silently.
- **Do NOT** hold a `GameEntity` across mission end. `FadeOut` takes a `UIntPtr` from `gameEntity.Pointer` (`GameEntityExtensions.cs:53`), so a stale entity is a pointer into freed native memory.

## How to use

**How to obtain it.** You cannot reference the interface, but you do not need to. The interface is `internal` (`IMBGameEntityExtensions.cs:8`) and the `MBAPI` field is `internal static` (`MBAPI.cs:36`), with `InternalsVisibleTo` granted only to `TaleWorlds.MountAndBlade.AutoGenerated`, `TaleWorlds.MountAndBlade.Multiplayer` and `TaleWorlds.Generator.Bannerlord` (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`) — so naming `IMBGameEntityExtensions` in mod code fails to compile.

The door out is [`GameEntityExtensions`](../../mission-ext/GameEntityExtensions), `public static class` at `GameEntityExtensions.cs:6`. Three of its methods are extension methods on `GameEntity`, so they read as instance calls; the fourth is a plain static factory. No casting, no reflection, no `InternalsVisibleTo` of your own.

**A typical use.** Fade a mission-owned entity out and let the engine finish the transition — the exact chain `GameEntityExtensions.cs:51-64` implements:

```csharp
using TaleWorlds.Engine;
using TaleWorlds.MountAndBlade;

// GameEntityExtensions is public static (GameEntityExtensions.cs:6), so these
// three read as ordinary methods on the entity. Internally each forwards the
// entity's Pointer to MBAPI.IMBGameEntityExtensions (GameEntityExtensions.cs:53,
// :58, :63) — which the bridge declares at IMBGameEntityExtensions.cs:14, :17, :20.
GameEntity ghost = Mission.Current.Scene.GetFirstEntityWithTag("RespawnMarker");
if (ghost != null)
{
    ghost.FadeOut(2.0f, false);   // 2-second fade, do not remove from scene
}
```

**What to watch out for.** The trap is the `HideIfNotFadingOut` name. It is not "hide this entity"; it is "hide this entity **if** it is fading out" — the native side checks the fade state itself. Code that calls it expecting to make something vanish will see nothing happen and no error, because the one member that *looks* like a hide is conditional on state the caller cannot observe. If you want an unconditional hide, you do not have one on this bridge; manage visibility through the entity's own lifecycle instead.

## Examples

Fade a spawned entity in from nothing, which is the paired use of `FadeIn` with its default `resetAlpha`:

```csharp
using TaleWorlds.Engine;
using TaleWorlds.MountAndBlade;

// FadeIn(this GameEntity, bool resetAlpha = true) — GameEntityExtensions.cs:56.
// The default resets alpha, so the entity appears from fully transparent.
GameEntity marker = Mission.Current.Scene.GetFirstEntityWithTag("Banner");
if (marker != null)
{
    marker.FadeIn();          // wrapper default resetAlpha: true
}
```

Instantiate a weapon entity through the public factory, never through the bridge — the factory's cleanup step is load-bearing:

```csharp
using TaleWorlds.Engine;
using TaleWorlds.MountAndBlade;

// GameEntityExtensions.Instantiate is public static (GameEntityExtensions.cs:8).
// Going through it is mandatory, not stylistic: it calls DeinitializeManagedPointers
// on the weapon data right after the native call (GameEntityExtensions.cs:15).
public static GameEntity SpawnWeaponMesh(Scene scene, MissionWeapon weapon)
{
    if (scene == null || weapon == null)
        return null;

    GameEntity spawned = GameEntityExtensions.Instantiate(scene, weapon, true, true);
    if (spawned != null)
    {
        spawned.SetPosition(Mission.Current.Scene.GetLastEntityWithTag("Ground").Position);
    }
    return spawned;
}
```

The misuse, shown so the name is not copied into a mod:

```csharp
using TaleWorlds.MountAndBlade;

public static class Visibility
{
    public static void HideIt(GameEntity entity)
    {
        // WRONG: this does nothing unless the entity is already fading out
        // (IMBGameEntityExtensions.cs:20). No error is raised, so the bug is silent.
        entity.HideIfNotFadingOut();

        // RIGHT: ask for the fade, and let the engine remove or dissolve it.
        entity.FadeOut(0.5f, true);
    }
}
```

## Risks and crash boundaries

- **A mod cannot name the interface.** `internal interface` (`IMBGameEntityExtensions.cs:8`) plus `internal static MBAPI` field (`MBAPI.cs:36`) plus `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). Compile-time failure.
- **But three members ARE publicly reachable**, unlike most bridges in this bucket. `FadeOut`, `FadeIn` and `HideIfNotFadingOut` are public extension methods on `GameEntity` (`GameEntityExtensions.cs:51`, `:56`, `:61`). If you concluded "internal bridge, therefore unusable" about this page, that conclusion is wrong for these three.
- **`HideIfNotFadingOut` fails silently.** It is conditional on native fade state that the caller cannot query. On a visible entity it does nothing and raises nothing.
- **`WeaponData` pointers must be released.** `CreateFromWeapon` is valid only for the duration of the native call; the caller must call `DeinitializeManagedPointers()` immediately after (`GameEntityExtensions.cs:15`). Calling the bridge yourself and skipping that leaves managed pointers that native no longer owns.
- **Every member takes a raw pointer.** `entityPointer` and `scenePointer` are `UIntPtr` taken from a managed handle. After mission teardown these are freed native addresses; calling `FadeOut` on a stale `GameEntity` is a use-after-free with no managed guard.
- **No completion signalling.** Nothing here tells you when a fade finished. Track your own state or observe visibility separately.
- **Not a save participant.** No `[Serializable]`, no state; fading is presentation only and is not persisted.

## Cross-Version Notes

The v1.4.5 file is 21 lines with four `[EngineMethod]` bindings — `create_from_weapon`, `fade_out`, `fade_in`, `hide_if_not_fading_out` — and the same file name and four-member shape appear under the same `Bannerlord.Source/bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/` layout in the `bannerlord-1.3.0` and `bannerlord-1.3.15` trees. The native symbol strings are the stable contract. What is **most likely to drift** is `create_from_weapon`'s parameter list: it already carries four data/length pairs for weapon and ammo (`IMBGameEntityExtensions.cs:11`), which is the shape that grows whenever a new weapon-data category is added, so do not hard-code an expectation of the arity across versions. The three fade members are the stable part. **VERIFIED MEASURED for v1.4.5** (21 lines, 4 members, `GameEntityExtensions.cs:8-64` call sites); the sibling version trees were not read member-by-member for this page.
