# Bannerlord v1.5.3 / 骑砍2 v1.5.3

## 心智模型

v1.5.3 是一个**源码完整**的版本：`bannerlord-1.5.3/` 根目录下有 68 个 `TaleWorlds.*` 目录
加上 `SandBox` / `StoryMode`，共 11 487 个 `.cs`。这就是为什么本版本能给出完整的**分桶清单与覆盖统计**，
而旧版本不能 —— 没有需要猜的东西。

把 SDK 想成一摞**只会向下依赖**的程序集：

```
   UI        GauntletUI · ScreenSystem · ViewModelCollection
   Mission   MountAndBlade · CustomBattle · Multiplayer
   Campaign  CampaignSystem · ObjectSystem · ActivitySystem
   Foundation Core · Library · DotNet · Localization · InputSystem
   Native    TaleWorlds.Native.dll（P/Invoke，不在本树范围内）
```

绝大多数 mod 只碰最上面三层：**Campaign**（世界规则）、**Mission**（单场战斗）、**UI**（界面）。
完整地图见 [SDK 分层概览](./architecture/sdk-overview)，程序集逐个查表见 [模块地图](./architecture/module-map)。

> **源码来源（provenance）**
> `bannerlord-1.5.3/` 是 **ILSpy 反编译产物** —— 11 487 个文件里有 11 398 个带 `// Token: 0x…` 标记。
> 签名可信，但排版是反编译器的，不是原作者的。这一点在做跨版本 diff 时很关键：
> 先读 [从 1.4.5 迁移](./architecture/migration-from-1.4.5)，再决定哪些差异能信。

## 这棵树现在没有什么

把话说清楚，不含糊：

- 1.5.3 源码在排除噪声命名空间（`AutoGenerated`、`obj/` 等）后扫描到 **6 824 个类型**
  （class 5 621 / enum 610 / struct 322 / interface 242 / delegate 29）。
- 本树已覆盖其中 **187 个**类型，也就是 **2.7%**。
- 其余 **6 637 个类型尚未撰写**。不是「即将到来」，也不是「按需生成」——
  就是目前没有对应页面。你在 `api/` 下的 10 个有页的桶里找不到的类型，都属于这一批。
- **桶索引页只有 2 个，不是 19 个。** v1.5.3 全树共 9 个 `_index.md`，其中只有
  [api/localization/](./api/localization/) 与 [api/storymode/](./api/storymode/) 两个桶目录有自己的 `_index.md`，
  可以点进去；其余 8 个有页面的桶（`campaign/`、`campaign-ext/`、`core-extra/`、`gui/`、`engine/`、`save-system/`、
  `mission/`、`core/`）与 9 个尚无页面的桶都没有，**点它们的桶名会 404**。
  旧版本文档里那种「点桶名进目录」的走法对这 17 个桶走不通，请从 [/api/](./api/)（自动列出全部 187 篇）、
  本页或 [模块地图](./architecture/module-map) 进。

### 缺口按桶分布

数字来源：`tools/_v153_inventory.json`（只读报告型数据，字段 `types[].dir`，实跑
`tools/_v153_inventory.mjs` 生成于 `../bannerlord-1.5.3`）。「已撰写」列是本树 `content/v1.5.3/zh/api/`
下实际存在的**叶子页**数（不含 `_index.md`）。「尚未撰写」按「类型数 − 已撰写页数」估，假定一类型一页 —— 这是本站的约定，
不是逐类型核对的结果。

三个值得记住的结论：

1. **缺口不是均匀的。** `mission-ext` 一个桶就占了 2 065 个未撰写类型（占全部缺口的 31%），
   它是 `TaleWorlds.MountAndBlade` 里除三个战斗门面以外的全部 —— 战斗控件、`MissionBehavior`、
   `MissionLogic`、多人全都在这里。
2. **已写的 187 篇分布极不均**：`storymode` 一个桶就占 92 篇（主线剧情完整实现），`core-extra` 44 篇，
   `localization` 19 篇，而 `mission-ext` / `sandbox` / `viewmodel` 三个大桶仍是 **0 页**。
   换句话说：**这棵树不是「按重要性从高到低写的」，而是按桶写的**，读覆盖面时要看桶，不要看总数。
3. **`sandbox` 是整桶空白**（1 247 个类型 0 页），它是可玩战役模块，
   具体实现类（`SandBoxGameManager` 等）在源码树里存在，但本树尚未撰写它们的类型页。
   `storymode`（183 个类型）则相反 —— 已有 **92 页**，是覆盖最多的桶。

### 分桶归属不是主观判断

每个桶都是权威表 `tools/_dir-map-canonical.json` 的命名空间规则（最长前缀优先，
`entryPointDirs` 优先于前缀匹配）作用在 1.5.3 真实命名空间集合上的输出。
1.5.3 源码里有 **621 个**命名空间声明，其中 442 个承载非噪声类型，落到 19 个桶。
一个类型只对应一个页面路径。

## 怎么用这一版

1. **先建大局观。** [SDK 分层概览](./architecture/sdk-overview) 给五层依赖模型与阅读主线。
2. **再查程序集边界。** [模块地图](./architecture/module-map) 给 68 个 `TaleWorlds.*` 程序集
   逐个的归属、职责、以及「mod 该不该关心」。
3. **然后按上面「这棵树现在有什么」的表进类型页。** 想挂行为就读
   [ICampaignBehavior](./api/campaign/ICampaignBehavior) 与
   [CampaignBehaviorBase](./api/campaign/CampaignBehaviorBase)；
   想改世界数值读 [Campaign](./api/campaign/Campaign) 与 [GameModels](./api/campaign/GameModels)；
   想加界面读 [ScreenManager](./api/gui/ScreenManager) 与 [ScreenBase](./api/gui/ScreenBase)；
   想让数据能存档读 [SaveManager](./api/save-system/SaveManager)。
4. **要升级？** 先读 [从 1.4.5 迁移](./architecture/migration-from-1.4.5) —— 它是源码实测的，
   并且标明了哪些结论可以直接信、哪些需要人工复核。

## 使用示例

一个 1.5.3 里真实存在的模块入口写法。所有签名都能在 `bannerlord-1.5.3/` 下对上：
`MBSubModuleBase.OnGameStart(Game, IGameStarter)` 在 `TaleWorlds.MountAndBlade/MBSubModuleBase.cs`，
`CampaignGameStarter.AddBehavior` / `AddModel` / `AddGameMenuOption` 在
`TaleWorlds.CampaignSystem/CampaignGameStarter.cs`，`Campaign.Current` 在
`TaleWorlds.CampaignSystem/Campaign.cs`，`Clan.PlayerClan` 在 `TaleWorlds.CampaignSystem/Clan.cs`，
`GameMenuOption` 与 `MenuCallbackArgs` 在 `TaleWorlds.CampaignSystem/GameMenus/`。

```csharp
using TaleWorlds.CampaignSystem;
using TaleWorlds.Core;
using TaleWorlds.MountAndBlade;
using TaleWorlds.ObjectSystem;

public class MySubModule : MBSubModuleBase
{
    // 1.5.3 的签名是 (Game, IGameStarter)，不是旧版的 (Game, IModularState)。
    protected internal override void OnGameStart(Game game, IGameStarter gameStarterObject)
    {
        base.OnGameStart(game, gameStarterObject);

        // CampaignGameStarter 是战役侧 IGameStarter 的实现类。
        CampaignGameStarter starter = (CampaignGameStarter)gameStarterObject;

        // 1) 挂战役行为：行为会在战役的各个阶段被 CampaignBehaviorManager 回调。
        starter.AddBehavior(new MyCampaignBehavior());

        // 2) 替换默认算法模型：AddModel<T> 会把 MBGameModel<T> 绑到栈顶的 T 上。
        starter.AddModel(new MyDefaultSettlementProsperityModel());

        // 3) 加一条战役菜单选项。condition / consequence 的委托类型是
        //    GameMenuOption.OnConditionDelegate / .OnConsequenceDelegate，
        //    两者都只接一个 MenuCallbackArgs。
        starter.AddGameMenuOption(
            "town",                                   // menuId：挂在哪个 GameMenu 下
            "my_option",                              // optionId
            "整备部队",                                 // optionText
            (MenuCallbackArgs args) => args.IsEnabled, // condition：只读判断，返回 bool
            (MenuCallbackArgs args) => { /* consequence：在这里改世界状态 */ });

        // Campaign 是世界状态根：所有跨存档的世界事实都在这里读写。
        if (Campaign.Current != null)
        {
            Clan playerClan = Clan.PlayerClan;
        }
    }
}
```

上面省掉了 `using TaleWorlds.CampaignSystem.GameMenus;`。各类型的完整心智模型与成员说明见
[CampaignGameStarter](./api/campaign/CampaignGameStarter) 与 [Campaign](./api/campaign/Campaign)。
