# 发布线读数与提交纪律（READING-RULES）

> **这份清单来自 2026-10-07 的一次会话。** 下面每一条都对应一次**实际发生的误判**——
> 不是格言，不是「最佳实践」，而是某条读数/提交流程在真实执行中**判错**之后被固定下来的动作。
> 每条都按同一格式写：**规则 → 为什么 → 实例 → 量它的命令**。
> 「量它的命令」是这条规则的可核证据：任何人都能重跑它，得到同一个数，从而判断这条规则是否被遵守。
>
> 引用实例时写明文件路径 / SHA / 命令，是为了让「实例」本身也可被复核，而不是转述。

---

## ① 报「某页被改了」/「某文件待入库」前，一律三样一起看

**规则**：在说出「某页被改了」「某文件待入库」之前，必须对同一条路径同时取三样读数：
字节数 + 修改时间、内容哈希、`git status`。三样一起看，缺一不可。

**为什么**：`git status` 的 ` M` 可能只是「测量与报告之间已被提交」的**过期读数**。
单看 `git status` 会把「我测量之后、报告之前被别人提交」误读成「文件被改了」。

**实例**：我多次报「写作线又改了一版」，而 `git status` 为空 ⇒ 是过期读数；boss 因此纠正我 ≥5 次。

**量它的命令**：

```bash
stat -c '%s %y' <path> && md5sum <path> && git status --porcelain -- <path>
```

**判据**：`git status` 为空 ⇒ 不报「被改了」。

## ② 报「门禁红」前，先判「病灶文件是否 untracked」

**规则**：报「门禁红」之前，先取门禁输出的病灶文件列表，再对每个病灶跑 `git status`，
判定它是 `??`（untracked，在制品）还是 ` M`/已入库（真红在 main 上）。

**为什么**：`audit-links.mjs` 扫的是【文件系统（含 untracked）】⇒ 一个 mid-batch 在制品可把权威尺判红，而 main 是绿的。
不判病灶归属就报「门禁红」，会把在制品的临时状态误报成 main 的缺陷。

**实例**：untracked 的 `content/v1.4.6/zh/api/campaign-ext/DiplomaticBartersBehavior.md` 链向 4 个尚未创建的兄弟页 ⇒ 门禁红（`BROKEN_LINKS=7 / FILES_WITH_BROKEN=1`），而该文件不在 HEAD ⇒ HEAD 是绿的。

**量它的命令**：

```bash
node tools/audit-links.mjs | grep -A9 '^## '   # 取病灶
git status --porcelain -- <病灶>                  # 判归属
```

**判据**：病灶是 `??` ⇒ 归属线在制品，**只上报、不修**；是 ` M`/已入库 ⇒ 才是「红在 main 上」。

## ③ 报数必附「量它的命令」

**规则**：任何报数（「N 个文件」「M 条断链」）必须同时附上**量它的命令**，让对方能重跑得到同一个数。

**为什么**：转述比原始测量更容易通过复核。一个没有命令支撑的数，无法被证伪，也就无法被信任。

**实例**：我报「4 个 0 字节文件」为假（实为 2）——git 对非 ASCII 路径加引号，`while read` 把引号当文件名。

**量它的命令（正确法）**：

```bash
git ls-files --others --exclude-standard -z -- tools/ | while IFS= read -r -d '' f; do [ -s "$f" ] || echo "$f"; done
```

**判据**：报数时若给不出可重跑的命令，该数视为未证。

## ④ 改派前必须先撤销原派单

**规则**：把一批任务改派给另一个执行体之前，必须先撤销原派单（`team_cancel <target>` 或发一条「任务已改派，不要执行」）。

**为什么**：否则两个执行体会做同一批，产生重复提交或「已被提交」的冲突。

**实例**：lead-21 把批 20/21/22 同时派给 worker-195 与 worker-234 ⇒ worker-234 先做完，worker-195 发现「已被提交」而停手。本会话实测 1 次，且那次是 lead-21 自己的错。

**量它的命令**：

```bash
team_cancel <target>          # 改派前
# 或发一条「任务已改派，不要执行」
```

**判据**：改派动作完成前，原派单必须已处于已撤销状态。

## ⑤ 提交前跑【全站】尺，不能只跑增量尺

**规则**：提交前必须跑全站尺 `audit-links.mjs`，不能只跑增量尺 `audit-changed-links.mjs`。

**为什么**：`audit-changed-links.mjs` 只看【未提交】文件 ⇒ commit 后对这批失明。
只跑增量尺，会在提交后漏掉刚提交的那批的断链。

**实例**：8 条断链被提交后才被全站尺看见（`FILES_WITH_BROKEN=3`），增量尺在 commit 后不报警。

**量它的命令**：

```bash
node tools/audit-links.mjs; echo "EXIT=$?"    # 不要接管道 —— 管道后的 $? 是 tail 的
```

**判据**：提交前必须看到全站尺的 `EXIT=0`（或已知红已被规则②判定归属）。

## ⑥ 提交前逐路径跑 `git log` + `git status`（防两线抢同一批）

**规则**：提交前对批内每个路径跑 `git log` + `git status`，确认没有别线正在动同一批；
提交一律用 `git commit -m "msg" -- <显式路径>`，且 `-m` 必须在 `--` 之前，pathspec 必须【文件级】。

**为什么**：本会话 3 次「两线抢同一批文件」，其中 2 次根因是裸 `git commit` 卷走别线 staged 文件。
目录级 pathspec 与裸 commit 是同一失败形态的两种写法，都必须禁止。

**实例**：worker-195 执行批 2 时暂存数 5 ≠ 期望 3（多出 lead-145zh 的 2 个 tools 文件）⇒ 停手；随后 lead-145zh 把整个暂存区提交为 `da1dfa7461`。

**量它的命令**：

```bash
while IFS= read -r p; do git log --oneline -3 -- "$p"; git status --porcelain -- "$p"; done < <list>
```

**配套**：提交一律 `git commit -m "msg" -- <显式路径>`（**`-m` 必须在 `--` 之前**；pathspec 必须【文件级】，目录级与裸 commit 是同一失败形态的两种写法）。

**判据**：暂存数 ≠ 期望数 ⇒ 停手，不提交。

## ⑦ 判据必须比语料宽；停滞判据必须用【可双向变化】的观测

**规则**：写判据（正则、条件、阈值）之前，先量语料有几种形态，判据必须覆盖全部形态；
停滞判据必须用【可双向变化】的观测（能触发、也能在推进时自清），不能用单调条件。

**为什么**：判据的失败长得像判据的正常输出——一个比语料窄的判据会报出「看起来对」的数，
一个结构上不可满足的判据会永远报「条件未满足」，而两者都被读成「正常」。

**实例 A（尺比语料窄）**：声明形态实测 **8~9 种**，我那条只认 2 种的正则报了「28/29」。

**实例 B（结构上不可满足）**：兜底判据含单调条件「`BattleCampaignBehavior.md` 仍不存在」——文件一旦创建就永不再消失 ⇒ 该条件永远为假 ⇒ 兜底永远无法触发，而「假」被读成「条件未满足」。

**量它的命令（实例 A）**：

```bash
for f in <files>; do grep -m1 -E 'schema' "$f"; done | cut -c1-30 | sort | uniq -c
# 先看语料有几种形态，再定尺
```

**判据（实例 B）**：停滞判据写成「**该批最新 mtime 距今 > 60 分钟【且】该批仍有未提交文件**」——两条件都能双向变化 ⇒ 能触发、也能在推进时自清。

**判据**：定尺前先量语料形态数；停滞判据的每个条件都必须能双向变化。

## 本清单的适用边界

这份清单是**发布线的读数与提交纪律**，约束的是「如何读数、如何提交」这一层动作。
它**不是项目总契约**——总契约是 `CONTRACT.md`。

**冲突时以 `CONTRACT.md` 为准。** 若本清单某条与 `CONTRACT.md` 冲突，
以 `CONTRACT.md` 为权威，并把冲突点上报 lead-21 裁决，不要自行取舍。

本清单不覆盖：内容写作规范、类文档的心智模型、导航结构设计、版本覆盖范围决策。
这些各有其权威文档，不在本清单的适用范围内。
