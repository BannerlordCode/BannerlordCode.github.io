# Alley

**Namespace:** `TaleWorlds.CampaignSystem.Settlements`
**Module:** `TaleWorlds.CampaignSystem`
**Type:** `public class Alley : SettlementArea`
**Base:** `SettlementArea`
**File:** `bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem.Settlements/Alley.cs`

## 概述

`Alley` 是城镇里的**暗巷**——玩家或敌对匪首占一条巷子，招募打手、赚日薪、被袭击。它继承 [SettlementArea](../SettlementArea)，实现里只有 **4 个 override（`Settlement` / `Name` / `Owner` / `Tag`）+ 1 个 `State` 属性 + `SetOwner` / `Initialize` / 构造器 / `AfterLoad`**。

全类型真正存进存档的只有一个字段：`[SaveableField(10)] private Hero _owner`。`State`（`Empty` / `OccupiedByGangLeader` / `OccupiedByPlayer`）**没有存档标记**，它是读档时由 `AfterLoad()` 重新推导的镜像——**这就是本类型的核心心智模型**。

## 心智模型

把 `Alley` 拆成「**持久层**」与「**派生层**」两半，误用全来自没分清这两半：

- **持久层只有 `_owner`。** `_settlement` / `_tag` / `_name` 都没有存档标记——它们从 `Settlement` 的 XML 重建（唯一构造点 `Settlement.cs:1026` 的 `Alleys.Add(new Alley(this, tag, new TextObject(value)))`）。存档里存的暗巷是**一个 `Alley` 对象引用 + 一个 `Hero` 引用**，位置与名字靠 `Settlement` 那边的定义还原。
- **派生层是 `State`。** `SetOwner` 在第 65 行 `State = ((_owner != Hero.MainHero) ? AreaState.OccupiedByGangLeader : AreaState.OccupiedByPlayer);`，第 69 行 `State = AreaState.Empty;`。`AfterLoad` 在第 90 行复制同一段逻辑。**所以 `State` 永远是 `_owner` 的函数**——只要你不绕过 `SetOwner` 改 `_owner`，它就不会失配。

由此推出必须记住的结论：

1. **`_owner` 是 `private`，唯一的写入口是 `SetOwner`。** 而 `SetOwner` 不只是赋值，它做了四件事：从旧持有者的 `OwnedAlleys` 移除 → 写 `_owner` → 加进新持有者的 `OwnedAlleys` → 重算 `State` → 最后 `CampaignEventDispatcher.Instance.OnAlleyOwnerChanged(this, newOwner, owner)`。**绕过它直接改 `_owner` 会同时丢失双向列表同步、事件派发和 `State` 更新。**
2. **`SetOwner` 里有一行废代码。** 第 58 行 `_owner.OwnedAlleys.Remove(this)` 之后，第 60 行 `Hero owner = _owner;` **无条件**再读一次 `_owner`。此时 `_owner` 还是旧值，所以 `owner` 确实拿到旧持有者——但写成局部变量在 remove 之后才赋值，读起来像 bug。**它能工作是因为顺序恰好正确：remove 用旧值，save 用旧值，赋值用新值。** 别照抄这个顺序。
3. **`Initialize` 是 `public`，因为读档路径真的在用它。** `Settlement` 的 XML 装配按加载类型分岔（`Bannerlord.Source/bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem.Settlements/Settlement.cs:1024`）：

   ```csharp
   if (Campaign.Current.CampaignGameLoadingType != Campaign.GameLoadingType.SavedCampaign)
   {
       Alleys.Add(new Alley(this, tag, new TextObject(value)));
   }
   else
   {
       Alleys[num].Initialize(this, tag, new TextObject(value));
   }
   ```

   新开局走 `new Alley(...)`；读档走 `Alleys[num].Initialize(...)`——**因为 `Settlement.Alleys` 列表本身在存档里（`collectedObjects.Add(Alleys)`，第 529 行），`Alley` 对象已被反序列化出来，此时只需重新绑上 `_settlement` / `_tag` / `_name` 三个不入存档的字段。** 这是 `Initialize` 必须 `public` 的唯一正当理由。**你自己调它去改一条已有 owner 的暗巷会制造跨城镇坏数据。**

4. **`AfterLoad` 是 `internal` 的，mod 调不到。** 它还负责一件历史包袱：读档时若 `MBSaveLoad.LastLoadedGameVersion < ApplicationVersion.FromString("v1.2.0")` 且当前 owner 已死，会 `SetOwner(null); State = AreaState.Empty;`——**1.2.0 之前的存档里的无主暗巷会被自动清空**。1.4.5 读新档时这个分支永不触发。
4. **`State` 与「是不是玩家」是两个问题。** `AreaState.OccupiedByPlayer` 的判据是 `_owner != Hero.MainHero` 的取反，即**owner 引用等于主英雄**。AI 控制的玩家（`_owner == Hero.MainHero` 但不是人类操作）同样会得到 `OccupiedByPlayer`。

## 真实示例

遍历一个城镇的所有暗巷并按状态分类（`Alleys` 是 `Settlement` 上的集合）：

```csharp
Settlement town = Settlement.Find("Epicrotea");
foreach (Alley alley in town.Alleys)
{
    if (alley.State == AreaState.OccupiedByPlayer)
    {
        Debug.Print("player alley " + alley.Tag + " in " + alley.Settlement.Name + " owner=" + alley.Owner.Name, 0);
    }
}
```

把一条暗巷易主，并确认事件确实派发了：

```csharp
Alley target = Settlement.Find("Epicrotea").Alleys[0];
Hero oldOwner = target.Owner;
Hero newOwner = Hero.MainHero;
target.SetOwner(newOwner);
Debug.Print(oldOwner.Name + " -> " + target.Owner.Name + " state=" + target.State, 0);
Debug.Print("main hero owns it = " + target.Owner.OwnedAlleys.Contains(target), 0);
```

放弃一条暗巷（传 null 是合法用法，`State` 会变 `Empty`）：

```csharp
Alley alley = Settlement.Find("Lycaron").Alleys.First((Alley a) => a.State == AreaState.OccupiedByGangLeader);
alley.SetOwner(null);
Debug.Print("owner now " + (alley.Owner == null ? "null" : alley.Owner.Name) + " state=" + alley.State, 0);
```

## 风险与边界

- **`Initialize` 是 `public` 的，但只有读档路径该用它。** 重新初始化一条已有 owner 的暗巷会换掉它的城镇/名字而保留 owner。它在 `Settlement.cs:1028` 的读档分岔里有正当用途，**在别处没有**。
- **`State` 与 `_owner` 可能失配的唯一途径**是绕过 `SetOwner`——目前没有公开途径，但反射或 mod 里的同类改动可以做到。**判 `State` 时若发现与 `Owner` 矛盾，以 `Owner` 为准。**
- **`AfterLoad` 有一个 1.2.0 的历史分支。** `MBSaveLoad.LastLoadedGameVersion < ApplicationVersion.FromString("v1.2.0") && !_owner.IsAlive` 时会 `SetOwner(null)`。读 1.4.5 的存档永不触发，但读跨版本 mod 造的旧存档会。
- **`AfterLoad` 会往 `_owner.OwnedAlleys` 里 `Add(this)`，而 `SetOwner` 也会。** 读档路径只走 `AfterLoad`（不会再调 `SetOwner`，除非命中 1.2.0 分支），所以不会重复；但若你手动在读档后调一次 `SetOwner(sameOwner)`，`OwnedAlleys` 会先 `Remove` 再 `Add`，仍是单份。
- **`Hero.OwnedAlleys` 的一致性由 `SetOwner` 独家维护。** 在 `OnAlleyOwnerChanged` 监听器里读 `newOwner.OwnedAlleys` 时列表**已经更新完毕**（事件在最后派发），可以放心用。
- **`Alley` 对象本身在存档里，但只有 `_owner` 是它的存档字段。** `Settlement.cs:529` 的 `collectedObjects.Add(Alleys)` 把整条暗巷列表收进引用图，而 `Alley` 自己只存 `SaveableField(10)` 的 `_owner`；`_settlement` / `_tag` / `_name` 靠读档时的 `Initialize` 重新绑定。**改这三个字段不入存档，改 `_owner` 才入。**
- **暗巷无法脱离城镇创建。** 构造器要 `Settlement`，而唯一调用点在 `Settlement` 的 XML 装配里。
- **`Name` 带 `[CachedData]`。** 它是本地化 `TextObject`，改语言/读档后由缓存机制处理，手动持有引用跨存档不安全。
