# Save system — 存档系统：把自己的数据写进存档

`TaleWorlds.SaveSystem` 所在的目录。它管一件事：**一个字段怎么进存档、读档时怎么回来**。游戏自身的实体（`Hero`、`Party`）有内建的保存逻辑，不需要经过这里；只有**你自己加的字段**才会走到 `SaveManager`。

这个桶的 3 个页面就是那条完整链路：

| 步骤 | 类型 | 做什么 |
| --- | --- | --- |
| 1 | `SaveableTypeDefiner`（未收录） | 在加载时注册"我的类型由我来存" |
| 2 | [SaveManager](./SaveManager) | 存档时找到你的类型，调用它的保存方法 |
| 3 | [SaveContext](./SaveContext) | 保存过程中的上下文，交给你的类型去写数据 |
| 4 | [LoadContext](./LoadContext) | 读档时的对应物，把数据还给你的类型 |

读写不对称是这套机制最容易踩的地方：`SaveContext` 和 `LoadContext` 是两个不同的类型，你的保存实现和加载实现要成对写，字段顺序要自己保证一致。游戏不会替你检查这件事。

英文树里没有这个目录的页面 —— `SaveManager`、`SaveContext`、`LoadContext` 目前只存在于中文树。

## 本区页面（3）

| 页面 | 讲的是什么 |
| --- | --- |
| [SaveManager](./SaveManager) | 存档的总入口：注册、保存、读回 |
| [SaveContext](./SaveContext) | 保存时你的类型拿到的上下文 |
| [LoadContext](./LoadContext) | 读档时你的类型拿到的上下文 |

3 页是这个桶的骨架，但它是整个文档树里最不完整的一个：保存/读取的实现方法、`SaveableTypeDefiner`、条目 ID 与存档基类、`Definition` 下的存档格式版本机制、以及驱动器（`FileDriver`、`InMemDriver`、`AsyncFileSaveDriver`）都还没有页面。

## 尚未收录

按命名空间属于这个桶、但没有页面的类型包括：`SaveableTypeDefiner`（自定义类型注册的入口）、`SaveableType`、`SaveableEntry`、`EntryId`、`IArchiveContext`、`ArchiveSerializer` / `ArchiveDeserializer` / `ArchiveConcurrentSerializer`、`FileDriver` 与 `InMemDriver` 与 `AsyncFileSaveDriver`、`GameData`、`ContainerType`、`AutoGeneratedSaveManager`，以及 `Definition` 目录下的存档格式版本定义。这是本版本文档里缺口最集中的一个桶 —— 想真正写出一个存档类型，现有页面只够你走到注册那一步。
