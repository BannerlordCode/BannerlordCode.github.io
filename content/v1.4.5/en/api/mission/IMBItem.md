## Overview

`IMBItem` is the bridge to the **weapon-and-ammo behaviour tables**: the native data that answers "what does a usage named `pistol_shot` actually do, where does it sit on the holster, how long does its reload take". The file is 32 lines, the type is `internal`, and `[ScriptingInterfaceBase]` sits at `IMBItem.cs:5`. The public door is `public static class MBItem` (`MBItem.cs:6`), which forwards every one of the eight with a one-line body — `MBItem.cs:8` returns `MBAPI.IMBItem.GetItemUsageIndex(itemUsageName)`, `MBItem.cs:35` wraps the reload result back into an `ActionIndexCache`. `MBItem` is `public static`, so unlike most of this bridge family it is fully reachable from a mod assembly.

Note the naming split that trips people up: **usage** is the behaviour (`pistol_shot`, `onehanded_sword_sword_slash`), **holster** is the resting place on the body. `GetItemUsageIndex` and `GetItemHolsterIndex` (`IMBItem.cs:9`, `:12`) index two separate tables that happen to sit in the same interface.

## Mental Model

Think of the usage table as a **tool board in a workshop**: each hole holds a tool, and the label under the hole is the usage name. `GetItemUsageIndex` finds the hole; `GetItemHolsterIndex` finds a completely different rack, the one that decides what the tool looks like when it is *not* being used. A usage name and a holster name are not interchangeable, and neither one is the item itself — the item is an `ItemObject` in `TaleWorlds.Core`, and this table only knows the animation and mount behaviour attached to a name.

The consequence that matters: **three of the eight members are context-dependent, not name-dependent.** `GetItemUsageReloadActionCode` and `GetItemUsageStrikeType` (`IMBItem.cs:24`, `:27`) both take six parameters, of which `usageDirection`, `isMounted`, `leftHandUsageSetIndex`, `isLeftStance` and `isLowLookDirection` all change the answer. The reload action for a one-handed sword raised overhead is a different action index from the same sword held low. Querying once with a guessed context and caching the result gives you an action that plays in the wrong posture — visibly wrong, never an exception.

The boundary is the same for every member: the bridge reports `int`. A usage name that is not in the table produces an index that is not flagged as missing anywhere in this file, so the guard has to be your own comparison against a known-good usage name.

## How to use

**How to obtain it.** Use `MBItem`, the public static wrapper. The interface itself is `internal` (`IMBItem.cs:6`) and its holder is `internal static IMBItem IMBItem;` (`MBAPI.cs:20`); `TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10` grants `InternalsVisibleTo` only to `TaleWorlds.MountAndBlade.AutoGenerated`, `TaleWorlds.MountAndBlade.Multiplayer` and `TaleWorlds.Generator.Bannerlord`. Unlike the neighbours in this bucket, `MBItem` needs no such detour — it is public.

**A typical use.** A mod that wants to pick the correct reload action for the pose the agent is actually in, which is the reason those six parameters exist. `Agent.GetIsLeftStance()` is a method (`Agent.cs:2843`) and mount state comes from `Agent.HasMount` (`Agent.cs:720`):

```csharp
using TaleWorlds.MountAndBlade;

Agent agent = null;
foreach (Agent a in Mission.Current.AttackerTeam.ActiveAgents)
{
    agent = a;
    break;
}
if (agent == null)
{
    return;
}

ActionIndexCache reload = MBItem.GetItemUsageReloadActionCode(
    "onehanded_sword_sword_slash",
    0,
    agent.HasMount,
    0,
    agent.GetIsLeftStance(),
    false);
Debug.Print("reload action for this pose = " + reload.GetName() + " on agent " + agent.Index, 0);
```

Check whether a usage is passive before wiring it to an input — a passive usage never fires on its own:

```csharp
using TaleWorlds.MountAndBlade;

bool needsManualTrigger = !MBItem.GetItemIsPassiveUsage("onehanded_sword_sword_slash");
Debug.Print("requires an explicit action = " + needsManualTrigger, 0);
```

**What to watch out for.** The single most common mistake is calling `GetItemUsageReloadActionCode` or `GetItemUsageStrikeType` once and reusing the result. Because the answer depends on posture, mount state and stance (`IMBItem.cs:24`, `:27`), a cached action index taken while the agent was mounted and walking is spent later while the agent is on foot and looking up. The consequence is a reload animation that plays from the wrong stance, and because the index is a perfectly valid one, nothing complains.

## Examples

Resolve a usage index and confirm it round-trips before you depend on it:

```csharp
using TaleWorlds.MountAndBlade;

int usageIndex = MBItem.GetItemUsageIndex("onehanded_sword_sword_slash");
Debug.Print("usage row = " + usageIndex, 0);
Debug.Print("passive = " + MBItem.GetItemIsPassiveUsage("onehanded_sword_sword_slash"), 0);
```

Ask for the reload action twice, in two different stances, to show that the answer is context-dependent:

```csharp
using TaleWorlds.MountAndBlade;

string usage = "onehanded_sword_sword_slash";
ActionIndexCache onFoot = MBItem.GetItemUsageReloadActionCode(usage, 0, false, 0, false, false);
ActionIndexCache onHorse = MBItem.GetItemUsageReloadActionCode(usage, 0, true, 0, false, false);
Debug.Print("dismounted reload = " + onFoot.GetName(), 0);
Debug.Print("mounted reload    = " + onHorse.GetName(), 0);
```

Read the holster frame to know where an idle weapon rests, and the set flags to know what the usage allows:

```csharp
using TaleWorlds.MountAndBlade;
using TaleWorlds.Library;

int holsterIndex = MBItem.GetItemHolsterIndex("holster_back");
MatrixFrame holsterFrame = MBItem.GetHolsterFrameByIndex(holsterIndex);
Debug.Print("back holster frame = " + holsterFrame, 0);

ItemObject.ItemUsageSetFlags flags = MBItem.GetItemUsageSetFlags("onehanded_sword_sword_slash");
Debug.Print("usage set flags = " + flags, 0);
```

Estimate how far a thrown or fired weapon travels before writing an AI range check:

```csharp
using TaleWorlds.MountAndBlade;

float rangeOnFlat = MBItem.GetMissileRange(55f, 0f);
float rangeUphill = MBItem.GetMissileRange(55f, 20f);
Debug.Print("flat range " + rangeOnFlat + "m, uphill range " + rangeUphill + "m", 0);
```

## Risks and crash boundaries

- **The interface is unreachable; the wrapper is not.** `internal interface IMBItem` (`IMBItem.cs:6`) and `internal static IMBItem IMBItem;` (`MBAPI.cs:20`), but `public static class MBItem` (`MBItem.cs:6`) is a normal public static class. Use the wrapper.
- **Unknown names are indistinguishable from known ones.** Nothing in the file validates `itemusagename`, `itemholstername` or `ItemUsageName`. A typo yields a valid-looking index, and the first symptom is a weapon that animates like a different weapon.
- **Usage and holster are different tables.** `get_item_usage_index` (`:8`) and `get_item_holster_index` (`:11`) index independently; swapping the two names compiles and misbehaves.
- **`GetItemUsageSetFlags` returns `int` and the wrapper casts it** (`MBItem.cs:32`). There is no validation that the bits are a legal combination.
- **Posture-dependent members must be queried live.** `GetItemUsageReloadActionCode` and `GetItemUsageStrikeType` both take six parameters (`:24`, `:27`); caching their result across a stance or mount change is the primary trap on this type.
- **`GetHolsterFrameByIndex` writes through a `ref`.** The wrapper relies on native mutation of its local (`MBItem.cs:25-27`); if the native call is skipped the returned frame is default-initialised, i.e. the origin.
- **Duplicated ballistics helper.** `get_missile_range` appears on both this interface (`:29`) and `IMBMission` (`IMBMission.cs:136`). Confirm which one you are calling before assuming equal results.
- **Not a save participant.** No `[Serializable]`, no sync surface; it is a stateless table read.
