# PropertyObject

**Namespace:** `TaleWorlds.Core`
**Module:** `TaleWorlds.Core`
**Type:** `public class PropertyObject : MBObjectBase`
**Base:** `TaleWorlds.ObjectSystem.MBObjectBase`
**File:** `TaleWorlds.Core/PropertyObject.cs`

## 概述

`PropertyObject` 是「一个可被 `MBObjectManager` 寻址、且带本地化名称与描述的数据对象」这条基线的抽象。它本身只有两个字段（`TextObject _name` 与 `TextObject _description`）和三个公开方法（`GetName()`、`Initialize(name, description)`、构造函数），70 行源码，是整个 [TaleWorlds.Core](../) 里最薄的非抽象基类之一。它存在的唯一理由是**给一整族内容对象提供统一的「名字 + 描述」契约**：`TaleWorlds.Core` 里的 [SkillObject](../SkillObject) 与 `BannerEffect`，以及 `TaleWorlds.CampaignSystem` 里的 `PerkObject` / `FeatObject` / `TraitObject` / `SkillEffect` / `CultureTrait` / `Figurehead` / `PolicyObject` 全部继承它。在存档侧它还有一个额外身份：`SaveableCoreTypeDefiner` 用 `AddClassDefinition(typeof(PropertyObject), 38, null)` 把它注册成可保存类型，`Campaign` 里的 `PropertyOwner<PropertyObject>` 与 `HeroDeveloper` 的 `Dictionary<PropertyObject, float>` 都以它为键类型。

## 心智模型

**把它当成 `MBObjectBase` 与「本地化元数据」之间的那层薄适配器。** `MBObjectBase.GetName()` 的默认实现返回 `new TextObject(this.StringId, null)`——用 StringId 当显示名，这对 `ItemObject` / `Monster` 这类有专门 Name 属性的对象无所谓，但对技能、专长、特性这类**名字本身就是内容**的对象就完全不够。`PropertyObject` 覆盖 `GetName()` 返回 `Name`，于是全树任何拿到 `MBObjectBase` 引用再调 `GetName()` 的通用代码（tooltip、列表项、AI 评估）都能拿到正确的中文显示名。**这就是这个基类的全部存在价值：让通用 UI 代码不需要知道具体类型就能显示名字。**

第二个心智锚点是 **`Initialize` 只赋值，不调 `AfterInitialized()`**。它的实现是 `base.Initialize(); this._name = name; this._description = description;`。`base.Initialize()` 只是把 `IsInitialized` 置 true；`IsReady` 是在 `AfterInitialized()` 里、且**仅当 `IsRegistered` 为 true 时**才置 true。所以手工调 `Initialize` 造出来的对象 `IsReady` 永远是 false。看派生类怎么处理就知道这是有意还是疏忽：[BannerEffect](../Banner) 的 `Initialize` 显式在末尾补了一句 `base.AfterInitialized();`——**说明这是官方认可的标准收尾动作，每个自定义子类都要自己做。** 忘了补，对象在游戏里表现为「已初始化但未就绪」，具体症状是各种 `IsReady` 门禁把它当没加载完。

第三个是**两个字段都不做 null 保护**。`Name` 与 `Description` 的 getter 直接返回 `_name` / `_description`，构造器只调 `base(stringId)`，**不初始化这两个字段**。所以 `new PropertyObject("some_id")` 之后 `Name` 与 `Description` 都是 null，`GetName()` 返回 null。1.4.6 里没有 `MBObjectBase` 那种 `TextObject.GetEmpty()` 兜底。要判断显示名请用 `TextObject.IsNullOrEmpty(...)`，不要直接 `.ToString()`。

第四个是 **`Initialize` 不是幂等的但可以重复调**。它是公开方法，重复调会覆盖已有名字，无任何检查。派生类通常在自己的 `Deserialize` 或工厂里调一次。

第五个是**它同时是「属性家族」的集合类型**。`Campaign` 用 `new PropertyOwner<PropertyObject>()` 存玩家的特性/专长加成，`HeroDeveloper` 用 `new Dictionary<PropertyObject, float>()` 存技能 XP。**这意味着 `PropertyObject` 的实例会被当字典键用**——而 `MBObjectBase.GetHashCode()` 返回 `this.Id.GetHashCode()`，`Id` 是 `MBGUID`。**未经 `MBObjectManager` 注册的实例 `Id` 是 `default(MBGUID)`，哈希全为 0**，多个这样的实例当键会互相覆盖。跟 `ItemObject` 的空物品撞码是同一个根因。

最后一条：**没有 `new PropertyObject(` 的调用点**。全树 11,385 个 `.cs` 里一次都没有（`new PropertyOwner<PropertyObject>()` 是泛型容器，不是本类型）。本类型只在**继承**的位置出现，永远是抽象意图上的基底。要造自己的属性对象，就继承它并在自己的加载流程里调 `Initialize` + `AfterInitialized`。

## 怎么用

### 怎么拿到它

`PropertyObject` 是 `public class PropertyObject : MBObjectBase`（`TaleWorlds.Core/PropertyObject.cs:9`），全文只有 70 行。它的定位很窄：**一个带名字和说明的 `MBObjectBase` 基类**。

公开面只有四个成员：

- `public TextObject Name`（`:25`）——**公开字段**。
- `public override TextObject GetName()`（`:34`）——覆写 `MBObjectBase.GetName()`（`MBObjectBase.cs:112`），直接返回 `Name`。
- `public TextObject Description`（`:41`）——也是公开字段。
- `public PropertyObject(string stringId)`（`:50`）与 `public void Initialize(TextObject name, TextObject description)`（`:56`）。

内置派生类只有三个，全是 sealed 且都只有一个 `stringId` 构造器：[SkillObject](../SkillObject)（`SkillObject.cs:28`）、`BannerEffect`（`BannerEffect.cs:16`），以及英雄特质那一族。`Game.RegisterTypes` 也会把它们注册进 `MBObjectManager`（id 区间 2–53）。

### 典型用法

```csharp
using TaleWorlds.Core;

// 取现成的
SkillObject tactics = DefaultSkills.Tactics;                    // DefaultSkills.cs:111
TextObject label = tactics.GetName();                           // PropertyObject.cs:34 → 直接返回 Name 字段
TextObject desc  = tactics.Description;                         // :41

// 自己建一个 PropertyObject（它不是 sealed）
public class TraitObjectLike : PropertyObject                    // :9
{
    public TraitObjectLike(string stringId) : base(stringId) { }
}

// 字段是公开可写的，但推荐用 Initialize 一次填两个
var p = new PropertyObject("my_mod_property");                  // :50
p.Initialize(new TextObject("{=name}我的属性"), new TextObject("{=desc}说明"));   // :56
```

### 最容易踩的坑

**写了 `Name` 字段却忘了 `Description` 是 null，然后在 UI 上拼出 null 引用的异常。** 两个都是公开字段（`:25`、`:41`），都**没有默认初始化**——`new PropertyObject("id")`（`:50`）之后两个都是 null。而 `GetName()`（`:34`）无条件返回 `Name`，引擎内部很多地方（UI 列表项、调试输出）会直接调它。所以自定义属性时要么用 `Initialize`（`:56`）一次性填两个，要么确保两个都赋过值。

第二个坑是继承层次上的一处误读：`Name` 和 `Description` 是**字段**，`GetName()` 是**覆写的方法**。给子类遮蔽（shadow）成同名属性不会影响 `GetName()` 的返回值，而 `MBObjectBase` 的其他路径（如 `ToString()` 风格的地方）调的可能是字段、也可能是方法——遮蔽属性之后两者会给出不同的值。**不要遮蔽，直接赋值。**

    }

    }

## 风险与边界

- **构造后 `Name` 与 `Description` 都是 null。** 构造器只设 StringId。要么走 `Initialize`，要么用 `TextObject.IsNullOrEmpty` 判空。**没有 `TextObject.GetEmpty()` 兜底。**
- **`Initialize` 不调 `AfterInitialized()`。** 手工装配的实例 `IsReady` 永远 false（`AfterInitialized` 只在 `IsRegistered` 为 true 时才置 `IsReady`）。子类必须自己补，[BannerEffect](../Banner) 就是范例。
- **没有无参构造器。** 子类必须转发 StringId。
- **子类必须覆盖 `GetName()` 才有意义。** 父类的实现只是返回 `Name`，如果子类改用别的字段存名字，就得同时覆盖 `GetName()`，否则通用 UI 会显示 null。
- **实例哈希依赖 `Id`。** `MBObjectBase.GetHashCode()` 返回 `this.Id.GetHashCode()`，**未注册实例的 `Id` 是 `default(MBGUID)`，哈希全为 0**。而 `Campaign` 的 `PropertyOwner<PropertyObject>` 与 `HeroDeveloper` 的 `Dictionary<PropertyObject, float>` 正好拿它当键——**手工 `new` 的实例当键会互相覆盖。**
- **`AutoGeneratedInstanceCollectObjects` 是空的。** 两个 `TextObject` 字段不进存档引用收集。实际影响有限，因为这些对象按 StringId 从 XML 重建。
- **不是 `sealed`，是设计上的扩展基类。** 全树 8 个派生类分布在 `TaleWorlds.Core`（[SkillObject](../SkillObject)、`BannerEffect`）与 `TaleWorlds.CampaignSystem`（`PerkObject` / `FeatObject` / `TraitObject` / `SkillEffect` / `CultureTrait` / `Figurehead` / `PolicyObject`）两个程序集里。
- **全树无 `new PropertyObject(`。** 它只在继承位置出现。
- **名字与描述可变。** `Initialize` 公开且无幂等保护，重复调用会覆盖已显示的名字。多语言切换或热重载时要小心。
- **注意与 `ItemModifierGroup` 混淆。** 后者名字里有 `Group`，与本类型**没有任何继承或组合关系**，只是命名相似。

## 跨版本提示

`bannerlord-1.3.15/` 与 `bannerlord-1.4.6/` 的 `TaleWorlds.Core/PropertyObject.cs` 公开表面**完全一致**（6 个公开成员、2 个私有字段）。但**派生家族在 1.4.6 有变化**：1.4.6 新增了 `TraitObject`（`TaleWorlds.CampaignSystem/CharacterDevelopment/TraitObject.cs`）并让 `CharacterHelper` / `Hero` 等改走「特性」路径；1.3.15 的对应形态由 `CultureTrait` / `HeroTraitDeveloperResolver` 承担。

**1.4.5 侧结论**：打开 `bannerlord-1.4.5/Bannerlord.Source/bin/TaleWorlds.Core/TaleWorlds.Core/PropertyObject.cs`（44 行）与 `bannerlord-1.4.6/TaleWorlds.Core/PropertyObject.cs`（70 行）逐成员比对 public/protected 表面。**本类自身三版完全一致（各 6 个成员，0 新增 / 0 移除 / 0 签名变化 / 0 可访问性变化）**。**本段上文关于派生家族的说法要撤回** —— 实测 `TraitObject.cs` 在**三个版本里都存在**（1.3.15 与 1.4.6 在 `<Module>/CharacterDevelopment/` 下，1.4.5 在 `bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem.CharacterDevelopment/` 下），且 `Hero.cs` 在三个版本里**都恰好引用 `TraitObject` 5 次、都 0 次引用 `CultureTrait`**；`CultureTrait.cs` 与 `HeroTraitDeveloperResolver.cs` 同样三个版本都在。**所以 1.3.15 → 1.4.6 这个区间内并没有发生本段上文描述的「新增 `TraitObject` 并改走特性路径」的演化。**

**为什么这份源码之前被判为「不存在」**：`bannerlord-1.4.5/` 的 C# 源码在 `Bannerlord.Source/bin/` 下**双层嵌套** `bin/<Assembly>/<Assembly>/<Type>.cs`，而 `bin/` 的一层里没有任何 `.cs`（实测 `find bannerlord-1.4.5/Bannerlord.Source/bin -maxdepth 1 -name "*.cs"` 命中 0），只扫一层就会误判成无源码。**1.4.5 是原始源码形态**（file-scoped namespace、无 `// Token:` 注释），1.4.6 与 1.3.15 是反编译产物，所以两边的行数不可直接比大小。
