## 概述

`DefinitionContext` 是**存档系统的类型表本体**。它把「.NET 类型 ↔ 存档编号」的全量映射握在手里：内部有约二十个字典，每一类定义（根类、类、结构体、接口、枚举、容器、泛型类、泛型结构体、基础类型）都同时按 `Type` 和按 `SaveId` 建两份索引，另有两份「全类型」合并索引，以及冲突解析器表。

它不是你要手动 `new` 的工具类，而是由 `SaveManager` 拥有：`TaleWorlds.SaveSystem/SaveManager.cs:19` 在初始化时建一个全局实例并立即 `FillWithCurrentTypes()`；`TaleWorlds.SaveSystem/SaveManager.cs:158` 在每次 `Load` 时**再建一个全新的实例**重新填表。后者是重要事实——类型表是「每次读档重建」的，不是全局只建一次。

填表过程（`FillWithCurrentTypes`，`DefinitionContext.cs:173`）是 `SaveableTypeDefiner` 各阶段的驱动者：先 `GetSaveableAssemblies()` + `CollectTypes()` 找出并实例化全部 definer，再按固定顺序回调它们的十来个 `Define*`，最后收集成员、错误与自动生成的 save manager。

## 心智模型

把它想成三件事的组合：一张**双向索引类型字典**、一个**错误收集器**、一个**代码生成出口**。中间那层「注册与查询」才是它的本体。

**① 双向索引。** 写入存档时对象带着运行时 `Type`，需要查编号 ⇒ 走 `Type` 键；读取旧档时字节流里只有编号，需要查回类型 ⇒ 走 `SaveId` 键。所以 `AddClassDefinition`（`DefinitionContext.cs:68`）一次往四个字典里写：按类型、按编号、以及两份全类型合并索引。`GetTypeDefinition(Type)`（`DefinitionContext.cs:292`）查的是合并索引，所以它能一次命中任意类别的定义。

**② 类别之间有优先级。** `GetClassDefinition`（`DefinitionContext.cs:303`）不是简单查表：它先拒绝容器（`type.IsContainer()` 直接返回 null），再依次查**根类 → 泛型类 → 普通类**，第一个命中即返回。这意味着同一个类型既被登记为根类又被登记为普通类时，根类身份胜出。`GetStructDefinition`（`DefinitionContext.cs:468`）同样先查泛型结构体再查普通结构体。

**③ 泛型是「两段式」，编号是复合的。** 开放泛型 `KeyValuePair<,>` 先登记一条普通定义，闭合类型再通过 `ConstructGenericClassDefinition`（`DefinitionContext.cs:384`）构造：它取开放定义的 `SaveId` 作为 `BaseId`，再把每个泛型实参的定义编号收进数组，拼成一个 `GenericSaveId`。读取时 `TryGetTypeDefinition`（`DefinitionContext.cs:328`）遇到 `GenericSaveId` 会反向走同一条路：解析 `BaseId`、解析每个 `GenericTypeIDs`、用 `ConstructTypeFrom`（`DefinitionContext.cs:451`）拼出闭合 `Type` 再查表。**任一实参查不到就整条返回 null**——这是「泛型类型读不回来」的根因。

**④ 容器登记会「顺带展开」。** `ConstructContainerDefinition`（`DefinitionContext.cs:416`）除了登记 `List<T>` 本身，还会自动补登记 `MBList<T>`（`CustomList`）与 `MBReadOnlyList<T>`（`CustomReadOnlyList`）两个兄弟——这就是为什么 mod 里把 `List<T>` 字段换成 `MBList<T>` 后旧档仍能读。

**⑤ 错误不抛异常，只累积。** `GotError`（`DefinitionContext.cs:14`）就是「错误表非空」，`Errors`（`DefinitionContext.cs:24`）把内部列表只读暴露出来。`SaveManager` 在 `TaleWorlds.SaveSystem/SaveManager.cs:78` 检查它并在 `SaveManager.cs:81` 逐条打印。**所以「定义有错」的表现是日志文字，而不是崩溃**——这也是漏注册的类型经常要到读档时才暴露的原因。

## 怎么用

### 怎么拿到

只在两种场景下你会碰到它：作为 definer 作者（框架把它注入给你），或作为工具作者（自己建一个来填表）。

```csharp
// 场景一：框架注入。SaveableTypeDefiner.Initialize 把它存进 _definitionContext，
// 你在 Define* 回调里用的 Add* 方法最终都转发到这个实例上。

// 场景二：自己建一个（官方 SaveManager 与代码生成器都这么做）
DefinitionContext definitionContext = new DefinitionContext();   // SaveManager.cs:158
definitionContext.FillWithCurrentTypes();                        // DefinitionContext.cs:173
```

### 典型用法

填表后按编号查回类型定义——这是自动生成的 save manager 的标准动作：

```csharp
// 形状同 SandBox/Sandbox/AutoGeneratedSaveManager.cs:17
TypeDefinition typeDefinition =
    (TypeDefinition)definitionContext.TryGetTypeDefinition(new TypeSaveId(1087001));

if (typeDefinition != null)
{
    // 拿到了类型定义，可以继续做成员级别的绑定
}
```

检查定义表是否健康（官方 SaveManager 的做法）：

```csharp
// TaleWorlds.SaveSystem/SaveManager.cs:78 与 TaleWorlds.SaveSystem/SaveManager.cs:81
if (SaveManager._definitionContext.GotError)
{
    foreach (string text in SaveManager._definitionContext.Errors)
    {
        Debug.Print(text, 0, Debug.DebugColor.White, 17592186044416L);
    }
}
```

用代码生成器把类型表导出成 C# 源文件：

```csharp
// TaleWorlds.MountAndBlade.SaveSystem.CodeGenerator/Program.cs:46
SaveCodeGenerationContext saveCodeGenerationContext = new SaveCodeGenerationContext(definitionContext);
definitionContext.FillWithCurrentTypes();
definitionContext.GenerateCode(saveCodeGenerationContext);      // DefinitionContext.cs:567
```

### 坑

- **类型表是每次读档重建的。** `SaveManager.Load` 每次 `new DefinitionContext()`（`SaveManager.cs:158`）再 `FillWithCurrentTypes()`，所以 definer 的构造器与全部 `Define*` 会**反复执行**。别在里面做重活，也别依赖「只跑一次」。
- **`Add*` 底层是 `Dictionary.Add`，重复即抛。** 同一类型或同一编号注册两次会抛异常，而 `ConstructContainerDefinition`（`DefinitionContext.cs:416`）走的是 `HasDefinition`（`DefinitionContext.cs:410`）检查 + `Debug.FailedAssert`，只警告不抛。两者行为不一致，是排查重复注册时最容易混的地方。
- **`AddConflictResolver` 会静默丢弃。** `DefinitionContext.cs:122` 先 `GetClassDefinition(conflictResolver.GetNewType())`，若拿不到定义就**什么都不做**——解析器被丢掉，且没有任何日志。旧档兼容失效时先查这里。
- **错误不中断流程。** `GotError` 为真时程序照常往下走。生产环境里这个错误很容易被忽略，直到某个对象读回来是 null。
- **`FillWithCurrentTypes` 依赖 AppDomain 扫描。** 它只挑「引用了 `TaleWorlds.SaveSystem`」的程序集（`DefinitionContext.cs:254`），且要求 definer 有公开无参构造（`DefinitionContext.cs:279` 用 `Activator.CreateInstance`）。动态加载时机不对可能整批 definer 都扫不到。
- **`_errors` 是公开字段。** 任何代码都能往错误表里塞字符串、也能清空它。别依赖它做流程控制。

## 真实示例

一个典型的「填表 → 查回类型 → 校验」小流程：

```csharp
var definitionContext = new DefinitionContext();
definitionContext.FillWithCurrentTypes();                       // DefinitionContext.cs:173

if (definitionContext.GotError)                                 // DefinitionContext.cs:14
{
    foreach (string text in definitionContext.Errors)            // DefinitionContext.cs:24
    {
        Debug.Print("[savesys] " + text, 0);
    }
}

// 按编号查回类型定义：30001 是内置 definer 登记的 int
TypeDefinitionBase def =
    definitionContext.TryGetTypeDefinition(new TypeSaveId(30001));   // DefinitionContext.cs:328
Debug.Print(def != null ? def.Type.Name : "int 未登记");
```

旧档兼容的编号重定向，读 `TryGetTypeDefinition` 的头几行就懂了：

```csharp
// TaleWorlds.SaveSystem/Definition/DefinitionContext.cs:328 起
IConflictResolver conflictResolver;
if (SaveManager.ShouldResolveConflicts()
    && this._conflictResolvers.TryGetValue(saveId, out conflictResolver)
    && conflictResolver.IsApplicable(SaveManager.OperatingVersion))
{
    return this.GetTypeDefinition(conflictResolver.GetNewType());   // 老编号 → 新类型
}
```

`AddConflictResolver` 静默丢弃的写法（旧档兼容失效时的第一嫌疑点）：

```csharp
// TaleWorlds.SaveSystem/Definition/DefinitionContext.cs:122 起
internal void AddConflictResolver(TypeSaveId saveId, IConflictResolver conflictResolver)
{
    TypeDefinitionBase classDefinition = this.GetClassDefinition(conflictResolver.GetNewType());
    if (classDefinition != null)          // ← 拿不到定义就什么都不做，也没有日志
    {
        this._conflictResolvers.Add(saveId, conflictResolver);
        this._conflictResolversWithType.Add(classDefinition, conflictResolver);
    }
}
```

冲突解析器的真实实现（`v1.3.0` 之前把 `CharacterAttribute` 的所有者换成泛型 `PropertyOwner<T>`）：

```csharp
// TaleWorlds.CampaignSystem/SaveCompability/CharacterAttributesResolver.cs:10
public class CharacterAttributesResolver : IConflictResolver
{
    public bool IsApplicable(ApplicationVersion version)
        => version != ApplicationVersion.Empty
           && version.IsOlderThan(ApplicationVersion.FromString("v1.3.0", 0));

    public Type GetNewType() => typeof(PropertyOwner<CharacterAttribute>);
}
```
