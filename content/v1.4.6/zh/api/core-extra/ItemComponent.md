# ItemComponent

**Namespace:** `TaleWorlds.Core`
**Module:** `TaleWorlds.Core`
**Type:** `public abstract class ItemComponent : MBObjectBase`
**Base:** `TaleWorlds.ObjectSystem.MBObjectBase`
**File:** `TaleWorlds.Core/ItemComponent.cs`

## 概述

`ItemComponent` 是 [ItemObject](../ItemObject) 的行为插槽。它自己不带任何数值，只回答两个问题：「我挂在哪个物品上」（`Item`）和「这个物品用哪一组品质词缀」（`ItemModifierGroup`）。真正干活的是派生类：[ArmorComponent](../ArmorComponent) 放护甲值与身体遮挡遮罩，[HorseComponent](../HorseComponent) 放坐骑机动/速度/负重，[WeaponComponent](../WeaponComponent) 放武器形态列表，[BannerComponent](../BannerComponent) 在武器之上再叠旗帜效果，[TradeItemComponent](../TradeItemComponent) 放士气加成，[SaddleComponent](../SaddleComponent) 是没有任何成员的纯标记。

在物品体系里它承担的是**能力**这一环。[ItemObject](../ItemObject) 存的是**静态数据**（mesh 名、数值、标志位），组件存的是**行为**。`ItemObject.WeaponComponent` / `ArmorComponent` / `HorseComponent` / `BannerComponent` / `SaddleComponent` / `FoodComponent` 六个访问器全部是 `this.ItemComponent as XxxComponent`，所以外部永远不要自己 `new` 一个组件再塞回去——那条路在 `ItemObject` 上是 `private set`。

## 心智模型

把它当成**单槽策略对象**就对了，别的都顺。装配发生在 `ItemObject.Deserialize` 里：遍历 `<Item>` 的子节点，遇到 `<ItemComponent>` 就再遍历它的子节点，**按子节点名硬编码分支**——`<Armor>` → `new ArmorComponent(this)`，`<Weapon>` → `this.ItemComponent ?? new WeaponComponent(this)`，`<Horse>` → `new HorseComponent()`，`<Trade>` → `new TradeItemComponent()`，`<Banner>` → `new BannerComponent(this)`，`<Food>` → 触发 `Debug.FailedAssert` 并把组件置 null（官方提示「FoodComponent tag 已改名为 Trade，请用 Trade」），其它任何标签名直接 `throw new Exception("Wrong ItemComponent type.")`。每个分支都紧跟一句 `itemComponent.Deserialize(objectManager, xmlNode12)` 再 `this.ItemComponent = itemComponent`——**后写的覆盖先写的**。

由此推出四个必须记住的结论。第一，**SaddleComponent 在 1.4.6 里从 XML 走不到**：全树 11,385 个 `.cs` 中 `new SaddleComponent(` 只出现在它自己的 `GetCopy()` 里，`ItemObject.Deserialize` 的标签分支表没有 `<Saddle>`。它能存在的唯一途径是程序化赋值，而 `ItemObject.ItemComponent` 又是 `private set`——所以这个类型在 1.4.6 的实际运行时里基本是死的。第二，**`<Weapon>` 是唯一可累加的分支**，因为它复用 `this.ItemComponent ?? new WeaponComponent(this)`：一个 `<Weapon>` 节点 `WeaponComponent.Deserialize` 往 `_weaponList` 里 `Add` 一条 `WeaponComponentData`，多个 `<Weapon>` 节点就是一条武器的多形态（刀 / 刀鞘）。第三，`<Banner>` 造出的 `BannerComponent` **本身就是一个 `WeaponComponent`**（它继承后者），所以它也占单槽；此后若再出现 `<Weapon>` 节点，`this.ItemComponent ?? new WeaponComponent(this)` 会命中那个 `BannerComponent` 并往它的 `_weaponList` 里加形态。第四，**别写 `new` + `Deserialize` 的手工装配**，那会绕过 `MBObjectManager` 的注册流程；`Deserialize` 里的 `modifier_group` 靠 `Game.Current.ObjectManager.GetObject<ItemModifierGroup>(text)` 解析，`Game.Current` 为 null 时直接 NRE。

`Item` 属性是 `public` 的 getter **和** setter，这是整个类型里最危险的一处：它本意是给 `ArmorComponent(ItemObject item)` / `WeaponComponent(ItemObject item)` / `BannerComponent(ItemObject item)` 这三个构造器在 `base.Item = item` 时用，但外部代码同样能写。手动改它会造成 `item.ItemComponent.Item != item` 的环形不一致，而且不会有任何断言拦住你。

最后一个心智锚点：**组件不是存档数据**。`ItemComponent.AutoGeneratedInstanceCollectObjects` 的实现是空的（只有一句 `base` 调用），`ItemObject` 的同名方法也一样，全树没有任何一处 `collectedObjects.Add(...ItemComponent...)`。存档存的是物品的 StringId，读档时重新按 id 加载 XML，组件随之重建。**改组件的 XML 定义不会破坏旧存档，但会让旧存档里的物品表现变成新定义。**

## 关键成员

| 成员 | 签名 | 这个成员是做什么用的 |
| --- | --- | --- |
| `Item` | `public ItemObject Item { get; set; }` | 指向宿主物品的双向指针。**setter 是公开的**——外部改它会让 `ItemComponent.Item` 与 `ItemObject.ItemComponent` 失去一致性，且无断言拦截。只有三个构造器会正常写它。 |
| `ItemModifierGroup` | `public ItemModifierGroup ItemModifierGroup { get; protected set; }` | 该物品的品质词缀组，由 XML 的 `modifier_group` 属性解析而来。**setter 是 `protected`**，只有派生类能写——[WeaponComponent](../WeaponComponent) 的 `AddWeapon` 就是通过它把词缀组从 `ItemObject` 转发到组件上的。属性缺失时为 null，不回退到默认组。 |
| `Deserialize` | `public override void Deserialize(MBObjectManager objectManager, XmlNode node)` | 先 `Initialize()`（把 `IsInitialized` 置 true），再读 `node.Attributes["modifier_group"]`；值非 null 时走 `Game.Current.ObjectManager.GetObject<ItemModifierGroup>(text)`。**依赖 `Game.Current`**，加载期之外调用会 NRE。**每个派生类的 `Deserialize` 都必须先 `base.Deserialize(...)`**，否则 `modifier_group` 不会被解析——[TradeItemComponent](../TradeItemComponent) 就是反例（见该页）。 |
| `GetCopy` | `public abstract ItemComponent GetCopy()` | 抽象深拷贝。全树只有两个调用方：`Crafting.cs`（6 处）与 `CraftingCampaignBehavior.cs`（2 处），都在合成武器重建流程里。**各派生类的实现完整度不一致**——[ArmorComponent](../ArmorComponent) 漏拷 `IsNoSlim`，[HorseComponent](../HorseComponent) 只拷四个 int，别当成通用 Clone。 |
| `AutoGeneratedInstanceCollectObjects` | `protected override void AutoGeneratedInstanceCollectObjects(List<object> collectedObjects)` | 存档遍历用的引用收集钩子。**基类实现是空的，只调 `base`**；`Item` 与 `ItemModifierGroup` 都不会进入 `collectedObjects`。所有派生类也都只是 `base` 调用，没有一个补上——因为组件本身就随 XML 重建，不进存档。 |

## 真实示例

读一个物品的组件，按派生类型分支（**先判 `HasXxxComponent` 再用**）：

```csharp
ItemObject item = MBObjectManager.Instance.GetObject<ItemObject>("my_custom_armor");
if (item == null)
{
    Debug.Print("item not loaded", 0);
    return;
}

if (item.HasWeaponComponent)
{
    WeaponComponentData primary = item.PrimaryWeapon;
    Debug.Print("class=" + primary.WeaponClass + " swing=" + primary.SwingDamage, 0);
}

if (item.ArmorComponent != null)
{
    Debug.Print("body armor=" + item.ArmorComponent.BodyArmor, 0);
}
```

直接向基类要引用，而不是靠派生类型猜：

```csharp
ItemObject helmet = hero.BattleEquipment.GetEquipmentFromSlot(EquipmentIndex.Head).Item;
ItemComponent component = helmet.ItemComponent;
if (component == null)
{
    Debug.Print("no component on " + helmet.StringId, 0);
}
else
{
    Debug.Print("component type = " + component.GetType().Name, 0);
    Debug.Print("modifier group = " + component.ItemModifierGroup, 0);
    Debug.Print("host item id = " + component.Item.StringId, 0);
}
```

走游戏自己的路径装一个带护甲组件的物品（`ItemObject.ItemComponent` 是 `private set`，`ArmorComponent` 的数值又全是 `private set`，所以 XML 是唯一能填满它的官方途径）：

```csharp
// 物品定义 XML：<Item id="my_armor" name="my_armor" mesh="..." type="body_armor">
//   <ItemComponent>
//     <Armor body_armor="42" head_armor="12" covers_head="true" />
//   </ItemComponent>
// </Item>
ItemObject bodyArmor = MBObjectManager.Instance.GetObject<ItemObject>("my_armor");
if (bodyArmor == null || !bodyArmor.HasArmorComponent)
{
    Debug.Print("armor component missing, check the <Armor> node name", 0);
    return;
}

Debug.Print("body armor = " + bodyArmor.ArmorComponent.BodyArmor, 0);
Debug.Print("head armor = " + bodyArmor.ArmorComponent.HeadArmor, 0);
Debug.Print("stealth   = " + bodyArmor.ArmorComponent.StealthFactor, 0);
```

自定义派生组件（继承 `ItemComponent` 是官方允许的扩展点，`ItemObject` 是 `sealed` 的，组件不是）：

```csharp
public class MyLegendaryComponent : ItemComponent
{
    public int LuckBonus { get; private set; }

    public override ItemComponent GetCopy()
    {
        MyLegendaryComponent copy = new MyLegendaryComponent();
        copy.Item = this.Item;
        copy.ItemModifierGroup = this.ItemModifierGroup;
        copy.LuckBonus = this.LuckBonus;
        return copy;
    }

    public void ApplyLuck(Hero target)
    {
        target.HitPoints += this.LuckBonus;
    }
}
```

## 风险与边界

- **单槽。** `ItemObject.ItemComponent` 只有一个。多个 `<ItemComponent>` 子标签时**后出现的覆盖先出现的**，只有 `<Weapon>` 例外（走 `?? new WeaponComponent(this)` 累加到同一组件的 `_weaponList`）。
- **`Item` 的 setter 公开。** 手动赋值会让 `item.ItemComponent.Item` 与 `item` 不再互相指向，且无任何断言。派生类的 `GetCopy()` 是唯一正当的写入理由。
- **没有公开的装配 API。** `ItemObject.ItemComponent` 是 `private set`，`AddWeapon` 只能装 `WeaponComponent`，`InitializeTradeGood` 只能装 `TradeItemComponent`。想装护甲/马匹组件只能改 XML。
- **XML 标签名是硬编码的字符串比较链。** 打错标签名得到的不是「忽略未知字段」，而是 `throw new Exception("Wrong ItemComponent type.")`，整个 `MBObjectManager` 加载中断。`<Food>` 走的是软失败（`Debug.FailedAssert` + null）。
- **派生类的 `Deserialize` 约定不一致。** [TradeItemComponent](../TradeItemComponent) 直接调 `this.Initialize()` 而非 `base.Deserialize(...)`，因此它的物品**读不到 `modifier_group`**。自定义派生类务必遵循 `base.Deserialize` 优先。
- **依赖 `Game.Current`。** `Deserialize` 里用 `Game.Current.ObjectManager` 解析词缀组，`OnSubModuleLoad` 阶段调用会 NRE。
- **`GetCopy()` 各家实现不等价。** 全树只有 [Crafting](../Crafting) 与 `CraftingCampaignBehavior` 会调它；[ArmorComponent](../ArmorComponent) 漏 `IsNoSlim`，[HorseComponent](../HorseComponent) 只拷 4 个 int。当通用 Clone 用会静默丢数据。
- **不进存档。** 组件随 XML 重建。改组件 XML 不会让旧存档崩，但旧存档里的物品会呈现新定义的数值。
- **抽象类，不能实例化。** 但也**没有 `sealed` 派生类**——除 [TradeItemComponent](../TradeItemComponent)（`public class`，可继承）外其余派生类都可被 mod 继承，无官方阻力。

## 跨版本提示

`bannerlord-1.3.15/` 与 `bannerlord-1.4.6/` 的 `TaleWorlds.Core/ItemComponent.cs` 公开表面**完全一致**（5 个公开成员、1 个 `protected override`），逐行比对无差异。

**1.4.5 侧结论**：打开 `bannerlord-1.4.5/Bannerlord.Source/bin/TaleWorlds.Core/TaleWorlds.Core/ItemComponent.cs`（30 行）与 `bannerlord-1.4.6/TaleWorlds.Core/ItemComponent.cs`（43 行）逐成员比对 public/protected 表面。**三版 public/protected 表面完全一致（各 5 个成员，0 新增 / 0 移除 / 0 签名变化 / 0 可访问性变化）**。1.4.5 是 30 行、1.4.6 是 43 行。

**为什么这份源码之前被判为「不存在」**：`bannerlord-1.4.5/` 的 C# 源码在 `Bannerlord.Source/bin/` 下**双层嵌套** `bin/<Assembly>/<Assembly>/<Type>.cs`，而 `bin/` 的一层里没有任何 `.cs`（实测 `find bannerlord-1.4.5/Bannerlord.Source/bin -maxdepth 1 -name "*.cs"` 命中 0），只扫一层就会误判成无源码。**1.4.5 是原始源码形态**（file-scoped namespace、无 `// Token:` 注释），1.4.6 与 1.3.15 是反编译产物，所以两边的行数不可直接比大小。
