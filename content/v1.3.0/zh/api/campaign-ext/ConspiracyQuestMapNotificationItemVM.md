## 心智模型

**地图通知是一条「数据 → 类型注册 → 反射构造 → 委托回调」的四段流水线，本类在第三段。**

**第一段：产生数据。** 上游是 [ConspiracyQuestMapNotification](../ConspiracyQuestMapNotification)（`StoryMode/ConspiracyQuestMapNotification.cs`，`:11`，`public class ConspiracyQuestMapNotification : InformationData`），它有两个生产点：

- `StoryMode/Quests/SecondPhase/ConspiracyQuestBase.cs:87`：`Campaign.Current.CampaignInformationManager.NewMapNoticeAdded(new ConspiracyQuestMapNotification(this, this.SideNotificationText));`
- `StoryMode/Quests/SecondPhase/ConspiracyQuests/DisruptSupplyLinesConspiracyQuest.cs:327`：同样一句

它身上有一个 `[SaveableProperty(1)] public QuestBase ConspiracyQuest { get; private set; }`，并在 `AutoGeneratedInstanceCollectObjects` 里把 quest 加进收集列表——**所以通知本身是存档的一部分**，`SaveableStoryModeTypeDefiner.cs:39` 注册了它（`AddClassDefinition(typeof(ConspiracyQuestMapNotification), 13, null)`）。

**第二段：注册类型对。** `StoryMode.GauntletUI/StoryModeGauntletUISubModule.cs:25-34`：

```csharp
private void OnScreenManagerPushScreen(ScreenBase pushedScreen)
{
    MapScreen mapScreen;
    if (!this._registered && (mapScreen = (pushedScreen as MapScreen)) != null)
    {
        mapScreen.MapNotificationView.RegisterMapNotificationType(
            typeof(ConspiracyQuestMapNotification),
            typeof(ConspiracyQuestMapNotificationItemVM));
        this._registered = true;

```

**注册时机是「第一个 `MapScreen` 被 push 上去」的那一帧**，而且有 `this._registered` 一次性闩锁。这条链是三层转发：[MapNotificationView](../MapNotificationView) 的 `public virtual void RegisterMapNotificationType(Type data, Type item)`（`SandBox.View/Map/MapNotificationView.cs:14`，基类体是**空的**）→ `GauntletMapNotificationView.cs:44-46` 覆写成 `this._dataSource.RegisterMapNotificationType(data, item)` → [MapNotificationVM](../../viewmodel/MapNotificationVM) 的实现只有一行：

```csharp
public void RegisterMapNotificationType(Type data, Type item)
{
    this._itemConstructors[data] = item;    // 一个 Dictionary<Type, Type>
}
```

**第三段（本类）：反射构造。** 通知进来时，`MapNotificationVM` 从 `_itemConstructors` 查出 VM 类型并 `Activator.CreateInstance(itemType, data)`，于是本类的构造函数被调用——**这个构造函数的签名 `(ConspiracyQuestMapNotification data)` 就是注册契约本身**。传错类型编译期查不出来（注册是 `Type` 对 `Type`），运行时会 `MissingMethodException`。

**第四段：点通知做什么。** 基类 [MapNotificationItemBaseVM](../../viewmodel/MapNotificationItemBaseVM) 的 `ExecuteAction()`（`:61-70`）就是转发：

```csharp
public void ExecuteAction()
{
    Action onInspect = this._onInspect;
    if (onInspect == null) { return; }
    onInspect();
}
```

**`protected Action _onInspect;`（`:290`）是本类唯一真正在写的东西。** 本类构造时把它填成一个「取 `NavigationHandler` → 判空 → `MapNavigationExtensions.OpenQuests(handler, data.ConspiracyQuest)`」的委托。

## 真实示例

**用法一：手动造一个 VM（调试用，注意 NavigationHandler 得自己注入）。**

```csharp
using StoryMode;
using StoryMode.ViewModelCollection.Map;
using TaleWorlds.CampaignSystem;
using TaleWorlds.CampaignSystem.Screens;

// 上游数据
ConspiracyQuestMapNotification data = new ConspiracyQuestMapNotification(quest, descriptionText);
var vm = new ConspiracyQuestMapNotificationItemVM(data);

// NotificationIdentifier 已被构造函数设好，直接读：
string id = vm.NotificationIdentifier;   // "conspiracyquest"
QuestBase q = vm.Quest;

// 不注入 NavigationHandler 的话，点通知什么也不会发生 —— _onInspect 里判空后直接 return。
vm.SetNavigationHandler(null);
```

**用法二：给 mod 自己的通知类型做一份同形状的 VM。** 这才是本类值得抄的地方。

```csharp
using TaleWorlds.CampaignSystem;
using TaleWorlds.CampaignSystem.ViewModelCollection.Map.MapNotificationTypes;

// 第 1 步：数据类（StoryMode 工程）
public class MyModQuestNotification : InformationData
{
    [TaleWorlds.SaveSystem.SaveableProperty(1)]
    public QuestBase Quest { get; private set; }

    public MyModQuestNotification(QuestBase quest, TextObject descriptionText) : base(descriptionText)
    {
        this.Quest = quest;
    }
}

// 第 2 步：VM（TaleWorlds.CampaignSystem.ViewModelCollection 之外的工程）
public class MyModQuestNotificationItemVM : MapNotificationItemBaseVM
{
    public QuestBase Quest { get; }

    public MyModQuestNotificationItemVM(MyModQuestNotification data) : base(data)
    {
        base.NotificationIdentifier = "mymodquest";       // 必须与 Gauntlet prefab 里的键一致
        this.Quest = data.Quest;

        QuestBase captured = data.Quest;                  // 显式捕获，别依赖 <>()4__this
        this._onInspect = delegate()
        {
            INavigationHandler handler = this.NavigationHandler;
            if (handler == null)
            {
                return;
            }
            handler.OpenQuests(captured);                  // TaleWorlds.CampaignSystem 里的扩展方法
        };
    }
}

// 第 3 步：注册（照抄 StoryModeGauntletUISubModule.OnScreenManagerPushScreen 的形状）
mapScreen.MapNotificationView.RegisterMapNotificationType(
    typeof(MyModQuestNotification),
    typeof(MyModQuestNotificationItemVM));
```

`MapNavigationExtensions.OpenQuests` 有四个重载（`TaleWorlds.CampaignSystem.ViewModelCollection/TaleWorlds/CampaignSystem/MapNavigationExtensions.cs:28/34/43/52`），分别吃无参、`QuestBase`、`IssueBase`、`JournalLogEntry`——**它是对 `INavigationHandler` 的扩展方法**，所以上面 `handler.OpenQuests(captured)` 与 `MapNavigationExtensions.OpenQuests(handler, captured)` 等价。

## 风险与边界

- **`NotificationIdentifier = "conspiracyquest"` 是与 Gauntlet prefab 的硬绑定字符串。** 基类的 setter 会 `OnPropertyChangedWithValue(value, "NotificationIdentifier")` 广播出去，prefab 侧按这个字符串选模板。**改这个字符串 = 通知条目在 UI 上消失，而且不报错。** 全树有一堆同形态的兄弟（`"ransom"` 出现两次、`"vote"` 出现两次、`"death"` 出现两次），说明**这个命名空间是扁平的、不带模块前缀**——你自定义一个 id 时很容易撞名。
- **构造函数不做任何校验，`data` 为 null 直接 NRE。** `this.Quest = data.ConspiracyQuest;` 是无判空的属性访问。注册机制用 `Activator.CreateInstance` 反射构造，**如果 `MapNotificationVM` 那边传错了参数类型，报错会是一个 `MissingMethodException`，而不是清晰的类型错误**。
- **`_onInspect` 里 `NavigationHandler` 为 null 时静默返回，什么都不发生。** 点通知没反应、日志里也没有一行。**根因通常是 VM 被造出来之后 `SetNavigationHandler(...)` 从没被调过**（`MapNotificationVM` 负责注入），而不是 `_onInspect` 没赋值。
- **必须同时做两件事，缺一不可：注册类型对 + 造 Gauntlet prefab。** 只注册不造 prefab，`NotificationIdentifier` 找不到对应模板，通知同样不显示。这两件事分属不同工程、不同作者习惯，`StoryMode` 那边靠 `StoryModeGauntletUI` 项目里的 prefab 提供。
- **注册有一次性闩锁且发生在特定时刻。** `StoryModeGauntletUISubModule.OnScreenManagerPushScreen` 靠 `this._registered` 保证只注册一次，触发条件是**第一个 `MapScreen` 被 push**。所以：**如果你在第一个 MapScreen 出现之前就调 `RegisterMapNotificationType`，引擎后来那次注册会把你的覆盖掉**（`_itemConstructors[data] = item` 是字典赋值，后写赢）。反过来，如果你注册得太早而 MapScreen 还没建，你的注册就**根本不在那张字典里**——因为 `MapNotificationView` 的注册是往 `MapNotificationVM._itemConstructors` 写，VM 本身属于那一个 MapScreen。
- **`Quest` 是 `QuestBase`，不是 `ConspiracyQuestBase`。** 上游 [ConspiracyQuestMapNotification](../ConspiracyQuestMapNotification) 的字段声明成 `QuestBase`，本类原样透传。**要调阴谋任务特有的方法必须 `as ConspiracyQuestBase`，而 `ConspiracyQuestBase` 在 `StoryMode.Quests.SecondPhase` 命名空间下**——mod 引用它就得引 `StoryMode` 工程。**
- **`Quest` 是不可变快照。** getter-only，构造时赋值一次。任务在中途被替换（`QuestBase` 的 `IsActive` 变 false、或者被换成另一个实例）时，**这个 VM 上读到的仍是旧引用**，不会自动跟着变。需要最新状态就重新从 `Campaign.Current` 查，不要信这个属性。
- **`StoryMode.ViewModelCollection` 是模块工程。** 裸战役（无 `StoryMode` 模块）里这整个类型不存在，`StoryModeGauntletUISubModule` 那条注册链也不会跑。
- **这条链有四层 indirection，每层都可能断。** `MapScreen.MapNotificationView`（虚拟方法，基类空实现）→ `GauntletMapNotificationView`（覆写）→ `MapNotificationVM._itemConstructors`（一个 `Dictionary<Type, Type>`）→ 反射构造。**排查「通知不出现」时要从后往前逐个确认，别只盯着 VM 类本身。**

### 最容易踩的坑

**把它当成可复用的通知对象，在多次调用之间缓存。** 构造函数里把 `this._onInspect` 绑成了一个捕获 `data` 的委托（`:20-28`），而 `data` 是构造参数。后果：一旦通知被丢弃、而你还持有这个 VM，**点击它就会拿着过期的 data 去导航**，可能跳到一个已经结束的阴谋任务上。它是「一次通知一个实例」。

第二个坑是 `Quest` 可能不是你以为的那个任务。它是在构造函数里从 `data.ConspiracyQuest` 直接取的（`:19`），**没有任何校验**。后果：你用别的任务类型构造通知，编译能过（如果类型兼容），但点开之后导航到的是一个没有界面处理的任务——**点击无反应**，而不是报错。

第三个坑是不处理 `NavigationHandler` 为 null 的情况。`_onInspect` 里显式判了 null 就 return（`:22-26`）。后果：通知在还没有导航处理器的时序里出现时，**点击完全静默无效**——这是设计上的静默，不是你的代码漏了处理。

## 跨版本提示

`ConspiracyQuestMapNotificationItemVM.cs` 在 `bannerlord-1.3.0` / `1.4.6` / `1.4.7` / `1.5.3` 四棵树里**公开面一字未改**：2 个 public 成员（`Quest` 属性 + 构造函数），逐行比对差集为空。

唯一可见的差异是**构造函数的写法**：1.3.0 是 `public ConspiracyQuestMapNotificationItemVM(ConspiracyQuestMapNotification data) : base(data)`，1.4.6 / 1.4.7 / 1.5.3 是 `public ConspiracyQuestMapNotificationItemVM(ConspiracyQuestMapNotification data)`——**`: base(data)` 被去掉了**。这是编译产物层面的差别（编译器在后续版本能推断出基类调用），**参数类型、参数个数、语义全都不变，对调用方零影响**。文件字节数 825B → 802B 就是这 23 字节。

注册点 `StoryMode.GauntletUI/StoryModeGauntletUISubModule.cs:31` 的 `RegisterMapNotificationType(typeof(ConspiracyQuestMapNotification), typeof(ConspiracyQuestMapNotificationItemVM))` 与 `this._registered` 闩锁，在四棵树里未变。上游数据类 `StoryMode/ConspiracyQuestMapNotification.cs` 的 `[SaveableProperty(1)] ConspiracyQuest` 与两个 `NewMapNoticeAdded` 调用点（`ConspiracyQuestBase.cs:87` / `DisruptSupplyLinesConspiracyQuest.cs:327`）也未变。

1.3.15 与 1.4.5 两棵树不含 `StoryMode.ViewModelCollection` / `StoryMode.GauntletUI` 工程，无法作为中间版本对照。

**结论：`NotificationIdentifier = "conspiracyquest"` 这个字符串契约跨 1.3 → 1.5 稳定，你抄一份同形状的 VM 到哪个版本上都能编译、能显示。** 唯一需要重新确认的是**你自己选的 id 有没有和后续版本新加的官方通知撞名**——官方那批 id（`"death"` / `"vote"` / `"ransom"` / `"marriage"` 等）在 1.3.0 里就已经有重复占位了，说明这个命名空间从来没有版本间的清理动作，撞名风险只会随版本上升。
