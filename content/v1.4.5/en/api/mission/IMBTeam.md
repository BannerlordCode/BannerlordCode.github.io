## Mental Model

Think of it as a **two-cell switch on the battle table**, not a property of either soldier. The teams in a mission are indices — 0, 1, and whatever custom battles add — and this interface writes one bit: "these two indices are hostile". Nothing about the two teams changes; only the mission's answer to "are these enemies?" does.

That framing explains the whole API shape. There is no "ally" member, because ally is the *absence* of enemy: `IsEnemy(a, b) == false` is how you ask. There is no list of relations, because the relation is queried pairwise. And there is no enumeration, because the bridge holds a matrix it will answer about but not enumerate.

The boundary that matters is **the relation is pairwise, and the network needs the higher-level entry point**. `SetIsEnemy(mission, teamIndex, otherTeamIndex, isEnemy)` writes one cell (`:13`). Whether the reverse cell follows is not something this interface promises — it forwards whatever the engine does, and the managed wrapper adds nothing (`:44-47`). Separately, replication lives one level up, in `Team` (`Team.cs:618-627`), not here. So two things follow: a mod that flips one direction and queries the other is relying on unspecified symmetry, and a mod that writes through `MBTeam` in multiplayer changes one machine's view only.

**A typical use.** A mod that turns a scripted encounter into a friendly fire scenario flips the relation through `Team`, which both writes the bridge cell and broadcasts it when this machine is the server or a recorder:

```csharp
using TaleWorlds.MountAndBlade;

Team attacker = Mission.Current.AttackerTeam;
Team defender = Mission.Current.DefenderTeam;

attacker.SetIsEnemyOf(defender, true);
defender.SetIsEnemyOf(attacker, true);

Debug.Print("attacker sees defender as enemy = " + attacker.IsEnemyOf(defender), 0);
Debug.Print("defender sees attacker as enemy = " + defender.IsEnemyOf(attacker), 0);
```

**What to watch out for.** Two mistakes sit on top of each other here, and the second hides the first. Writing one direction only gives an asymmetric battlefield where targeting on one side disagrees with the other. The consequence in a multiplayer battle is a relation that differs per client, which desynchronises the encounter and the mission record.

## Examples

Make two teams hostile to each other in both directions, then verify:

```csharp
using TaleWorlds.MountAndBlade;

Team attacker = Mission.Current.AttackerTeam;
Team defender = Mission.Current.DefenderTeam;

attacker.SetIsEnemyOf(defender, true);
defender.SetIsEnemyOf(attacker, true);

Debug.Print("a->d = " + attacker.IsEnemyOf(defender), 0);
Debug.Print("d->a = " + defender.IsEnemyOf(attacker), 0);
```

Make two teams allies by clearing the relation in both directions — there is no `SetIsAlly`, so this is the only way:

```csharp
using TaleWorlds.MountAndBlade;

Team attacker = Mission.Current.AttackerTeam;
Team defender = Mission.Current.DefenderTeam;

attacker.SetIsEnemyOf(defender, false);
defender.SetIsEnemyOf(attacker, false);
Debug.Print("now allies = " + !attacker.IsEnemyOf(defender), 0);
```

Branch on the relation instead of assuming sides line up, which is the robust form when a custom battle may have reassigned it:

```csharp
using TaleWorlds.MountAndBlade;

Team team = Mission.Current.PlayerTeam;
Team other = Mission.Current.PlayerTeam == Mission.Current.AttackerTeam
    ? Mission.Current.DefenderTeam
    : Mission.Current.AttackerTeam;

if (team.IsEnemyOf(other))
{
    Debug.Print("player team is hostile to " + other, 0);
}
```

## Risks and crash boundaries

- **A mod assembly cannot call this interface.** `internal interface IMBTeam` (`IMBTeam.cs:7`), `internal static IMBTeam IMBTeam;` (`MBAPI.cs:44`), `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`).
- **The relation is per-mission, not per-team.** Both members take `missionPointer` (`IMBTeam.cs:10`, `:13`), so an index read in one mission means nothing in another.
- **One call writes one direction.** The wrapper forwards exactly what it is given (`MBTeam.cs:46`) and adds no mirroring. One-sided writes produce an asymmetric battlefield with no diagnostic.
- **The bridge does not replicate; `Team` does.** `Team.SetIsEnemyOf` broadcasts `TeamSetIsEnemyOf` only when `GameNetwork.IsServerOrRecorder` (`Team.cs:621`-`:625`). **Writing through `MBTeam` in multiplayer changes one machine's view only**, and a non-server client calling `Team.SetIsEnemyOf` also does not broadcast.
- **`IsEnemy` and `SetIsEnemy` carry different `EngineMethod` flags.** `true` at `:9` versus `false` at `:12`. Do not assume the two are interchangeable marshalling-wise.
- **The wrapper does not validate the other team.** `MBTeam.cs:46` passes `otherTeam.Index` with no check, so `MBTeam.InvalidTeam` (index `-1`, `MBTeam.cs:9`) reaches native as a relation target.
- **Validity is `Index >= 0`.** `MBTeam.IsValid` (`MBTeam.cs:11`) — so a default-constructed `MBTeam` has index `0`, which **is valid** and means "team 0", not "no team". Check `IsValid` on a field you did not initialise.
- **Changing the relation mid-battle does not rewrite existing orders.** Nothing in this interface touches formations, agents or the team AI; the visible effect is on subsequent hostility checks and targeting.
- **Not a save participant.** No `[Serializable]`, no sync surface; the relation is rebuilt when a mission is loaded.
