# IMBDelegate

**Namespace:** TaleWorlds.MountAndBlade
**Module:** TaleWorlds.MountAndBlade
**Type:** `internal interface IMBDelegate`
**Base:** none
**File:** `bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/IMBDelegate.cs`

## Overview

`IMBDelegate` is the **empty native bridge of the Mount & Blade module** — a 6-line file that declares an interface, marks it `[ScriptingInterfaceBase]`, and stops. There is not a single `[EngineMethod]` in it, and there are no members of any kind (`IMBDelegate.cs:4-6`). Compare its siblings: `IMBGame` is 13 lines with two engine methods, `IMBBannerlordConfig` is 10 lines with one. `IMBDelegate` has zero.

What it still does is occupy a slot in the engine's interface table. `TaleWorlds.MountAndBlade.AutoGenerated` registers it under its full type name with a generated adapter instance (`TaleWorlds.MountAndBlade.AutoGenerated/ManagedCallbacks/ScriptingInterfaceObjects.cs:736-737`), and `MBAPI` reads that registration back into an `internal static IMBDelegate IMBDelegate` field during `SetObjects` (`MBAPI.cs:18`, assigned at `MBAPI.cs:86`). The generated adapter is correspondingly empty: `ScriptingInterfaceOfIMBDelegate` implements the interface and holds a single `Encoding` field it never uses (`TaleWorlds.MountAndBlade.AutoGenerated/ManagedCallbacks/ScriptingInterfaceOfIMBDelegate.cs:6-9`).

## Mental Model

### What it is / which layer

- It is a **placeholder in the bridge's registry**, not a working seam. Read it as a nameplate on an empty socket: the slot exists so the loader's table has an entry, not so anyone can call through it.
- The name says "delegate" because the native side of the M&B engine uses a delegate/registration concept for this slot. **The managed interface exposes nothing of that**, so do not expect a callback to arrive by calling something here.
- Direction matters: `IMBActionSet` goes *managed → native* (you call, native answers). `IMBDelegate` has no methods in either direction. There is nothing to call and nothing to implement.

### Why it is still in the table

The `[ScriptingInterfaceBase]` attribute at `IMBDelegate.cs:3` is what the interface loader looks for before it will bind a type. Removing the interface would remove a row the generated `ScriptingInterfaceObjects` table expects (`ScriptingInterfaceObjects.cs:736`), and the table is machine-generated. So the interface is kept as a stable key, not as an API. Treat any absence of members as deliberate, never as "members missing, go look again" — there is nothing to look for.

### What this means when you are searching

If you are grepping the managed source for how the native delegate mechanism is driven, this interface will produce **zero** hits and that is the correct answer, not a failed search. The mechanism you want is elsewhere: the `[MBCallback]` attribute marks managed methods the engine calls *into*, which is the actual direction a native-originated callback uses. `BannerlordTableauManager.RequestCharacterTableauSetup` is a real example — an `[MBCallback(null, false)]` method the native side invokes (`BannerlordTableauManager.cs:43-47`).

## How to use

**How to obtain it.** You cannot, and there is nothing to obtain. The interface is `internal` (`IMBDelegate.cs:4`), the `MBAPI` field holding it is `internal static` (`MBAPI.cs:18`), and `TaleWorlds.MountAndBlade` grants `InternalsVisibleTo` only to `TaleWorlds.MountAndBlade.AutoGenerated`, `TaleWorlds.MountAndBlade.Multiplayer` and `TaleWorlds.Generator.Bannerlord` (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). A mod assembly that names `IMBDelegate` in a `using` or a field type fails to compile. And because the interface declares no members, `MBAPI.IMBDelegate` is a value you can only ever be `null`-check — the field is populated by `GetObject<IMBDelegate>()` (`MBAPI.cs:86`) from a registration that carries no callable behaviour.

**A typical use.** There is no typical use, and writing one would be a fabrication. The closest legitimate mod-side activity is checking whether the engine's bridge table is alive at all before touching *other* bridges, which is what `MBAPI` fields are actually for:

```csharp
using TaleWorlds.MountAndBlade;

// IMBDelegate itself is internal and empty — the useful fact is that the
// bridge table was populated at all. MBAPI's fields are internal too, so a mod
// asserts this indirectly: any public call that needs the bridge would throw
// NullReferenceException if SetObjects had never run.
bool bridgeLoaded = Mission.Current != null;
Debug.Print("mission present => engine bridge populated: " + bridgeLoaded, 0);
```

**What to watch out for.** Do not treat the empty interface as a bug to report or a gap to fill. A "TODO: implement members" note here would be wrong — the file is complete at 6 lines. The real risk is the opposite one: a modder greps for `IMBDelegate`, finds nothing callable, and concludes the native delegate system is missing from the managed tree. It is not missing; it lives behind `[MBCallback]`, which is a different mechanism and is public to reach.

## Examples

There is no code example for calling an interface with no members, so the runnable example here is the **negative** one: prove the compile-time refusal, which is the single most useful thing a reader can take from this page.

```csharp
// This does not compile — deliberately shown, not a working snippet.
//   error CS0122: 'IMBDelegate' is inaccessible due to its protection level
using TaleWorlds.MountAndBlade;

public sealed class Probe
{
    // error CS0122 on both the type and the MBAPI field
    private readonly IMBDelegate _bridge = MBAPI.IMBDelegate;
}
```

And the sanctioned substitute — marking a managed method so the engine calls *into* it, which is what a modder actually wants when they searched for "delegate":

```csharp
using TaleWorlds.MountAndBlade;

public static class MyNativeHooks
{
    // Same mechanism BannerlordTableauManager uses at BannerlordTableauManager.cs:43-47.
    // The [MBCallback] attribute is what marks a method as engine-invoked; the
    // signature must match what the native side declares, or the callback table
    // entry never resolves.
    [MBCallback(null, false)]
    internal static void OnSomethingNativeHappened(int a)
    {
        Debug.Print("native callback fired with " + a, 0);
    }
}
```

## Risks and crash boundaries

- **A mod cannot reference it, and the failure is at compile time.** `internal interface` + `internal static MBAPI` field + `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). This is the one friendly failure mode in the whole bridge layer.
- **`MBAPI.IMBDelegate` carries no behaviour.** It is assigned once in `SetObjects` (`MBAPI.cs:70`) and then never read by any managed code. Do not build a null-check "guard" around it and assume the guard means the bridge works.
- **Nothing here can throw.** An interface with no members cannot raise an `ArgumentException`, an index error, or a native fault. Any crash attributed to `IMBDelegate` is actually attributed to something else — most likely an `[MBCallback]` signature mismatch.
- **Not a save participant.** No `[Serializable]`, no fields, no state. It is stateless by construction.
- **Do not edit it to add members.** The file is consumed by the generated `ScriptingInterfaceObjects` table (`ScriptingInterfaceObjects.cs:736-737`) and by nothing else; adding an `[EngineMethod]` without a matching native symbol produces a binding failure at engine load, not a managed exception.

## Cross-Version Notes

In v1.4.5 the file is 6 lines and declares zero engine methods. The same file name under the same `Bannerlord.Source/bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/` layout in the `bannerlord-1.3.0` and `bannerlord-1.3.15` trees is likewise an empty `[ScriptingInterfaceBase]` interface — the type exists in every version precisely so the loader's generated table has a stable key. Nothing about the shape should be assumed stable across versions: an interface with no members is the shape most likely to gain one, and a `[EngineMethod]` added in a later version would appear here with a native symbol string that older versions do not have. **VERIFIED MEASURED for v1.4.5 only** — the other two trees were not read line-by-line for this page, so treat the cross-version claim as "same file, same marker", not as a member-level diff.
