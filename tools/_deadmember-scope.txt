# 路由 / 桶判定判据（2026-10-03 实测更正，三条都要守）
# ============================================================================
#
# 【判据 1】桶由**源码声明的 namespace** 定，不由「本页所在桶」定
#   同桶兄弟规则成立，是因为兄弟类型确实同桶。
#   一旦**同名跨桶**（1.4.5 有 2,199 个名字跨桶重复，如 Army / TroopRoster /
#   Settlement / TroopSacrificeModel / MapEvent 在 campaign 与 campaign-ext 各一份），
#   **「本页所在桶」就不再是判据** —— 它只能推出同桶，若推错了就是
#   「一个不再报错的干净链接指向了错误的类型」，比断链更坏。
#   · 判定必须附 **File.cs:行号**（哪个文件的哪个声明），没有源码行号的桶判定不接受。
#   · 不以 lead 的说法为准，**也不以作者原文为准**（作者也会写错）。
#   · 两者分歧 → 原样报 lead 裁，不要自己挑一个。
#
# 【判据 2】namespace 只能定到**桶**，定不到「同名类型里是哪一个」
#   若源码里 `Army` 在 campaign 与 campaign-ext 各有一个声明，而调用点要靠
#   `using` 与接收者类型才能区分，**namespace 判据本身就不够**，
#   必须看调用点的接收者类型。
#   → 仍不能定 → **报 UNRESOLVED，不要挑一个。**
#
# 【判据 3】同页内已存在的正确写法是最佳参照物
#   优先于任何规则、优先于 lead 的说法。
#   实例：zh/CampaignSiegeStateHandler.md:130,131,133 本来就正确写着
#   `../../campaign/Settlement` · `../../mission-ext/MissionLogic` · `../../core-extra/MissionResult`
#   —— 页内自证比任何上游转述都强。
#
# 【层级推导，不是结论】（叶子页 base = /vX/<lang>/api/<bucket>/<Page>/）
#   ../Foo           → 同桶兄弟
#   ../../<桶>/Foo   → 跨桶（上一层是 api/）
#   ⚠ 注意 `../campaign/Foo` 这类「前缀深度与桶同时错」的写法：
#     `..` 只回到 <bucket>/，回不到 api/，会拼出 <bucket>/campaign/Foo。

# rev 4 · 委托 / 方法组引用的最小样本与判层（lead-2 实测，给规范做实例）
# ============================================================================
# 样本：成员 GivePlayerAHaircut
#   声明  BarberCampaignBehavior.cs:175   private void GivePlayerAHaircut()
#   引用  :109  campaignGameStarter.AddPlayerLine(..., new OnConsequenceDelegate(GivePlayerAHaircut), ...)
#         :113  同一行形态，再次 new OnConsequenceDelegate(GivePlayerAHaircut)
#   另一个同型：InDisguiseSpeakingToBarber  声明 :121 / 引用 :107 new OnConditionDelegate(...)
#
# 【落在哪一层 —— 与另一种根因不同，别并成一条】
#   ⛔ 不是「提取器丢了前缀」。这里**根本不存在限定名**：没有 `SomeType.GivePlayerAHaircut`，
#      名字是以**裸标识符**出现在构造实参里。
#   ✅ 是「『调用点』这个词本身定义过窄」：它是一个**引用**（把方法变成委托对象），
#      不是一次调用。名字在文本里存在，只是任何「调用形」判据
#      （点前缀 `.Name` 或后跟 `(`）都看不见它 —— `Delegate(Name)` 里 Name 后面是 `)`。
#   → 修法方向也不同：不是补前缀提取，而是**把「引用」纳入计数**。
#   → Bannerlord 的对话 API（AddDialogLine / AddPlayerLine）是主流通法，这是系统性形态。
#
# ⚠ 与 field/property 那次同族但不同层：
#    field/property 那次是**类内裸读**（`_cheeringAgents[i]`），
#    这次是**被委托引用**。两者都让「0 调用点」不可信，但修法不同。

# ⛔ 行尾：唯一权威是共享尺，不许各自即兴造探针（boss-1 裁定 · lead-2 落成文件）
# ============================================================================
# 工具：node tools/_line-endings.mjs   （自检 8/8，exit 0）
#
# 【为什么它是唯一的】本会话同一个 CRLF 争议吵过两轮：第二轮的结论一度与第一轮相反。
# 原因不是判断分歧，而是**每个 worker 各自即兴造探针**，而本会话已经有**三个探针**
# 栽在这件事上（见下方黑名单）。结论会随时间失效，工具不会。
#
# 【怎么用】
#   node tools/_line-endings.mjs --selftest
#   node tools/_line-endings.mjs --scope tools/_deadmember-scope.txt campaign-ext
#   node tools/_line-endings.mjs <文件...>
#
# 【判读规则（写在尺的文件头，不靠记忆）】
#   CR 数 == 0                        → 纯 LF
#   CRLF 数 == LF 行数 且 游离CR == 0 → 全 CRLF
#   CRLF 数 <  LF 行数                → mixed，**必须逐行看是哪几行**，不许笼统说 mixed
#   游离 CR > 0                       → 存在不跟 LF 相邻的 CR（老 Mac 行尾 / 杂散 CR）
#   CRLF 数 > LF 行数                 → 尺或数据有问题 → exit 2
#
# 【三条规则】
#   1. 这把尺的输出就是**唯一权威**，逐字引用。
#   2. 任何人对某页行尾有异议，**必须给出命令与输出**，且那条命令要是**别的口径**
#      （regex / grep / 换行统计），并解释它与字节级读数为什么不同 ——
#      **不许只说「我测的是 CRLF」。**
#   3. ⛔ 黑名单（三个探针在本会话都栽在这里，输出「全命中」或 0 这种过于整齐的错值）：
#        grep -o ''     BRE 里匹配的是**字母 r**，数的是 r 的个数
#        rg -c $'$'     把每个 CRLF 行都算命中；部分 CRLF 时输出「全命中」
#        grep -c $'$'   在真·CRLF 文件上也返回 0
#      「全命中」和「全不命中」一样需要阳性对照。
#
# 【本线 80 页的读数（lead-2 实测，尺为准）】
#   mission-ext  40 页 = 全 LF 40 · 全 CRLF 0 · mixed 0
#   campaign-ext 40 页 = 全 LF 38 · 全 CRLF 2 · mixed 0
#     全 CRLF 两页：content/v1.4.5/zh/api/campaign-ext/AgentBehaviorManager.md  (191/191)
#                   content/v1.4.5/zh/api/campaign-ext/NavigationHelper.md       (206/206)
#   ⚠ 但**动手前仍要自己跑一次尺**：名单只是线索，不是判据。
