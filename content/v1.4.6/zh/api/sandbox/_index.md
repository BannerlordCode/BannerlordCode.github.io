# sandbox：官方沙盒玩法（`SandBox*`）

> **本桶当前没有任何已撰写页面。** 先说结论：**这是官方玩法的实现代码，不是给 mod 调用的 API 面。** 本页要回答的是「我要改的东西跟它什么关系」，而不是「它有哪些方法」。

## 这个桶对应源码里的什么

权威映射只有一条规则：`SandBox` → `sandbox`。前缀匹配，所以 `SandBox.*` 下的所有子命名空间都在本桶。`bannerlord-1.4.6/` 下相关的源码目录：

| 源码目录 | 里面是什么 |
| --- | --- |
| `SandBox/` | 沙盒战役玩法的实现：任务、遭遇、城镇经营、巷战、竞技场、地下城、教程 |
| `SandBox.ViewModelCollection/` | 沙盒专属的官方界面数据类（锻造、工坊、部队整备等） |
| `SandBox.View/` | 沙盒专属的官方界面（View，不是 ViewModel） |
| `SandBox.GauntletUI/` | 沙盒的 Gauntlet 部件与预制体 |
| `SandBox.GauntletUI.AutoGenerated.0` / `.1` | 由 prefab 生成的类，噪声清单排除 |

**统计口径要说明白**：`SandBox*` 前缀下按声明抓到的类型名有 1273 个，但这个数字里绝大部分是 `*_Dependency_1_ItemTemplate` 这类从 prefab 生成的类（命名里带 `__TaleWorlds_CampaignSystem_ViewModelCollection_` 之类）。真正手写的沙盒玩法类型是几十个量级，不是 1273 个。**本桶的价值不在类型数量。**

顺带一个命名空间的坑：`SandBox/` 目录下有一个 `Sandbox/` 子目录（拼写不同，少了一个 `B`），里面的 `AutoGeneratedSaveManager` 声明在 `Sandbox` 这个命名空间里。权威映射把它列进 `sourceTypoNamespaces`，**明确排除、不建页**——所以别把 `SandBox` 和 `Sandbox` 混着写。

## mod 什么时候会碰到它

诚实的结论：**你的 mod 从不「调用」沙盒实现，它只是和沙盒住在同一张战役图上。**

三种真实关系，按重要性排序：

1. **插入点关系（最主要）。** 你的行为会和沙盒自带的几百个行为一起被加进战役。想知道「沙盒都挂了哪些行为、挂的顺序是什么」，答案在 `SandBoxSubModule` 里。这就是为什么 mod 作者要读本桶——**不是为了调它，是为了知道自己在跟谁抢同一个位置**。要挂行为本身，写的是 [campaign](../campaign) 桶的 `CampaignBehaviorBase` + `CampaignGameStarter`。
2. **场景关系（少数 mod）。** 地下城遭遇、竞技场决斗、巷战小游戏这些是沙盒特有的玩法对象。如果你做一个「所有地下城都给奖励」的 mod，你需要认识沙盒的遭遇类型和它们的完成条件。这条路最终会走到本桶。
3. **界面参考（抄写法）。** `SandBox.View` 里的官方界面骨架，以及 `SandBox.ViewModelCollection` 里的少数几个沙盒专属界面数据类，是现成范例。**注意一个容易踩的坑**：锻造（`CraftingVM`）、工坊、部队整备这些看着像「沙盒界面」的类，实际命名空间是 `TaleWorlds.CampaignSystem.ViewModelCollection`，落在 [viewmodel](../viewmodel) 桶，**不在本桶**。别按界面名字猜桶，要按命名空间查。

**心智模型**：把 `SandBox` 想成「官方战役的第一批 mod」。它是玩家装游戏时默认就有的一个大 mod，做的正是你打算做的事（加任务、加行为、改数值、加界面）。所以读它的正确姿势是**对照**——看它怎么用 `CampaignBehaviorBase`、怎么注册游戏模型、怎么在 `SubModule` 里挂东西，然后照着做你的一份。**先读 [core](../core) 的 `Module` / [campaign](../campaign) 的 `CampaignBehaviorBase`**，再读这里。

**边界**：本桶里的类型是官方内容实现，没有向后兼容承诺。**不要继承沙盒的任务 / 行为类来做扩展**——它们会在下个版本被改掉。正确做法是继承稳定的基类（`CampaignBehaviorBase`、`MissionBehavior`），把沙盒类型当作**只读的数据来源和参照**。

## 待写清单（节选，19 条已核实类型）

下面每个名字都在 `bannerlord-1.4.6/` 核实过确实存在。**这是节选**——本桶候选上千，且大部分是生成物。挑的是 mod 真会打开看的那些。

模块入口与加载：

- `SandBoxSubModule` — 沙盒玩法的 `MBSubModuleBase` 子类，**本桶最值得写一页的类型**。要理解「沙盒挂了哪些 `CampaignBehaviorBase` 派生类、按什么顺序」，从这里读起。写法与 [core](../core) 的 `Module` 同源
- `SandBoxMissions` — 沙盒相关的 mission 创建入口
- `SandBoxSaveManager` — 沙盒的存档类型注册

任务与遭遇：

- `ArenaDuelMissionController` / `ArenaPracticeFightMissionController` — 竞技场决斗 / 练武的实现
- `ArenaDuelQuestTask` / `ArenaDuelMissionBehavior` — 竞技场任务的步骤与行为
- `AlleyCampaignBehavior` — 巷战（暗巷）玩法对应的战役行为，是「沙盒专属行为」的一个好例子
- `ArenaMasterCampaignBehavior` — 竞技场主持人行为

城市与聚落：

- `MapEntityVisual` / `EntityVisualManagerBase` — 地图实体的视觉表现（聚落图标之类），**属于表现层**，改地图图标时才需要

界面骨架（`SandBox.View`，实测 10 个顶层类型，可以全列）：

- `SandBoxViewSubModule` — 沙盒界面子模块的入口
- `SandBoxViewCreator` / `SandboxView` / `SandBoxViewVisualManager` — 官方界面的创建与视觉管理，抄自定义界面时参照这三个
- `PreloadScreen` / `SaveLoadScreen` — 预载与存读档界面；这两个是沙盒最常被 mod 改的官方界面
- `CampaignMusicHandler` — 战役音乐处理
- `MainHeroSaveVisualSupplier` — 主角外观在存档里的视觉来源
- `IChangeableScreen` — 可切换外观的屏幕接口
- `SandBoxViewCheats` — 调试用的作弊界面

界面数据类（`SandBox.ViewModelCollection`，实测只有 5 个顶层类型，可以全列）：

- `TournamentRewardVM` — 锦标赛奖励界面
- `SPOrderOfBattleVM` / `SPScoreboardVM` — 单人模式的战前布阵与计分板
- `SandBoxUIHelper` — 沙盒界面的公共辅助
- `PerkObjectComparer` — 专长（perk）对象的比较器，排序列表时用

**没有页面**。写的时候强烈建议以「一个问题」为主线组织（例如「我想在沙盒里插一个自己的战役行为，要看哪几个类」），而不是逐类平铺上千个名字——尤其不要为 `*_Dependency_*_ItemTemplate` 这类 prefab 生成物建页。

## 为什么现在还没有页面

1.4.6 的手写覆盖按 **mod 实际使用频率** 排序。本桶排在最后一段，理由是**它没有可写的调用面**：

1. **没有继承价值。** 沙盒的类是官方内容实现，继承它们等于和官方更新赛跑。mod 该继承的是 `CampaignBehaviorBase` / `MissionBehavior` / `MBSubModuleBase` 这些稳定基类——而它们全都已经在 [campaign](../campaign) 和 [mission](../mission) 桶里写好了。
2. **规模全是噪声。** 1273 个候选里真正手写的只有几十个，剩下的都是 prefab 生成物。给生成物写页毫无意义。
3. **它的正确用法是「读一遍」，不是「查一条」。** 一次性的通读指导（哪几类行为、挂载顺序）价值远高于分散的类页。

所以本桶排在手写队列后段是对的。**这一页不是占位符**——归属规则、命名空间的拼写坑、三种真实关系、以及上面这批逐个核实过的类型名，都是写专题页时能直接用的素材。如果你判断一个 mod 确实需要本桶的深度内容，值得写的是一篇「沙盒玩法解剖」专题，而不是几十张类页。
