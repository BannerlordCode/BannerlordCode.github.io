# ArmyDispersionMapNotification

**Namespace:** `TaleWorlds.CampaignSystem.MapNotificationTypes`
**Module:** `TaleWorlds.CampaignSystem`
**Type:** `public class ArmyDispersionMapNotification : InformationData`
**Base:** `InformationData`
**File:** `bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem.MapNotificationTypes/ArmyDispersionMapNotification.cs`

## 概述

`ArmyDispersionMapNotification` 是「军团解散」地图通知的数据载体，比同类多带一个信息维度：**为什么散的**。除了 `[SaveableProperty(1)] public Army DispersedArmy`，它还有 `[SaveableProperty(2)] public Army.ArmyDispersionReason DispersionReason`。

它的 UI 行为与 [ArmyCreationMapNotification](../ArmyCreationMapNotification) **完全不同**，这是本类型最值得记住的一点：解散通知的 VM（`ArmyDispersionItemVM`）没有订阅任何战役事件、**没有自移除逻辑**，「检视」动作直接 `NavigationHandler?.OpenKingdom(data.DispersedArmy)` 打开被解散军团的王国界面，然后 `ExecuteRemove()`。成立通知的 VM 是「把镜头移到军团位置」，解散通知的 VM 是「打开那个王国的外交面板」。

## 心智模型

把它当成**「解散原因 + 军团引用」的静态快照**，理解三条链路就够了：

1. **写入。** `Campaign.Current.CampaignInformationManager.NewMapNoticeAdded(data)` 是唯一入口。注意官方只在玩家**不在**这支军团里时才发这条通知：`army.LeaderParty.MapFaction == Hero.MainHero.MapFaction && army.Parties.IndexOf(MobileParty.MainParty) < 0`。玩家本人在军团里时，聊天栏那条 [ArmyDispersionLogEntry](../ArmyDispersionLogEntry) 才是唯一提醒。

2. **查表。** `MapNotificationVM` 构造函数里 `_itemConstructors.Add(typeof(ArmyDispersionMapNotification), typeof(ArmyDispersionItemVM))`（`Bannerlord.Source/bin/TaleWorlds.CampaignSystem.ViewModelCollection/TaleWorlds.CampaignSystem.ViewModelCollection.Map/MapNotificationVM.cs:111`）。未注册的类型静默丢弃。

3. **清理由玩家点击驱动。** 本类型**不 override `IsValid()`**，基类默认返回 true，通知永不过期。`ArmyDispersionItemVM` 的 `_onInspect` 里先 `OpenKingdom(data.DispersedArmy)` 再 `ExecuteRemove()`——**玩家不点它就一直挂在地图角落**。这与带 `TriggerTime` 的 [AllianceOfferMapNotification](../AllianceOfferMapNotification) 靠 `IsValid()` 定时淘汰是两套机制，别混。

第二个心智锚点是 **`DispersedArmy` 是活引用，而检视链路会顺着它解引用**。VM 里 `NavigationHandler?.OpenKingdom(data.DispersedArmy)` 走的是 `MapNavigationExtensions.OpenKingdom(this INavigationHandler, Army)`（`Bannerlord.Source/bin/TaleWorlds.CampaignSystem.ViewModelCollection/TaleWorlds.CampaignSystem/MapNavigationExtensions.cs:68`），它把 `Army` 直接交给 `GetElement(handler, MapNavigationItemType.Kingdom).OpenView(army)`，中间没有任何判空。而官方调用点是在**解散事件回调里**构造的，此时 `Army` 对象还在但可能已空壳化——这是官方自己的时序，mod 里若延后构造要自己兜住。

第三个锚点：**`DispersionReason` 在本类型里只被存下来，VM 根本不用它**。`ArmyDispersionItemVM` 的构造器只读 `data.DispersedArmy`。所以这个字段是给 **mod 与日志系统**用的——想知道「玩家为什么没收到解散通知」还是「玩家本人为什么没在聊天栏看到」这类问题时，唯一的数据来源就是这里。

## 真实示例

官方唯一构造形态，从 [DefaultLogsCampaignBehavior](../DefaultLogsCampaignBehavior).OnArmyDispersed 照抄：

```csharp
ArmyDispersionLogEntry entry = new ArmyDispersionLogEntry(army, reason);
LogEntry.AddLogEntry(entry);
if (army.LeaderParty.MapFaction == Hero.MainHero.MapFaction && army.Parties.IndexOf(MobileParty.MainParty) < 0)
{
    Campaign.Current.CampaignInformationManager.NewMapNoticeAdded(
        new ArmyDispersionMapNotification(army, reason, entry.GetEncyclopediaText()));
}
```

查当前是否已有未处理的解散通知，以及它们各自的解散原因：

```csharp
CampaignInformationManager infoManager = Campaign.Current.CampaignInformationManager;
bool pending = infoManager.InformationDataExists<ArmyDispersionMapNotification>(
    (ArmyDispersionMapNotification notice) => notice.DispersionReason == Army.ArmyDispersionReason.CohesionDepleted);
Debug.Print("pending cohesion-depleted notices = " + pending, 0);
```

在 mod 里补一条带自定义说明的解散通知，并顺手把原因塞进文本变量：

```csharp
if (army.LeaderParty.MapFaction == Hero.MainHero.MapFaction)
{
    TextObject note = new TextObject("{=mykey2}The host warband of {ARMY_NAME} has broken up.");
    note.SetTextVariable("ARMY_NAME", army.EncyclopediaLinkWithName);
    Campaign.Current.CampaignInformationManager.NewMapNoticeAdded(
        new ArmyDispersionMapNotification(army, Army.ArmyDispersionReason.ObjectiveFinished, note));
}
```

## 风险与边界

- **通知不会自己过期。** 不 override `IsValid()`，基类返回 true。清理完全靠玩家点「检视」（VM 的 `_onInspect` 调 `ExecuteRemove()`）。无人值守场景（自动测试、后台存档流程）下发通知会永久堆积在 `CampaignInformationManager._mapNotices`，读档时 `OnGameLoaded` 的 `RemoveAll(t => t == null || !t.IsValid())` 也清不掉。
- **VM 不订阅任何事件。** 与 `ArmyCreationNotificationItemVM` 相反，它不监听 `ArmyDispersed` / `OnPartyJoinedArmyEvent` / `OnClanChangedKingdomEvent`。**军团已解散这条通知不会因为军团再次变动而自动消失。**
- **`DispersedArmy` 可能是空壳。** 活引用；官方在解散事件里构造，之后 `Army` 的 `Parties` / `LeaderParty` 可能已清空。VM 侧 `OpenKingdom(data.DispersedArmy)` 没有判空，延后构造的 mod 必须自己兜。
- **`DispersionReason` 无人消费。** 官方 VM 不读它，地图 UI 上永远只显示 `TitleText` 与 `DescriptionText`。想在 UI 上显示「因凝聚力耗尽」，得自己派生通知类型并注册新 VM。
- **构造器无校验。** `army` 为 null 时 `DispersedArmy` 直接是 null，没有 `Debug.FailedAssert`；`reason` 是值类型不会有问题。
- **`TitleText` 每次访问都分配。** 别在循环里反复读。
- **必须注册 VM。** 未在 `_itemConstructors` 里登记的类型会被静默丢弃，不报错、不显示。
- **存档 id 是 1 和 2。** 加字段从 3 往后，**必须同步改 `AutoGeneratedSaveManager`** 里 `AutoGeneratedGetMemberValueDispersedArmy` / `...DispersionReason` 的注册与 `SaveableCampaignTypeDefiner`，否则读旧档丢字段。
- **`DispersionReason` 依赖枚举名稳定。** 枚举成员改名会让旧存档里的字符串解析失败；1.4.5 用 [ArmyDispersionReasonEnumResolver](../ArmyDispersionReasonEnumResolver) 兜了已知的 `"LowPartySizeRatio"` 改名，未覆盖的改名仍会坏档。

## 跨版本提示

`bannerlord-1.4.5/Bannerlord.Source/bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem.MapNotificationTypes/ArmyDispersionMapNotification.cs` 是 47 行、5 个公开成员，`SaveableProperty` id 为 1 与 2。1.4.6 同名文件公开表面一致。1.3.15 侧无同名文件。

配套的 `ArmyDispersionItemVM` 在 1.4.5 里只有 18 行、1 个构造函数，与 `ArmyCreationNotificationItemVM`（56 行、3 个事件监听）形成鲜明对比——**两条通知的 UI 复杂度不是一个量级**。
