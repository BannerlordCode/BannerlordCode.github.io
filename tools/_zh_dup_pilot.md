## 2. Why the criterion fails — two distinct phenomena, conflated

### (a) SAME NAME, DIFFERENT TYPE — not duplication at all

The boss's criterion assumes one type name → one type. **Source says otherwise:**

**`AutoGeneratedSaveManager` — `internal`, in FIVE different places in 1.3.0 alone:**

```
bannerlord-1.3.0/SandBox/Sandbox/AutoGeneratedSaveManager.cs:12   internal class AutoGeneratedSaveManager : IAutoGeneratedSaveManager
bannerlord-1.3.0/StoryMode/AutoGeneratedSaveManager.cs:18          internal class AutoGeneratedSaveManager : IAutoGeneratedSaveManager
bannerlord-1.3.0/TaleWorlds.CampaignSystem/AutoGeneratedSaveManager.cs:38  internal class AutoGeneratedSaveManager : IAutoGeneratedSaveManager
   (+ 6 more files in 1.3.0; 11 files in 1.4.5, incl. TaleWorlds.Core/…, TaleWorlds.Localization/…)
```

There is **no single "the type's actual namespace"** — there are five to eleven. The
criterion has **no well-defined answer here**.

**`MetaDataExtensions` — FOUR namespaces, all real:**

```
bannerlord-1.3.0/TaleWorlds.Core/MetaDataExtensions.cs:8
bannerlord-1.3.0/TaleWorlds.CampaignSystem/Extensions/MetaDataExtensions.cs:7
bannerlord-1.3.15/TaleWorlds.SaveSystem/MetaDataExtensions.cs:7
bannerlord-1.3.0/StoryMode/Extensions/MetaDataExtensions.cs:7
```

**`Crafting` — 2 types:** `TaleWorlds.Core/Crafting.cs:11` and a
`TaleWorlds.CampaignSystem.CharacterDevelopment` one at `DefaultPerks.cs:3598`.
**`IssueQuestFlags` — 2 enums:** `.../GameMenus/GameMenuOption.cs:243` and
`.../ViewModelCollection/CampaignUIHelper.cs:3781`.

**Consequence:** the pages in `campaign`, `campaign-ext`, `core-extra`, `save-system`,
`storymode`, `mission`, `localization`, `system`, `viewmodel` are documenting **different
types that happen to share a name**. The page's own declared namespace matches a real type in
each case. **Moving any of them removes a correct page.** This is a *bucket-naming* problem
(the buckets cannot express these namespaces), not a duplication problem.

The 6 genuine duplicate groups — **every one is cross-tree**:

| `3507506e` | 3 | Crafting | v1.3.0/`campaign` · v1.3.15/`campaign-ext` · v1.4.5/`campaign-ext` |

Each version tree is a **separately published documentation set**. v1.3.0 needs its own

Note the bucket name drifts across those copies (`campaign` → `campaign-ext`) while the body
is identical — that is a **bucket-attribution change applied inconsistently across trees**,
which is a real finding, and is *not* solved by deleting a page.

## 8. What scaling this criterion would do

**Do not scale it.** On the worst cases — the ones the boss picked *because* they looked worst —
the criterion finds **zero** correct moves out of 35 pages.

If scaled, it would most likely:
1. **delete correct pages** documenting real same-named types (phenomenon a), and
2. **leave the real duplication untouched** (phenomenon b), because the duplicates live in
   different version trees where they are both required.

**A better-framed task, if the boss wants the real problem:**
- **A. Taxonomy**: buckets cannot express 4+ namespaces sharing a type name. This needs a
  naming/placement decision, not deletion. Cite the 4 `MetaDataExtensions` namespaces.
- **B. Cross-tree divergence**: v1.3.15 and v1.4.5 ship byte-identical pages for the same
  type. That is a *release/regeneration* question — should a new tree regenerate, or reuse?
- **C. Bucket drift**: the same body sits under `campaign` in v1.3.0 and `campaign-ext` in
  v1.3.15/v1.4.5. **This is a real inconsistency worth fixing** and it is invisible to the
  current criterion because no single tree contains both.

**The pilot succeeded as a pilot**: it stopped 2,215 pages from moving on a criterion with a
0% hit rate, for ~35 pages of work.
