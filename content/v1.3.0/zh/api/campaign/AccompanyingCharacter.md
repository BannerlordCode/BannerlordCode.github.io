## 概述

`AccompanyingCharacter` 回答一个具体问题：**这个跟着玩家进入聚落的 NPC，能进哪些内室？** 它只有 7 个 public 成员——一个属性、一个字段、一个构造器、五个方法。

它的模型极简：内部一个 `private List<Location> _disallowedLocations` **黑名单**。`CanEnterLocation(Location)` 就是 `!this._disallowedLocations.Contains(location)`——**名单里没有就能进**。构造器会把黑名单初始化成空列表，所以**新建的 `AccompanyingCharacter` 默认「哪里都能进」**，必须显式禁止。

**它不继承 `MBObjectBase`、没有 `StringId`、不能被 `MBObjectManager` 单独取到。** 它由 [LocationEncounter](../LocationEncounter) 持有——那是 `public List<AccompanyingCharacter> CharactersAccompanyingPlayer { get; private set; }`（`LocationEncounter.cs:20`），构造器里 `new` 出空列表。所以**你永远是从 `PlayerEncounter.LocationEncounter` 上拿到它，而不是自己 new 一个**。

**存档上有一个必须知道的缺口。** 三个持久化标记分别是 `[SaveableProperty(1)] IsFollowingPlayerAtMissionStart`、`[SaveableField(2)] _disallowedLocations`，以及 `protected override void AutoGeneratedInstanceCollectObjects` 只做了 `collectedObjects.Add(this._disallowedLocations);`。**`public LocationCharacter LocationCharacter` 这个字段没有任何存档标记**，`AutoGeneratedSaveManager.cs:376-379` 注册的也只有 property 1 与 field 2。所以 `LocationCharacter` 是**运行期重建的**，读档后要靠 `LocationEncounter` 重新绑定。

## 心智模型

把它当成**「一个 NPC 在当前聚落内的活动范围」**，然后死记两条规则。

**规则一：白名单式的默认 + 黑名单式的管理。** 初始 `_disallowedLocations` 为空 ⇒ 处处可进。之后只有两种改法：把某个 Location 加进黑名单（`DisallowEntranceToLocations` / `DisallowEntranceToAllLocations`），或从黑名单里移除（`AllowEntranceToLocations` / `AllowEntranceToAllLocations`）。**四个改法方法成对**：

| 方法 | 判据 | 实现要点 |
| --- | --- | --- |
| `DisallowEntranceToLocations(predicate)` | 谓词命中**且**当前不在黑名单 | `if (predicate(location) && !this._disallowedLocations.Contains(location))` 才 Add ——**自带去重** |
| `AllowEntranceToLocations(predicate)` | 谓词命中**且**当前在黑名单 | `if (predicate(location) && this._disallowedLocations.Contains(location))` 才 Remove ——**同样自带去重** |

那个 `Contains` 检查不是冗余，是**幂等性的保证**：重复调用 `DisallowEntranceToLocations` 两次，黑名单里也只有一条，不会出现重复项。

**规则二：三个批量方法遍历的是静态的 `LocationComplex.Current`，不是「这个角色所属的聚落」。** `AllowEntranceToLocations` 与 `DisallowEntranceToLocations` 的循环体都是 `foreach (Location location in LocationComplex.Current.GetListOfLocations())`，`DisallowEntranceToAllLocations` 也一样 `this._disallowedLocations.AddRange(LocationComplex.Current.GetListOfLocations());`。

`GetListOfLocations()` 的实现是 `foreach (KeyValuePair<string, Location> keyValuePair in this._locations) yield return keyValuePair.Value;`——**它是个 `yield return` 迭代器，返回的是活视图，每次遍历都重新走字典**。

所以推论很硬：**黑名单里装的 Location 对象，身份绑定的是「调用那一刻的 `LocationComplex.Current`」**。在一个聚落里禁止进入某个 Location，存下来的那个 `Location` 引用换到另一个聚落就没有意义；而 `DisallowEntranceToAllLocations()` 禁止的也**只是当前 LocationComplex 的那批 Location**，不是「所有聚落的所有内室」。`AllowEntranceToAllLocations()` 反而是安全的——它只 `Clear()` 自己那个列表，不碰任何静态状态。

**第三件事：`IsFollowingPlayerAtMissionStart` 是存档的。** 它带 `[SaveableProperty(1)]`，getter 公开、setter 私有。官方四个读点全在 `SandBox/Missions/` 与 `SandBox/Conversation/` 下：`MissionLocationLogic.cs:175` 用 `CharactersAccompanyingPlayer.Any((AccompanyingCharacter c) => c.IsFollowingPlayerAtMissionStart)` 统计有多少跟随者，`MissionAgentHandler.cs:1137` 与 `MissionAlleyHandler.cs:253` 用它决定 Agent 是否生成，`MissionConversationLogic.cs:200` 用它决定是否触发跟随对话。**它与准入无关，只管「这个人跟不跟你走」。**

## 真实示例

关进所有内室，只放开指定的几间（照抄 `ClanMemberRolesCampaignBehavior.cs:493-495` 的形状）：

```csharp
AccompanyingCharacter accompanyingCharacter =
    PlayerEncounter.LocationEncounter.GetAccompanyingCharacter(locationCharacter);

if (accompanyingCharacter != null)
{
    accompanyingCharacter.DisallowEntranceToAllLocations();
    accompanyingCharacter.AllowEntranceToLocations((Location x) =>
        x == LocationComplex.Current.GetLocationWithId("center")
        || x == LocationComplex.Current.GetLocationWithId("lordshall"));
}
```

**调用顺序很重要**：必须先 `DisallowEntranceToAllLocations()` 再 `AllowEntranceToLocations(...)`。反过来先放开再全禁，放开的效果会被抹掉。

放宽到「除某个目标房屋外全部可进」（照抄 `ProdigalSonIssueBehavior.cs:869-871` 的形状）：

```csharp
foreach (AccompanyingCharacter character in PlayerEncounter.LocationEncounter.CharactersAccompanyingPlayer)
{
    if (!character.CanEnterLocation(this._targetHouse))
    {
        character.AllowEntranceToLocations((Location x) =>
            character.CanEnterLocation(x) || x == this._targetHouse);
    }
}
```

谓词里那个 `character.CanEnterLocation(x) ||` 的意思是「本来就能进的保持能进，不能进的看是不是目标房屋」——**因为 `AllowEntranceToLocations` 只会 Remove 黑名单项，这个写法等价于「只把目标房屋从黑名单里摘出来」**。

遍历并统计跟随玩家的人数：

```csharp
int followers = 0;
foreach (AccompanyingCharacter c in PlayerEncounter.LocationEncounter.CharactersAccompanyingPlayer)
{
    if (c.IsFollowingPlayerAtMissionStart)
    {
        followers++;
    }
}
Debug.Print("followers = " + followers, 0);
```

`CharactersAccompanyingPlayer` 是 `public List<AccompanyingCharacter>`，可直接 `foreach`；也可以用 LINQ 的 `.Any((AccompanyingCharacter c) => c.IsFollowingPlayerAtMissionStart)`——`MissionLocationLogic.cs:175` 就是这么写的。

## 风险与边界

- **默认处处可进。** 构造器把 `_disallowedLocations` 初始化成空列表，`CanEnterLocation` 于是恒返回 true。**不显式 `Disallow*` 就等于没有约束。**
- **三个批量方法都绑死静态的 `LocationComplex.Current`。** 循环体是 `foreach (Location location in LocationComplex.Current.GetListOfLocations())`，`DisallowEntranceToAllLocations` 的 `AddRange` 同理。**这意味着黑名单里的 `Location` 引用来自「调用那一刻的当前 LocationComplex」**——换一个聚落再解除禁止，解禁的是新聚落的同名 Location 对象，旧聚落的记录不会跟着对。**跨聚落复用同一个 `AccompanyingCharacter` 实例是错的用法。**
- **`DisallowEntranceToAllLocations` 不是全局禁用。** 它只 `AddRange(LocationComplex.Current.GetListOfLocations())`，范围就是当前这个 LocationComplex。名字比实际范围大。
- **`LocationCharacter` 不进存档。** 它是 `public` 字段但**没有 `[SaveableField]`**，`AutoGeneratedInstanceCollectObjects` 也只收 `_disallowedLocations`。读档后这个引用要靠上层重建——**不要假设它跨存档有效**。
- **`IsFollowingPlayerAtMissionStart` 的 setter 是 `private`。** `[SaveableProperty(1)]` 属性外部只读。想改只能在构造时传。
- **`AllowEntranceToLocations` / `DisallowEntranceToLocations` 都幂等。** 内部有 `Contains` 检查，重复调用不会产生重复项。**但这也意味着「重复调用」不能用来累加计数**。
- **`GetListOfLocations()` 是 `yield return` 迭代器。** 每次遍历都重新走 `_locations` 字典。在谓词里做重活会有明显开销。
- **不是 `MBObjectBase`。** 没有 `StringId`、没有 `Id`、不能 `Game.Current.ObjectManager.GetObject<AccompanyingCharacter>(...)`。**只能通过 `PlayerEncounter.LocationEncounter` 取。**
- **`GetAccompanyingCharacter` 有两个重载，按引用相等查找。** `GetAccompanyingCharacter(LocationCharacter)` 是 `Find((AccompanyingCharacter x) => x.LocationCharacter == locationCharacter)`；`GetAccompanyingCharacter(CharacterObject)` 是 `Find(delegate (AccompanyingCharacter x) { ... x.LocationCharacter.Character == characterObject ... })`。**第一个按 `LocationCharacter` 引用相等，第二个按里面的 `Character` 相等**——传错重载会返回 null。
- **非 `sealed`，但也没有虚方法可覆写。** 五个方法里没有一个是 `virtual`（只有 `AutoGeneratedInstanceCollectObjects` 是 `protected virtual`，那是存档生成的）。所以**派生它没法改变行为**，只能包装。

## 怎么用

### 怎么拿到它

它没有工厂。**正规入口是遭遇系统，不是构造函数。** `TaleWorlds.CampaignSystem/Encounters/LocationEncounter.cs:30` 的 `AddAccompanyingCharacter(LocationCharacter locationCharacter, bool isFollowing = false)` 才是官方用的那条路，`:34` 在里面 `new`。你自己能拿到的容器是 `PlayerEncounter.LocationEncounter`（`TaleWorlds.CampaignSystem/Encounters/PlayerEncounter.cs:285`，静态属性），它内部的列表 `CharactersAccompanyingPlayer` 是 `public` 的 `List<AccompanyingCharacter>`（`LocationEncounter.cs:20`）。

构造函数本身是 `AccompanyingCharacter(LocationCharacter locationCharacter, bool isFollowingPlayerAtMissionStart)`（`TaleWorlds.CampaignSystem/Settlements/Locations/AccompanyingCharacter.cs:41`），两个参数——但**绕过 `AddAccompanyingCharacter` 直接 `new` 的话，这个实例不会进入遭遇的列表，也就永远不会被游戏查到**。

### 典型用法

加入一个随行角色，然后把某些地点禁掉：

```csharp
using TaleWorlds.CampaignSystem;
using TaleWorlds.CampaignSystem.Encounters;
using TaleWorlds.CampaignSystem.Settlements.Locations;

public static class CompanionGating
{
    public static void Gate(LocationCharacter companion, Location forbidden)
    {
        LocationEncounter encounter = PlayerEncounter.LocationEncounter;
        if (encounter == null)
        {
            return;
        }

        // 走遭遇系统的入口，不要自己 new。
        encounter.AddAccompanyingCharacter(companion, true);

        AccompanyingCharacter added = encounter.GetAccompanyingCharacter(companion);
        if (added == null)
        {
            return;
        }

        // 谓词要对 LocationComplex.Current 里的地点生效，必须在遭遇进行中调用。
        // Location 的身份字段叫 StringId，不叫 Id。
        added.DisallowEntranceToLocations(loc => loc.StringId == forbidden.StringId);

        // 读回来确认：空列表时恒为 true，也就是"处处可进"。
        bool canEnter = added.CanEnterLocation(forbidden);
    }
}
```

签名核对：`GetAccompanyingCharacter` 有两个重载，`LocationEncounter.cs:40` 收 `LocationCharacter`（按引用相等查），`LocationEncounter.cs:46` 收 `CharacterObject`（按 `LocationCharacter.Character` 查，并且对 null 做了保护）。**两者都可能返回 null。**

### 最容易踩的坑

**重复调用 `AddAccompanyingCharacter` 去改 `IsFollowingPlayerAtMissionStart`，改不动。**

看 `LocationEncounter.cs:32` 那个守卫：

```
LocationEncounter.cs:32   if (!this.CharactersAccompanyingPlayer.Any(
                              x => x.LocationCharacter.Character == locationCharacter.Character))
LocationEncounter.cs:34       new AccompanyingCharacter(locationCharacter, isFollowing);
LocationEncounter.cs:35       this.CharactersAccompanyingPlayer.Add(item);
```

判重依据是 **`LocationCharacter.Character` 这个角色**，不是 `LocationCharacter` 实例，也不是你要传的 flag。所以同一个角色第二次被加进来时，`Any(...)` 为 true，整个 `if` 体被跳过——**没有异常，没有日志，什么都没发生**，而列表里留着的是第一次创建的那个实例，它带着第一次传进去的 `IsFollowingPlayerAtMissionStart`。

后果很具体：你先以 `isFollowing: false` 加入一个同伴，随后想改成跟随玩家，改法如果是"再调一次 `AddAccompanyingCharacter(companion, true)`"，那这个改动**静默失效**。而 `IsFollowingPlayerAtMissionStart` 的 setter 是私有的（`AccompanyingCharacter.cs:38`），你也没有别的入口能改它，于是这个角色整个这次遭遇都保持"不跟随"，直到遭遇结束。正确做法是先 `RemoveAccompanyingCharacter(LocationCharacter locationCharacter)`（`LocationEncounter.cs:56`）再重新添加。

顺带一句：那个守卫里的 `x.LocationCharacter.Character` **没有 null 保护**，而同文件 `GetAccompanyingCharacter(CharacterObject)` 在 `:51` 里是显式判过 `locationCharacter != null` 的。如果某条路径能让列表里出现 `LocationCharacter` 为 null 的项，`AddAccompanyingCharacter` 会在这里抛 `NullReferenceException`——而 `GetAccompanyingCharacter` 不会。排查"同一个报错只在某个特定遭遇里出现"时，这条差异是线索。

## 跨版本提示

`AccompanyingCharacter` 的 public 表面在 `bannerlord-1.3.0/`、`bannerlord-1.3.15/`、`bannerlord-1.4.6/`、`bannerlord-1.4.7/`、`bannerlord-1.5.3/` 五棵树里**完全一致**：都是 7 个 public 成员（1 个属性 + 1 个公开字段 + 1 个构造器 + 5 个方法），0 新增 / 0 移除 / 0 签名变化。

**变的是 LocationComplex 的内部布局。** `LocationComplex.Current.GetListOfLocations()` 返回哪些 Location、它们的 `StringId`（`"center"`、`"lordshall"`、`"prison"` 这些硬编码 id）仍然稳定，但 `LocationComplex` 内部结构在后续版本有过调整。**`ClanMemberRolesCampaignBehavior` 那段代码依赖 `"center"` 这个 id 存在**——如果你覆盖聚落布局并改掉了它，那个 NPC 会留在一个不存在的 id 上，行为静默失效。

另一条要注意的是：`IsFollowingPlayerAtMissionStart` 读的四个官方点全在 `SandBox/Missions/` 与 `SandBox/Conversation/` 目录下，**都属于沙盒而不是引擎**。引擎侧只通过 `HeroAgentLocationModel.DefaultHeroAgentLocationModel.cs:74` 那一条间接涉及——它用 `PlayerEncounter.LocationEncounter.Charact...` 判断同伴是否已作为 Agent 生成。**这意味着这一整套机制的可扩展点主要在沙盒行为里，而不是在引擎 API 里。**
