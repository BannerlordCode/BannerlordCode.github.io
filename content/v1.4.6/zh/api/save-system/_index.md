# save-system 桶：存档系统

这个桶对应 `TaleWorlds.SaveSystem` 程序集，是全站唯一一个**可以独立于游戏存在**的持久化子系统：它不认识英雄、不认识物品、不认识战役，它只认识「类型定义表 + 对象图 + 一份字节流」三件事。源码目录下按职责分成 `Definition/`（类型定义表）、`Save/`、`Load/`、`Resolvers/`（冲突与枚举解析）四个子目录，加上根目录的入口类型，共 110 个 `.cs`、56 个公开类型。

**mod 作者在什么场景碰到它**：只有两个场景，但都绕不开——

1. **让自定义数据活过存档**。给 `CampaignBehaviorBase` 的自定义类加字段时，那个字段必须挂 `[SaveableField]` 或 `[SaveableProperty]`（[SaveableFieldAttribute](./SaveableFieldAttribute)、[SaveablePropertyAttribute](./SaveablePropertyAttribute)），否则重载后字段归零。同时你的类型必须能被存档系统认出：`[SaveableRootClass]`、`[SaveableInterface]`，或者由一个 `SaveableTypeDefiner` 子类登记进定义表（[SaveableTypeDefiner](./SaveableTypeDefiner)）。这三个特性加一个 definer，就是「mod 数据进存档」的全部前置条件。
2. **主动发起一次存档或读档**。绝大多数 mod 并不自己调（游戏在退出战役、进入菜单时自动存），但做云存档、存档槽管理、或者调试「我的行为存进去没有」时会直接用 [SaveManager](./SaveManager) 的 `Save` / `Load`。

一个容易踩的坑：`SaveManager` **不决定存档文件名**，文件名由 `ISaveDriver` 实现决定（官方是 `FileDriver` / `AsyncFileSaveDriver`）。自带一个 `InMemDriver` 做内存存档时，这个差别才会显出来。

## 已手写的页面

本桶已手写 6 张页，覆盖「怎么标字段」「怎么发起流程」「遍历与编号谁来做」与「谁来读写字节」这一条主线：

- [SaveableFieldAttribute](./SaveableFieldAttribute) — 标注一个私有字段参与序列化，告诉保存系统这个字段在所属类型内的局部存档 id。
- [SaveablePropertyAttribute](./SaveablePropertyAttribute) — 标注一个属性参与序列化，作用同上，但走属性而非字段。
- [SaveableTypeDefiner](./SaveableTypeDefiner) — 存档类型定义的抽象基类，mod 靠子类向 `DefinitionContext` 登记类、结构体、枚举、容器与泛型的存档编号。
- [SaveManager](./SaveManager) — 存档流程总管，建立 `DefinitionContext`、收集对象图交给 `ISaveDriver` 落盘，并把结果包成 `SaveOutput` / `LoadResult`。
- [ISaveDriver](./ISaveDriver) — 「存档数据最终怎么落到介质上」的抽象边界。它完全不碰对象图——遍历、序列化、还原都由上下文那一层负责，它只管写一份、列出条目与存档名、读元数据、读一份、删一份、判断是否存在、判断自己是否异步。官方有三个实现，介质与是否异步的差别直接决定你的保存流程能不能拿到最终结果。
- [SaveContext](./SaveContext) — 单次保存的**遍历与编号上下文**：从根对象出发递归遍历整个对象图，为对象 / 容器 / 字符串分配唯一 id，最终产出 `GameData` 四段字节流。它是 `SaveManager` 与 `ISaveDriver` 之间的桥梁，也是排查「我的字段到底进没进存档」时真正该断点的地方。

## 尚未撰写的部分

上面 6 个类型出自 56 个公开类型，**还有 50 个没有页面**。缺口集中在流程的另外两半——「表与结果长什么样」：

- **驱动（自己实现存档格式时必看）**：`FileDriver`、`AsyncFileSaveDriver`、`InMemDriver`
- **上下文（理解收集流程）**：`DefinitionContext`、`LoadContext`、`LegacySaveContext`、`SaveCodeGenerationContext`、`LateLoadInitializationCallback`、`LoadInitializationCallback`
- **解析器（版本冲突与枚举）**：`IConflictResolver`、`IEnumResolver`、`IObjectResolver`、`IAutoGeneratedSaveManager`、`IBasicTypeSerializer`
- **定义表结构**：`TypeDefinition`、`TypeDefinitionBase`、`MemberDefinition`、`FieldDefinition`、`PropertyDefinition`、`ContainerDefinition`、`ContainerType`、`SaveableBasicTypeDefiner`
- **特性与编号**：`SaveableRootClassAttribute`、`SaveableInterfaceAttribute`、`SaveId`、`ContainerSaveId`、`TypeSaveId`、`MemberTypeId`、`EntryId`
- **结果与错误对象（判失败时要看）**：`SaveOutput`、`SaveEntry`、`SaveEntryFolder`、`LoadResult`、`LoadData`、`ObjectLoadData`、`ObjectHeaderLoadData`、`ContainerHeaderLoadData`、`LoadError`、`SaveError`、`SaveStatistics`、`GameData`、`MetaData`、`MetaDataExtensions`、`SaveGameFileInfo`
- **杂项**：`ISavedStruct`、`CustomField`、`FolderId`、`LegacyGameDataDeserializer`

`SaveEntryExtension` / `SaveFolderExtension` / `SaveEntry` 系列的扩展方法集中在 `Save/` 与 `Load/` 子目录，是翻旧存档最常用的工具；`SaveGameFileInfo` 是枚举存档文件的入口。这些类型都属于「读得懂源码就能用」的层级，mod 作者通常只在排查存档损坏或做存档迁移时才深入。

要确认某个类型实际落在哪个桶，见 [模块地图](../../architecture/module-map)。存档根对象在 [core-extra](../core-extra/Game)，自定义字段挂在 [campaign](../campaign/Campaign) 的行为上——这两页是本桶最常被链接出去的方向。
