## Mental Model

Picture it as **three doorbells on a wall, each wired to one room**. A doorbell does not open the door; it announces that something happened at it. Every member here is `void` and takes no arguments — there is no payload, no result, no way to ask "is the exit button down?". The bridge tells the managed side *that* an input occurred and leaves the interpretation entirely to the receiver.

The consequence is that these calls are **events, not commands**. Calling `OnExitButtonAction()` does not close the game; it announces to native that the exit affordance was activated, and whatever native does next happens outside managed control. That is why they are `void` and why none of them returns a `bool` — contrast with [`IMBTeam`](../IMBTeam), where a `bool` return means "the relation was written" and means nothing else either.

The boundary worth naming is that **the press/release pair is a two-phase signal, not two independent actions**. `on_edit_mode_enter_press` and `on_edit_mode_enter_release` (`:11`, `:14`) describe the two halves of one key event. A receiver that treats them as independent will react to the press and then again to the release, which is the classic double-toggle: enter edit mode, immediately leave it.

**A typical use.** A mod that drives the engine's own edit-mode toggle from a menu option calls the pair in order, the same way `MBInitialScreenBase` itself does — it invokes the press from its own input handling at `MBInitialScreenBase.cs:83`:


**What to watch out for.** Firing only one half of the press/release pair. The single most common mistake is calling `OnEditModeEnterPress()` alone, because it is the member whose name suggests "enter". The consequence is that the engine receives a press with no matching release and the toggle stays half-applied — the edit-mode key reads as stuck. Always pair them, in press-then-release order, exactly as `MBInitialScreenBase.cs:83` and its release counterpart do.

## Risks and crash boundaries

- **A mod assembly cannot call this interface.** `internal interface IMBScreen` (`IMBScreen.cs:7`), `internal static` field (`MBAPI.cs:38`), `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). `MBInitialScreenBase` is public.
- **Every member is `void` with no parameters.** `IMBScreen.cs:8`-`:15`. **You get no acknowledgement** — a call that native ignores is indistinguishable from one it honoured, so do not branch on "did it work".
- **These are notifications, not commands.** `DoExitButtonAction()` (`MBInitialScreenBase.cs:211`) signals; it does not itself terminate the game or return a result.
- **The press/release pair is a unit.** Sending only `OnEditModeEnterPress()` (`:221`) leaves the edit-mode key half-applied. This is the primary trap on the page.
- **Order matters.** Release before press is as wrong as press without release.
- **Despite the module, nothing here is mission-aware.** No mission pointer, agent or position appears in any signature — do not expect this bridge to work during a battle.
- **Direction is native → managed.** These are entry points the engine calls, not capabilities a mod drives the game with; calling them from a mod means announcing an input the player did not make.
- **Not a save participant.** No `[Serializable]`, no sync surface.
