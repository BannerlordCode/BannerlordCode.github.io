## 概述

`AgentSaveData` 解决的问题很具体：**大地图上存档只记了「哪些尸体下次任务里要复现」，任务里却需要一个能重建那些尸体的完整描述。** 这个 struct 就是那个描述，一个 4 字段的值类型：

| 字段 | 类型 | 存档 ID | 说明 |
| --- | --- | --- | --- |
| `CharacterStringId` | `string` | `[SaveableField(1)]` `readonly` | 角色的 `StringId`，读档后用 `MBObjectManager.Instance.GetObject<CharacterObject>(...)` 解回来 |
| `SpawnFrame` | [MatrixFrame](../MatrixFrame) | `[SaveableField(2)]` **可写** | 世界坐标 + 朝向。**唯一可变的字段**，被 `UpdateSpawnFrame` 改写 |
| `AgentSpawnPointTags` | `string[]` | `[SaveableField(3)]` `readonly` | 复制体身上的实体标签，用来禁用对应的巡逻点 |
| `AgentSeed` | `int` | `[SaveableField(4)]` `readonly` | 装备随机种子，复现时喂给 `AgentBuildData.EquipmentSeed` |

它是 `struct` 不是 `class`，所以**没有 `StringId`、不会被 `MBObjectManager` 注册、不参与引用比较**。它在存档系统里的身份完全由两个硬编码数字定义：`SaveableCoreTypeDefiner.cs:61` 的 `AddStructDefinition(typeof(AgentSaveData), 1012, null)`——**类型 ID `1012` 就是它在存档二进制格式里的身份**。改字段顺序、改字段类型都会让旧档读不出来。

**注意 `[SaveableField]` 的编号 `1..4` 与类型 ID `1012` 是两套东西**：前者是结构体内部字段序号（`AutoGeneratedSaveManager.cs:155-158` 里 `new MemberTypeId(1, 1)` ~ `new MemberTypeId(1, 4)`），后者是全局类型表里的位置。**两者都不能改。**

## 心智模型

把它当成**「任务期快照 + 下次任务期的重建清单」**，只有这一个用途。完整链路在 `CheckpointMissionLogic`（检查点任务）里跑了一圈：

**第一步，任务开始时登记所有生成过的单位。** `RegisterAgent(Agent agent)`（`CheckpointMissionLogic.cs:187`）：

```csharp
allSpawnedSaveableAgents.Add(agent, new AgentSaveData(stringId, new MatrixFrame(ref lookRotation, ref position), agent.AgentVisuals.GetEntity().Tags, agent.Origin.Seed));
```

四个实参一一对应四个字段：`agent.Character.StringId`、`agent.LookRotation` + `agent.Position` 拼成的 `MatrixFrame`、`agent.AgentVisuals.GetEntity().Tags`、`agent.Origin.Seed`。**`AgentSpawnPointTags` 存的是活体 agent 当前的实体标签，不是它出生点的标签**——名字有点误导，实际用途是复现时把同样的标签贴回尸体（见第四步）。

**第二步，敌人死亡时更新它的位置。** `OnEarlyAgentRemoved`（`CheckpointMissionLogic.cs:40`）：

```csharp
if (affectedAgent.Team == Mission.Current.PlayerEnemyTeam && agentState == 4)   // 4 == AgentState.Deleted
{
    foreach (KeyValuePair<Agent, AgentSaveData> keyValuePair in this._allSpawnedSaveableAgents)
    {
        if (keyValuePair.Key == affectedAgent)
        {
            AgentSaveData value = keyValuePair.Value;
            Mat3 lookRotation = keyValuePair.Key.LookRotation;
            Vec3 position = keyValuePair.Key.Position;
            value.UpdateSpawnFrame(new MatrixFrame(ref lookRotation, ref position));
            break;
        }
    }
}
```

**为什么需要这一步**：agent 是按编队点在任务开始时生成的，登记时的位置是**出生位置**；等它被打死滚到坡底，复现时应该出现在**尸体所在处**。`value` 是 `KeyValuePair.Value` 的一个**结构体副本**——`UpdateSpawnFrame` 只能改这个副本，**原字典里的那一份不会被更新**。这是官方代码的一个真实局限（`KeyValuePair.Value` 不可 `ref` 返回），但因为紧接着 `OnCheckpointUsed` 会从字典重新取值，实际没出问题。

**第三步，用检查点时把「当前已死的」写入战役数据。** `OnCheckpointUsed`（`CheckpointMissionLogic.cs:124`）：

```csharp
this._checkpointCampaignBehavior.LastUsedMissionCheckpointId = checkpointUniqueId;
this._checkpointCampaignBehavior.CorpseList.Clear();
foreach (KeyValuePair<Agent, AgentSaveData> keyValuePair in this._allSpawnedSaveableAgents)
{
    if (keyValuePair.Key.State == 4 || keyValuePair.Key.State == 3)   // Deleted 或 Killed
    {
        this._checkpointCampaignBehavior.CorpseList.Add(keyValuePair.Value);
    }
}
```

`CorpseList` 的类型是 `public List<AgentSaveData> CorpseList = new List<AgentSaveData>();`，通过 `CheckpointCampaignBehavior.cs:20` 的 `dataStore.SyncData<List<AgentSaveData>>("CorpseList", ref this.CorpseList);` 落盘。**这一步才真正跨任务持久化**，前面两步都只是任务内的 `Dictionary<Agent, AgentSaveData>`。

**第四步，下次进任务时复现。** `SpawnCorpses()`（`CheckpointMissionLogic.cs:160`）：

```csharp
foreach (AgentSaveData agentSaveData in this._checkpointCampaignBehavior.CorpseList)
{
    CharacterObject @object = MBObjectManager.Instance.GetObject<CharacterObject>(agentSaveData.CharacterStringId);
    AgentBuildData agentBuildData = new AgentBuildData(@object).TroopOrigin(new SimpleAgentOrigin(@object, -1, null, default(UniqueTroopDescriptor))).EquipmentSeed(agentSaveData.AgentSeed).InitialPosition(ref agentSaveData.SpawnFrame.origin);
    Vec3 f = agentSaveData.SpawnFrame.rotation.f;
    Vec2 asVec = f.NormalizedCopy().AsVec2;
    AgentBuildData agentBuildData2 = agentBuildData.InitialDirection(ref asVec);
    Agent agent = Mission.Current.SpawnAgent(agentBuildData2, false);
    agent.MakeDead(true, ActionIndexCache.act_none, -1);
    GameEntity entity = agent.AgentVisuals.GetEntity();
    foreach (string text in agentSaveData.AgentSpawnPointTags)
    {
        entity.AddTag(text);
    }
    this.RegisterAgent(agent);
}
```

四个字段在这里**逐个被消费**：`CharacterStringId` → 解对象；`AgentSeed` → `EquipmentSeed`；`SpawnFrame.origin` → `InitialPosition`；`SpawnFrame.rotation.f.NormalizedCopy().AsVec2` → `InitialDirection`；`AgentSpawnPointTags` → 贴回实体标签。最后又 `RegisterAgent(agent)` 一次，让复现出来的尸体也能被后续检查点再次登记。

**第五步，反向使用标签。** `DisablePatrolAreasAccordingToTheLastUsedCheckpoint()`（`CheckpointMissionLogic.cs:137`）用 `gameEntity2.GetChild(0).Tags.SequenceEqual(agentSaveData.AgentSpawnPointTags)` 匹配 `DynamicPatrolAreaParent` 的孩子，把对应的 `PatrolPoint` 禁用掉——**已经死过的敌人，其巡逻点不再重新激活**。这是 `AgentSpawnPointTags` 真正被当作「生成点身份」用的地方。

一句话心智模型：**`AgentSaveData` = 「这个单位是谁 + 他死在哪 + 他身上贴了什么点标签 + 他的装备随机种子」，让检查点机制能在下一次进入同一场景时精确复现战场痕迹。**

## 真实示例

登记一个单位（照抄 `CheckpointMissionLogic.RegisterAgent` 的形状，注意 `MatrixFrame` 的 `ref` 构造）：

```csharp
private readonly Dictionary<Agent, AgentSaveData> _registry = new Dictionary<Agent, AgentSaveData>();

public void RegisterMyAgent(Agent agent)
{
    if (agent == null || agent.Character == null)
    {
        return;
    }
    string stringId = agent.Character.StringId;
    Mat3 lookRotation = agent.LookRotation;
    Vec3 position = agent.Position;
    // 结构体数组字段是引用拷贝，不是深拷贝——这里存的是同一批字符串
    this._registry[agent] = new AgentSaveData(
        stringId,
        new MatrixFrame(ref lookRotation, ref position),
        agent.AgentVisuals.GetEntity().Tags,
        agent.Origin.Seed);
}
```

敌人死亡后把位置改成尸体所在处（`agentState == 4` 就是 [AgentState](../AgentState) 的 `Deleted`）：

```csharp
public override void OnEarlyAgentRemoved(Agent affectedAgent, Agent affectorAgent, AgentState agentState, KillingBlow blow)
{
    if (affectedAgent.Team != Mission.Current.PlayerEnemyTeam || agentState != AgentState.Deleted)
    {
        return;
    }
    if (!this._registry.TryGetValue(affectedAgent, out AgentSaveData value))
    {
        return;
    }
    Mat3 lookRotation = affectedAgent.LookRotation;
    Vec3 position = affectedAgent.Position;
    // 只改副本：value 是 struct 的拷贝，写回字典需要重新赋值
    value.UpdateSpawnFrame(new MatrixFrame(ref lookRotation, ref position));
    this._registry[affectedAgent] = value;
}
```

**官方那段循环漏掉了最后这行 `this._registry[affectedAgent] = value;`**，所以它的更新只活到 `OnCheckpointUsed` 之前——但因为中间没有别的读取点，行为上看不出差别。你自己写的时候补上这一行更稳。

复现一具尸体（`SpawnCorpses` 的精简版，四个字段逐个消费）：

```csharp
private void RespawnCorpse(AgentSaveData data)
{
    CharacterObject character = MBObjectManager.Instance.GetObject<CharacterObject>(data.CharacterStringId);
    if (character == null)
    {
        return;   // StringId 指向的角色在当前模块里不存在
    }
    AgentBuildData buildData = new AgentBuildData(character)
        .TroopOrigin(new SimpleAgentOrigin(character, -1, null, default(UniqueTroopDescriptor)))
        .EquipmentSeed(data.AgentSeed)
        .InitialPosition(ref data.SpawnFrame.origin);
    Vec2 direction = data.SpawnFrame.rotation.f.NormalizedCopy().AsVec2;
    Agent agent = Mission.Current.SpawnAgent(buildData.InitialDirection(ref direction), false);
    agent.MakeDead(true, ActionIndexCache.act_none, -1);
    GameEntity entity = agent.AgentVisuals.GetEntity();
    foreach (string tag in data.AgentSpawnPointTags)
    {
        entity.AddTag(tag);
    }
}
```

## 风险与边界

- **这是官方内部结构体，不是扩展点。** 全树唯一的 `new AgentSaveData(...)` 在 `CheckpointMissionLogic.RegisterAgent`。你可以照着它的形状造自己的存档结构，但**别指望改本类型的字段去满足你的需求**——改了会同时破坏官方检查点机制和旧档兼容。
- **`struct` + 数组字段 = 浅拷贝。** `AgentSpawnPointTags` 存的是数组引用。`AgentSaveData a = b;` 之后改 `a.AgentSpawnPointTags[0]` 会同时改到 `b`。`readonly` 只挡住「换引用」，挡不住「改元素」。
- **`UpdateSpawnFrame` 只改副本。** 它是实例方法、`struct` 按值传递。你在 `foreach (KeyValuePair<Agent, AgentSaveData> kv in dict)` 里拿到的是拷贝，改完必须显式写回字典——**官方就漏了这一步**，只是恰好不影响结果。
- **类型 ID `1012` 与字段 ID `1..4` 是存档格式的一部分。** `SaveableCoreTypeDefiner.cs:61` 和 `AutoGeneratedSaveManager.cs:155-158` 把它们写死了。**改字段顺序、改字段类型、加字段到中间都会让旧存档读不出**，而且症状通常是加载时抛异常而不是静默降级。
- **`CharacterStringId` 是弱引用。** 它只是字符串。角色所属模块没被加载时 `MBObjectManager.Instance.GetObject<CharacterObject>(...)` 返回 `null`，你的复现逻辑会 NRE。**官方代码没有判空**（`SpawnCorpses` 直接把 `@object` 塞进 `AgentBuildData`），因为它假定检查点任务的角色一定在同一模块里。
- **四个字段里三个 `readonly`。** 想加第五个信息（比如血量、装备 override）必须改类型定义——那就等于改存档格式。**实践上的正确做法是在你自己的 `ICampaignBehavior` 里另建一个自己的 saveable struct。**
- **只有 `SpawnFrame` 可写，而且没有 setter。** 想原地改某一项得整个替换 `MatrixFrame` 再调 `UpdateSpawnFrame`。
- **`Mission.Current` 与 `Campaign.Current` 的隐式依赖。** 复现路径同时用到 `MBObjectManager.Instance`（读对象）、`Campaign.Current`（读 `CorpseList`，由 `CheckpointCampaignLogic` 构造器捕获）、`Mission.Current`（生成 agent）。**在任务外调用这些方法会 NRE**，它是纯任务期 + 战役期的桥接结构。
- **`AutoGenerated*` 成员别碰。** 一个 `public static`、一个 `private`，加四个 `internal static`。它们是存档框架的产物，手写调用没有任何意义，签名也会随框架变化。

## 怎么用

**怎么拿到。** 本体在 `bannerlord-1.3.0/TaleWorlds.Core/AgentSaveData.cs:9`，结构体，构造函数是 `AgentSaveData(string characterStringId, MatrixFrame spawnFrame, string[] agentSpawnPointTags, int agentSeed)`（`AgentSaveData.cs:12`）—— 四个参数，没有无参版本。

**但你要先接受一个前提：这个类型不是给你用的扩展点。** 全树唯一的 `new AgentSaveData(...)` 在官方自己的检查点逻辑里。也就是说你的代码不会从任何入口「拿到」一个它 —— 想用只有 `new` 一条路，而 new 出来的实例官方流程根本不会读。

四个字段的**可写性不一样，这是最需要先记住的**（`AgentSaveData.cs:64/68/72/76`）：

- `CharacterStringId` 是 `public readonly string` —— 赋值后不可改
- `SpawnFrame` 是 `public MatrixFrame` —— **唯一可写的字段**，配套有 `UpdateSpawnFrame(MatrixFrame)`（`AgentSaveData.cs:21`）
- `AgentSpawnPointTags` 是 `public readonly string[]`
- `AgentSeed` 是 `public readonly int`

**一段可直接跑的三行自持结构体**（四个参数逐字照自 `SandBox/Missions/CheckpointMissionLogic.cs:185` 的官方唯一构造点）：

```csharp
Mat3 look = agent.LookRotation;
Vec3 pos = agent.Position;
AgentSaveData data = new AgentSaveData(agent.Character.StringId, new MatrixFrame(ref look, ref pos), agent.AgentVisuals.GetEntity().Tags, agent.Origin.Seed);
```

四个参数的真实来源依次是：`agent.Character.StringId`（要重新生成时用哪个角色）、`new MatrixFrame(ref lookRotation, ref position)`（由朝向与位置两个局部变量组装）、`agent.AgentVisuals.GetEntity().Tags`（**原生实体的标签数组**，不是 C# 集合）、`agent.Origin.Seed`（**随机种子，来自 origin 而非 agent 本身**）。最后两个是官方代码里最容易被猜错的地方。

想改重生位置就用 `UpdateSpawnFrame`，**不要试图给 `SpawnFrame` 重新赋一个新结构体再指望别的地方看到** —— 虽然字段可写，但官方流程持有的是它自己那个实例的副本。

**按官方形状抄一份自己的。** 正确的用法是把它当**格式参考**：四个字段正好对应「用谁生成」「在哪生成」「带哪些生成点标签」「随机种子是多少」，这四样是一个可复现 agent 所需的最少信息。自己定义一个同形状的类，就能得到同样的存档能力而不必碰官方结构。

**最常见的坑：这是官方内部结构体，不是扩展点。** 改了本类型的字段会同时破坏官方检查点机制和旧档兼容。这条已在「风险与边界」首条展开。

## 跨版本提示

`AgentSaveData.cs` 在 `bannerlord-1.3.0/`（78 行 / 2466 字节）与 1.3.15、1.4.6、1.4.7、1.5.3 **四棵树 `grep -v Token` 逐行 diff 后完全一致**。**字段集合、`readonly` 布局、``[SaveableField]` 1..4` 编号、构造函数参数顺序、`UpdateSpawnFrame` 签名全部跨 1.3 → 1.5 三个大版本零变化**，存档格式也保持二进制兼容。

`bannerlord-1.4.5/` 那棵树保存的是去掉了 `// Token:` 注释的精简版本，只有 55 行 / 1522 字节——**存储格式差异，不是类型被裁剪**，别据此认为 1.4.5 少了字段。

`SaveableCoreTypeDefiner` 里注册的两行（`AddStructDefinition(typeof(AgentSaveData), 1012, null)` 与 `ConstructContainerDefinition(typeof(List<AgentSaveData>))`）在这几个版本里都存在，所以**1.3.0 存的检查点尸体能一直读到 1.5.3**。

跨版本真正会变的是**消费端**：`CheckpointMissionLogic` 与 `CheckpointCampaignBehavior` 的实现细节（`OnEarlyAgentRemoved` 的过滤条件、`CanUseCheckpoint` 的判定）可能随检查点机制扩展而调整，但你依赖的 `AgentSaveData` 本身不会变。
