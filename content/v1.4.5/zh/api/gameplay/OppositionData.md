# OppositionData

**Namespace:** `StoryMode.Quests.ThirdPhase`（嵌套在 `DefeatTheConspiracyQuestBehavior` 内）
**Module:** StoryMode
**Type:** `internal class OppositionData`（嵌套于 `public class DefeatTheConspiracyQuestBehavior`）
**Base:** 无
**File:** `Bannerlord.Source/Modules.StoryMode/StoryMode/StoryMode.Quests.ThirdPhase/DefeatTheConspiracyQuestBehavior.cs`

## 概述

`OppositionData` 是「**敌对王国这一侧的全部可变进度**」的容器，声明在 `DefeatTheConspiracyQuestBehavior.cs:27-73`。它只有 4 个字段，**每个都带 `[SaveableField]`**，id 分别是 **10 / 20 / 30 / 40**（不是连续的 1-4）：`InitialWarScore`、`ReinforcedWarScore`、`QuestLog`、`LastPeaceOfferDate`。

**它自己没有任何业务方法**——除了 4 个存档读取器（`:53`/`:58`/`:63`/`:68`）与 2 个收集器（`:41`/`:46`）。所有读写都在宿主 `DefeatTheConspiracyQuest` 里进行：任务开始时 `OnStartQuest`（`:433-444`）构造并填三个字段、`:443` 存进 `_oppositionData`；运行期 `:173-179` 读分数并按「距上次和谈是否满一周」决定要不要触发和谈。

## 心智模型

把它当成**「任务进度行」**。三条推论：

第一,**四个字段里有三个是「进度」，一个是「节流器」。** `InitialWarScore` 在任务开始时算一次（`:436` 的 `CalculateWarScoreForKingdom`）并作为满分基准；`ReinforcedWarScore` 初值 0（`:437`），由 `CalculateReinforcedWarScore()`（`:446-449`）按敌国战况重算；`QuestLog` 是任务面板上的双向连续进度条（`:442` 的 `AddTwoWayContinuousLog(…, 0, 100, false)`，范围 0-100）；`LastPeaceOfferDate` 初值 `CampaignTime.Zero`（`:39`），**唯一的用途是让和谈提议每周最多触发一次**。

第二,**存档 id 从 10 起跳、间隔 10，不是 1/2/3/4。** `:29`/`:32`/`:35`/`:38`。这是 Bannerlord 主线的约定（同文件 `DefeatTheConspiracyQuest` 用 100/110，见 `:93`/`:96`），**给后续插入字段留了空位**。但**这意味着你不能按 1-4 去推断别的任务的数据结构**。

第三,**`LastPeaceOfferDate` 是唯一带初始值的字段。** `:39` 显式写 `= CampaignTime.Zero`；另外三个靠字段默认值（`float` 的 0.0、引用类型的 null）。**而 `QuestLog` 若为 null（`:49` 的 `collectedObjects.Add(QuestLog)` 会把 null 加进收集列表），读档后可能仍是 null** —— `:257`/`:307` 的 `RemoveLog(_oppositionData.QuestLog)` 会传 null 进去。

边界：**`internal` 嵌套类**，编译期不可引用；**只能由宿主 `DefeatTheConspiracyQuest` 构造**（全树唯一 `new OppositionData()` 在 `:435`）。

## 如何使用

**怎么拿到它**：**你没有公开路径。** 宿主字段 `_oppositionData` 是 `private`（`:97`），本类 `internal`，`OnStartQuest` 是 `protected override`。mod 想看敌国进度，只能读公开的任务进度条或复算 `CalculateWarScoreForKingdom`。

对应的公开面（宿主 `DefeatTheConspiracyQuest` 的进度条参数就来自 `:442`）：

```csharp
using TaleWorlds.CampaignSystem;
using TaleWorlds.CampaignSystem.Settlements;

// OppositionData.QuestLog 的 0-100 范围写死在 AddTwoWayContinuousLog(..., 0, 100, false)（:442）
// 而 InitialWarScore（:436）才是真实分数 —— 面板上的百分比是 分数 / InitialWarScore 的映射
// :174 用 InitialWarScore / 2f 作为「过半」的判定阈值（和平提议的门槛之一）
Debug.Print("进度条 0-100，真实分数在 InitialWarScore，过半阈值 = InitialWarScore / 2f", 0);
```

复现「每周最多一次和谈」的节流条件（`:177`）：

```csharp
using TaleWorlds.CampaignSystem;

// :177 的条件：不在 MapEvent、不在 SiegeEvent、主角未被俘、
//              当前分数 <= InitialWarScore / 2f、
//              LastPeaceOfferDate 距今 >= CampaignTime.DaysInWeek
bool weekElapsed = CampaignTime.Now.ElapsedDaysUntilNow >= CampaignTime.DaysInWeek;
Debug.Print("DaysInWeek = " + CampaignTime.DaysInWeek + "  是否已过一周 = " + weekElapsed, 0);
```

**用它最容易踩的一条**：**和谈提议的门槛是「当前分数 ≤ `InitialWarScore / 2f`」，不是「已完成一半」。** `:174` 先算出 `num2 = _oppositionData.InitialWarScore / 2f`，`:177` 再用 `num <= _oppositionData.InitialWarScore / 2f` 判定。**如果敌国被打得越狠 `InitialWarScore` 越难算，`InitialWarScore / 2f` 这个门槛就跟着变大** —— 也就是说**战斗越进展顺利，和谈越不容易触发**。这是设计而非 bug，但读源码不逐行看很容易误以为是「过了 50% 就能谈」。

## 风险与边界

- **`internal` 嵌套类，编译期不可引用。** 唯一 `new OppositionData()` 在 `:435`，位于 `protected override OnStartQuest()` 内。
- **存档 id 是 10/20/30/40，不是 1/2/3/4。** `:29`/`:32`/`:35`/`:38`。同文件的 `DefeatTheConspiracyQuest` 用 100/110（`:93`/`:96`），**这是留空位的约定，不是随机。**
- **只有 `LastPeaceOfferDate` 有显式初始值。** `:39`。`QuestLog` 在 `new` 之后是 null，直到 `:442` 赋值。
- **`QuestLog` 为 null 时 `:257`/`:307` 的 `RemoveLog(null)` 会传 null。** 我没有读 `RemoveLog` 的实现，**不断言它是否判空**。
- **和谈门槛是 `InitialWarScore / 2f`，不是 50%。** 见「如何使用」。
- **`ReinforcedWarScore` 初值 0 但立刻被 `:448` 覆盖。** 若 `CalculateReinforcedWarScore()` 在第一次进度计算之前没跑过，`:173` 会读到 0。
- **`protected virtual` 的收集方法可被派生类覆盖。** 本类是 `internal` 且实际不派生，**但存档系统可能依赖这个虚性**。
- **四个 `AutoGeneratedGetMemberValue*` 是代码生成产物。** 改字段时漏加方法 = 读档丢值，**且不会有编译错误**。
