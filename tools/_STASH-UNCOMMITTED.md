## B7. 提交判据（已随本会话修订，取代原合取）

原判据：
```
收 = 归属方已报交付 且 静默 >=15 分钟 且 非 stale-pin
```

**现判据（取代上面）：**
```
提交依据不是「归属方说过已交付」，是「归属方已交付 且 之后没有再被动过」。
交付声明会过期，所以「已交付」是一个**会失效的断言**，提交前必须重新核。
```

**为什么改**：「声明完了又动过」与「仍在写」是**两种不同的失效，危害一样**。
原规则只防了后者。前者更阴——它带一张「已交付」的凭据，凭据是真的，只是**过期了**。

**静默 >=15 分钟单独不够**：`tools/_NAV-BASELINE.md` 即使静默满15 分钟也不收，
因为它是 owner **自己声明尚未完成**的文件（围栏归因实验进行中）。
静默只说明它**此刻没在写**，不说明它**完成了**。

**已验证的失效实例**：
- `tools/_NAV-BASELINE.md` 声明 22,498 字节，实测 25,400，**声明后漂移 +2,902 字节**。
- 口径差异与真实漂移必须分开判：`_NAV-ARCHITECTURE.md` 实测 859 行 vs 声明 858 行、
  `-invariants` 129 vs 128、`_LINK-GATE` 345 vs 344，三处**均差1 行**，
  成因是文件以 `\n` 结尾、`split('\n').length` 多算一行——**内容与声明一致，不是漂移**。
  只有 `_NAV-BASELINE.md` 的字节差是真实漂移。

## B8. 判据的三条界（数字被实测推翻时该怎么处置）

```
· 页面内部自相矛盾（加总对不上）→ 直接修，它不需要外部信息就能被发现
· 页面自洽但归属存疑（版本 / 对象 / 基线）→ 先报不动，此时缺的是「它该跟谁比」
· 页面自洽且归属无争议，而测量结果与常识都矛盾 → 先怀疑测量，别改页面
```

第三条不是推演出来的，是撞出来的：本会话曾用 `public (float|int) (\w+)` 数属性，
它把**方法** `public float GetStat(DrivenProperty …)` 也算成了属性，于是 91 float 变成 92，
并据此差点把一个**本来正确**的计数改错。

判据归属：方法有参数列表（名字后跟 `(`），属性没有（跟 `{` 或行尾）。

| 类别 | 处理 | 例 |

## B10. 一套判据的验收方式：看它会不会自己排除掉危险项

本会话初版 checkpoint 判据是「归属方已报交付 + 静默 ≥15 分钟 + 非 stale-pin」。

跑到某一轮时出现了一个**不是我设计、而是它自己长出来的**结果：

> 候选集里静默 ≥15 分钟的条目，**恰好只剩下那三个 stale-pin 记录**——
> 而它们全在「永不收」名单上。也就是说，静默条件一旦满足，
> 候选集自动缩回到例外名单，**没有任何东西可能被误收**。

**判据与例外名单此时是自洽的，不是共存的。**

这比「排除过几次」强得多：排除次数是运气，自洽性是性质。
**验收一套判据，应该观察它会不会自己把危险项排除掉，而不是统计它排除过多少回。**
（本会话已出现五例同族错误：对象错 ×2、基线错、版本错、版本混淆——根因都是
**在比之前没确认两边说的是同一个对象**。）

## B13. 裁定里的事实会过期——引用前必须重新核

一条裁定里的事实，会在裁定写下之后过期。**裁定里带「现在 / 仍然 / 还在」这类时态的事实，引用前必须重新核一次**——尤其是它决定「收什么、不收什么」的时候。

## B15. 契约可被引用的三条（取代旧的单一「已定稿」）

```
可被引用 = ① 已宣布 rev N 定稿
         ② 此刻磁盘上文件头确实写着 rev N
         ③ 宣布之后没有再被写过
```

**① 只是一句话，②③ 是可核的事实。** 收一个契约的完整判据是三条同时成立。

**为什么 ② 不是形式**：若磁盘上是 rev 6 而宣布的是 rev 7，worker 读到的契约
与它被告知的版本不是同一份——**而这种不一致是静默的**：worker 照它读到的那份干活，
回报里写「我读的是 rev 7」，而它实际读的是 rev 6 加上 rev 7 的某个早期版本。
**所以 ② 是让「回报里写的 rev」这句话有意义的前提。**

**真正在等的是 ③**，而且要带时刻：「rev 7 自 <时刻> 起不再变更」，
时刻需能与 mtime 对上。**再宣一次「定稿」不算数**——已宣两次且两次之后仍被动过。
不给就继续等：两种情况都有确定动作，不需猜。

## B16. 三个合取项的实测覆盖（第三项**保留但尚未独立生效**）

| 合取项 | 单独挡下过 | 证据 |
|---|---|---|
| 静默 ≥15 分钟 | ✅ 多次 | 契约 1/2/4m、`_LINK-GATE` 3/3/12m、`refuted` 13m |
| 归属方已报交付 | ✅ 2 次 | `_NAV-BASELINE.md` 18m/26m、`_DEAD-MEMBER-LIST.md` 16m（**两者静默均达标**） |
| 非 stale-pin | ⚠️ **尚未独立生效** | 三个 stale-pin 文件静默全部达标，但**从未被归属方宣布交付**，拦住它们的是**第二项** |

**裁定：保留第三项，标注「尚未独立生效」。**

**理由是一个对称的陷阱，两边都要避开：**
```
因为没触发就删掉它   → 用「结果好不好」替代「设计对不对」，与当初凭想象加它同一种错
因为写「已验证」就当它有效 → 用「发生过一次」替代「它对不对」
```

> **一条守卫条款该存在的理由，是它防的那种失效形态，不是它触发过几次。**
> stale-pin 防的是「pin 在已落后的 sha 上，入库即制造一个过期锚点」——**这个形态本会话真的发生过**。
> 所以这一项防的形态是真的，只是至今没有一次**独立地**成为决定因素。

**真实的分工（经实测修正，不是「各管一类失效」）：**

```
静默      ：只在「owner 还会继续写」的情况下有意义；对刚落盘的新文件近乎无效
交付声明  ：唯一承重的那一项 —— 它挡住「没人宣布完成」，而这正是静默挡不住的那一类
stale-pin ：保留，但尚未独立生效
```

**这不是判据设计失败，是判据用在了它测不了的对象上。**

> **静默测的是「有没有人在动」，而要问的其实是「有没有人在负责」。**

- 静默对「**已交付、正在被改**」的文件有效——它能识别出声明已过期；
- 静默对「**未交付、已停笔**」的文件**会把半成品放行**——没人动它，它就一直静默。

## B17. 静默条件挡不住「刚写完但未验收」

一批新落的 nav 产物（`_nav-apply-batch*.txt` / `_nav-batch*-list.txt` / `_nav-dryrun-batch*.txt`）共10 个，**其中 7 个静默 17–35m 全部达标**，但**无任何一条线对它们发过「已交付」声明**，因此全部未收。

**原因**：文件落盘后没人动它，20 分钟后它就自动「达标」。
但**「没人动」不等于「写完了」**——一份刚落盘、还没人检查过的文件，同样会静默很久。

- 静默挡的是「正在写」
- 静默**挡不住**「刚写完但未验收」

**根本原因（B17 的延伸）：静默测的是「有没有人在动」，而要问的是「有没有人在负责」。**

- 静默挡的是「正在写」；
- 静默**挡不住**「刚写完但未验收」。

一份刚落盘、还没人检查过的文件，会安静地躺很久并自动「达标」。
**所以「静默达标」既不是完成证据，也不是安全证据**——它是**没有责任人**的证据。

**唯一承重的是交付声明**：它问的是「有没有人负责宣告完成」，而这正是静默问不出的。

**不要要求承诺落进文件。** 判据 ③ 是**一个事实**（「宣布之后有没有被写过」），
不是一句话，只能靠**时点与 mtime 对齐**核实。

> **承诺不需要自证**：它一旦写进文件，就会变成一个**可以被下一次写入静默作废**的字符串；
> 而 **mtime 对不上是藏不住的**。
> 要求承诺落进文件，是把一条判据变成另一条。

## B18. 承诺不需要自证

判据 ③（「宣布之后有没有被写过」）是**一个事实**，不是一句话，只能靠时点与 mtime 对齐核实。

> **承诺不需要自证**：它一旦写进文件，就会变成一个**可以被下一次写入静默作废**的字符串；

## B20. 单点读数 vs 序列：判据的强度常来自看序列

我曾三轮读到契约静默 `1m → 2m → 4m`，**以为那是「连续三轮被正在被写挡住」**。
**那个读法是反的。**

> 这三个数是「距上次写入已经多久」，**单调递增**。
> 若文件在被反复写，这个数会被**重置回小值**再重新爬升。
> 它一路递增，唯一解释是：**最后一次写入之后再没动过。**

**所以「持续递增」本身就是「没在写」的证据**——我观察到的是三个失败，其实是一个成功信号。

> **单次读数只能说「此刻距上次写入多久」；
> 一串单调递增的读数能说「写入已经停止」。**

**判据的强度常常来自看序列，而不是看单点**（与 §B13「裁定会过期」、§B16「结构未验证」同族）。
