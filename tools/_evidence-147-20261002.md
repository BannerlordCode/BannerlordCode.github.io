## 3. 本轮最有价值的发现：链接层级系统性缺陷

### 3.1 缺陷本体

生成器把**跨桶**链接少写了一层 `../`：

```
错：content/v1.4.7/zh/api/activitysystem/Activity.md -> ../campaign/FastModeSubModule/
对：                                                            ../../campaign/FastModeSubModule/
```

根因：本仓库链接按 **route-relative** 解析，每个页面 route 即自身目录，一个 `..` 只弹一层。从 `/api/<bucket>/<Name>/` 弹一次只回到 `/api/<bucket>/`，因此单个 `../` **只能到达同桶兄弟**。

### 3.2 证据链（不靠猜）

**(a) 权威门禁的比值指纹**

```
FILES=1803  TOTAL_LINKS=11533  BROKEN_LINKS=11513
RESOLVE_OK_FILE=9330   RESOLVE_OK_URL=20   RESOLVE_OK_BOTH=0
RESOLVE_NEITHER=2183
```

`RESOLVE_OK_FILE=9330` 对 `RESOLVE_OK_URL=20` 是**链接层级**缺陷的指纹：链接在磁盘上存在，但解析不成 route。若只看 `BROKEN_LINKS` 总数，时序问题与真实缺陷会被搅在一起。

**(b) 与已发布树对照实测约定**（不靠记忆、不靠 AGENTS.md）

| 树 | 2+ `../` 跨桶链接 | 单 `../` 却带桶名的链接 |
|---|---|---|
| 已发布 v1.4.5 zh/api | **5,215** | 203 |
| 新生成 v1.4.7 zh/api | **40** | **4,135** |

样例（已发布树，正确）：`campaign/AccompanyingCharacter.md -> ../../campaign-ext/CampaignMissionComponent`

### 3.3 按成因分类（boss 要求：分类而非总数）

| 类 | 数量 | 判定 |
|---|---|---|
| A `../` 指向尚未落盘的桶/区块 `_index.md` | 1,802 | 时序，不动 |
| B 指向尚未写出的门面页 | ~372 | 时序，不动 |
| **C 跨桶链接少一层 `../`** | **~9,330** | **系统性缺陷，改生成器** |
| D `./` dot-slash 残留 | ~9 | 低优先 |

**A+B ≈ 2,174 为时序；C ≈ 9,330 为真实缺陷。** 按 boss 口径：不在产物页面上逐条手改（会被下一次生成覆盖），只改生成器，并加 route-relative 断言门禁。

## 4. lead-2 自身工具的两次自我修正（boss 要求原样记录）

> 这两条比任何数字都重要：**一个"看起来在工作"的校验器，如果解析口径错了，它会系统性地掩盖它本该发现的那一类缺陷。**

### 修正 1：filesystem-relative 掩盖了 9,330 条系统性缺陷

第一版 `tools/_v147_verify.mjs` 用 `resolve(dirname(fromFile), href)` + `fs.existsSync` 解析链接，报出 **2,186** 条断链——看上去问题不大。实际它把 C 类 **9,330 条全部掩盖**：因为错层级的链接**作为文件确实存在**，存在性检查必然通过。

改为 route-relative 解析后，harness 报 11,513 条，与 `audit-links.mjs` 的 11,513 **完全一致**。

> **教训：本仓库的 `fs.existsSync` 不是有效链接检查。** 任何针对该站点的校验器必须 route-relative 解析，否则系统性低报。

### 修正 2：原始 `./` 计数制造幻影缺陷

统计 `](./` 出现次数时，已发布树 5,963、新树 5,544，看似"新树也有问题"。实际上这些绝大多数位于**代码围栏内**，门禁会跳过。

> **教训：原始字符串计数不是缺陷判据，只有门禁的裁决算数。** 我差一点把一个幻影缺陷报上去。

### 修正 3：未校准的校验器报出 14,548 条幻影缺陷

收尾阶段我用一段临时脚本分类断链，得出「真实缺陷 14,548 条」，与 worker-11 自报的 0 条严重冲突。**先怀疑自己的工具**，把该解析器跑在**已知为 0 断链的已发布树**上：

| 解析器 | 已发布 v1.4.5 zh/api（31,779 条链接，应为 0） |
|---|---|
| 有 bug 的版本 | **5,999 断链** ← 明显错误 |
| 修正后的版本 | **0 断链** ← 校准通过 |

bug 是 `routeOf()` 先剥掉 `.md`，又对类型名多切了 3 个字符，把每条 route 都切坏。校准通过后，同一脚本在新树上的结论从 14,548 变为 **真实缺陷 67 条**，与独立路径一致。

> **教训：校验器必须先在已知良好的基线上校准，它的数字才可采信。** 这是同一条原则的第三次出现（§4.1 filesystem-relative、§4.2 原始计数、本条未校准）。已把校准步骤固化为 `tools/_v147_verify.mjs` 的常驻步骤。

## 5. 潜伏 bug：override-first 顺序

worker-11 报告其按"entryPointDirs 先于最长前缀"实现，并称这是"唯一可行顺序"。lead-2 核查后**判此说法不成立**：

- 7 个覆写 key 在 inventory 中**各仅出现 1 次**（均在 `TaleWorlds.MountAndBlade`），故两种顺序**当前输出完全相同**——这恰恰说明它是**潜伏 bug 而非无害**。
- 一旦第二个命名空间出现同名 `Agent` 或 `Module`，override-first 就会**纯按名字**把它搬走。
- 已要求按 artifact 文档顺序实现（最长前缀 → 再按精确类型名覆写），并保留"声明桶非空"硬断言持续兜底。

> **通用教训：每当有人声称"顺序无关紧要所以无害"时，去验证那个使其无害的前提本身是否稳定。**

## 7. 跨版本链接：旧树实测为**阴性**（boss 指令 5，只报数字不改）

boss 指出 `popToSiteRoot` 这条规则在旧树里从未写过，旧版本可能有同样的少一层问题。已用校准后的解析器实测（**未修改任何旧树文件**）：

| 版本 | 页数 | 跨版本链接 | 可解析 | **断链** |
|---|---:|---:|---:|---:|
| v1.3.0 | 10,601 | 134 | 134 | **0** |
| v1.3.15 | 11,362 | 0 | 0 | **0** |
| v1.4.5 | 16,671 | 15 | 15 | **0** |

跨版本 href 形态全部为 `pops=4 tail=<version>/<lang>/<section>`，与 `popToSiteRoot == route 段数` 的规则一致。

> **结论：旧树不存在此类缺陷，无需下一波修复。** 阴性结果同样要如实上报，不得为了"有产出"而虚构问题。
