# SandBox / StoryMode / Native Reading Policy (v1.4.5)

All three areas contain code that can look like an API, but they solve different problems. Mixing official examples, story content, and decompiled engine code makes a mod depend on the wrong lifetime or internal implementation.

## One-line responsibilities

- **SandBox:** the official single-player campaign module and reference implementation for composing Behaviors, quests, menus, dialogue, and campaign rules.
- **StoryMode:** main-story content, useful for tracing story-specific registration and state flow; a normal mod should not treat story objects as general extension points.
- **Native:** the engine implementation and managed bridge, useful for rendering, scenes, physics, animation, audio, and low-level crash investigation; it is not the daily business API.

## Reading priority

```text
Read TaleWorlds.* managed APIs and task guides first
    -> read SandBox when an official implementation example is needed
    -> read StoryMode when tracing story-only registration or state
    -> trace Native only when the managed wrapper is insufficient or the crash is in the engine
```

For a Campaign feature, start with [CampaignBehaviorBase](../../api/campaign/CampaignBehaviorBase), [CampaignEvents](../../api/campaign/CampaignEvents), and [CampaignGameStarter](../../api/campaign/CampaignGameStarter). Do not bypass the managed registration boundary because SandBox contains a similar class.

## How to read each module

### SandBox: learn composition, not internal identity

SandBox is best for answering how the official game composes systems: when a Behavior is registered, when events are subscribed, how menus return to Campaign, and how an Action creates a cascade. Copy the call order and lifetime reasoning, not private fields, private SaveIds, or the identity of a particular NPC.

When changing world state, return to the matching `*Action.Apply`. When changing a calculation policy, return to [GameModels](../../api/campaign/GameModels) and [GameModelsManager](../../api/core-extra/GameModelsManager).

### StoryMode: trace specialized state, then bridge back

StoryMode Behaviors, quests, and story objects can depend on a particular story phase, flag, or save state. First map who creates, owns, saves, and ends the object; then decide whether the path can exist in a general Campaign.

If a mod only needs to observe a Hero, settlement, or campaign clock, return to [Hero](../../api/campaign/Hero), [Campaign](../../api/campaign/Campaign), and [CampaignEvents](../../api/campaign/CampaignEvents). Do not use a story Behavior as a general service locator.

### Native: understand the bridge, do not P/Invoke it directly

Native code and `IMB*` interfaces form the bridge between managed code and the engine. Managed wrappers receive function pointers during game initialization and maintain native-object lifetime; direct `[DllImport("TaleWorlds.Native.dll")]` bypasses that initialization.

For ordinary Mission logic, read [Mission](../../api/mission/Mission), [Agent](../../api/mission/Agent), and [MissionBehavior](../../api/mission/MissionBehavior) first. Trace Native only when the managed API genuinely lacks the capability or the crash stack clearly lands in Native. Even then, product code should return to an existing managed wrapper whenever possible.

## Decide whether an example is reusable

| Question | Reusable evidence | Do not carry over directly |
|----------|-------------------|----------------------------|
| Entry timing | `OnGameStart`, `CampaignGameStarter.AddBehavior`, and Mission initialization callbacks | A module's private initialization order |
| World mutation | The matching Action's `Apply` call and event result | Direct entity-field, internal-list, or private-cache writes |
| Saves | Behavior `SyncData(IDataStore)` and stable keys | AutoGenerated numbers, private SaveIds, story-only object graphs |
| Engine calls | Managed-wrapper arguments and lifetime checks | Native export addresses, function pointers, and direct P/Invoke |

## Version and risk

- v1.4.5 module boundaries and decompiled source establish facts for this version; check version differences before migrating to v1.3.15 or v1.3.0.
- SandBox/StoryMode examples may depend on module load order and do not become valid without the matching `SubModule.xml` dependencies.
- Native objects, Agents, Scenes, and UI layers have explicit lifetimes; using them after their end callback can cause null references, released handles, or native crashes.
- Route all save-related changes through the [crash and save boundaries](../crash-boundary); do not treat decompiled fields as a stable mod protocol.
