# HeroRelations

**命名空间：** `TaleWorlds.CampaignSystem`  
**模块：** `TaleWorlds.CampaignSystem`  
**类型：** `internal class HeroRelations`（嵌套于 `CharacterRelationManager` 内）  
**源文件：** `TaleWorlds.CampaignSystem/CharacterRelationManager.cs`

## 概述

`HeroRelations` 是 `CharacterRelationManager` 内部用来**保存两个英雄之间“基础个人关系值”**的存储结构，本身不是对外公开的类型（`internal`，且由外层 `CharacterRelationManager` 私有持有，mod 代码拿不到它的实例）。它用一张二级字典 `_relations`（`Dictionary<long, Dictionary<long, int>>`）来记录关系：外层键是“关系双方中 Id 较大一方”的 `Hero.Id.GetHashCode()`，内层键是“另一方”的哈希，值是整数关系数（通常范围 −100~100，0 表示无记录）。关系是**对称存储**的——`GetHashCodes` 会先把两个 Hero 排成固定顺序，所以同一对英雄只存一条数据。它只管“存储与增删”，不计算阵营修正、不广播事件；真正读取有效关系、改变关系并通知其它系统，都发生在 `Hero` 与 `ChangeRelationAction` 那一层。它在 `CharacterRelationManager` 构造时被 `new HeroRelations()` 创建，随战役存档被序列化，并在英雄死亡或读入旧版本存档时被清理。

## 心智模型

把 `HeroRelations` 想成 `CharacterRelationManager` 私有的**“关系值登记表”**，而不是你平时在玩法里看到的那个“关系”。它处在战役数据层的最底层：由 `Campaign.CharacterRelationManager` 这个单例持有，生命周期与整个 `Campaign` 一致——游戏启动时在 `Campaign` 构造函数里 `new CharacterRelationManager()`，进而 `new HeroRelations()`，读档时由 `AutoGeneratedSaveManager` 反序列化 `_relations` 并随 `Campaign` 一起重建。它**不直接挂在 `Hero` 上**，而是集中放在管理器里，用两个 Hero 的 Id 哈希做联合键来寻址。

几条必须记住的边界：

- **它存的是“基础个人关系”，不是玩法里的“有效关系”**。`HeroRelations.GetRelation` / `CharacterRelationManager.GetHeroRelation` 返回的是字典里那个原始整数；而你在 `Hero.GetRelation` 里看到的、任务/对话/AI 真正判断用的“关系”，还要再经过 `DiplomacyModel.GetEffectiveRelation` 叠加家族与王国修正。两者数值可能不同，直接读底层存储会漏掉阵营影响。
- **它不广播事件、不做合法性裁剪**。往里写值只更新字典（值为 0 时还会把该条目删掉），不会触发 `CampaignEvents.OnHeroRelationChanged`，也不会处理亲属连带。所以正常改关系必须走 `ChangeRelationAction`，由它去读旧值、计算变化量、夹紧区间，再写回并广播。
- **不要直接改它**。它连类型都是 `internal`，你本就拿不到实例；即使通过反射拿到，直接写 `_relations` 会绕过 `SetRelation` 的“0 值删除 / 对称键”逻辑和所有上层校验，极易产生坏档或读档时反序列化不一致。
- **它有清理职责**。`Remove(Hero)` 会从一个英雄死亡时，把它从所有关系对里抹掉；`ClearOldData()` 在读入早于 v1.1.0 的存档时（由 `CharacterRelationManager.AfterLoad` 触发）扫描整张表，删除那些哈希已无法对应到任何存活英雄的无效条目，防止引用到已消失的角色。

## 何时使用 / 何时不要使用

**正常使用（读）：**
- 想拿到两个英雄之间的**原始基础关系值**，且明确不需要阵营修正时，用 `CharacterRelationManager.GetHeroRelation(hero1, hero2)`（本质就是调 `HeroRelations.GetRelation`）。
- 绝大多数玩法判定要的是“有效关系”，请用 `Hero.GetRelation` / `Hero.IsEnemy` / `Hero.IsFriend`，它们内部会走 `DiplomacyModel`。

**正常变更（写）——走 Action：**
- 改变玩家与某英雄关系：`ChangeRelationAction.ApplyPlayerRelation(hero, delta)`。
- 改变任意两个英雄关系：`ChangeRelationAction.ApplyRelationChangeBetweenHeroes(heroA, heroB, delta)`（注意 `delta` 是**变化量**，内部读旧值累加后再夹紧到 [−100, 100]）。
- 仅做低层、单点写入且不关心事件/亲属连带时，可用 `Hero.SetPersonalRelation(otherHero, value)`——它仍会经 `CharacterRelationManager.SetHeroRelation` 并夹紧到 `DiplomacyModel` 的关系上下限，但**不广播 `OnHeroRelationChanged`**。只在你清楚后果时使用。

**不要使用：**
- 不要 `new HeroRelations()`，也不要把它替换进 `CharacterRelationManager`（实例由 manager 私有持有，且已注册进存档类型定义）。
- 不要直接写 `_relations` 字典或调 `SetRelation`（`internal` 且绕过所有上层逻辑）；直接改字段会让 `Hero`、`Clan`、`Kingdom`、对话与任务拿不到关系变化。
- 不要把 `CharacterRelationManager.GetHeroRelation` 的返回值当成“玩法关系”——它不含家族/王国修正，比对数值前先想清楚你要的是基础值还是有效值。
- 不要假设关系值永远在 −100~100：`HeroRelations.SetRelation` 本身不夹紧，`SetHeroRelation` 只在 `hero1 == hero2` 时断言失败，真正夹紧发生在 `ChangeRelationAction`（[−100, 100]）和 `Hero.SetPersonalRelation`（关系上下限）那一层。

## 依赖图

```text
Campaign (持有 CharacterRelationManager)
   └─ CharacterRelationManager  (public static Instance / GetHeroRelation / SetHeroRelation / RemoveHero / AfterLoad)
        └─ HeroRelations  (_relations: Dictionary<long, Dictionary<long, int>>，[SaveableField(1)])
             ├─ 键来自 Hero.Id.GetHashCode()
             ├─ 读：CharacterRelationManager.GetHeroRelation → HeroRelations.GetRelation
             ├─ 写：CharacterRelationManager.SetHeroRelation → HeroRelations.SetRelation
             └─ 清理：Remove(Hero) / ClearOldData()

上层调用方（不直接碰 HeroRelations，而是经 manager / Hero / Action）：
  Hero.GetRelation / SetPersonalRelation ─────────┐
  ChangeRelationAction.Apply* ─────────────────────┤→ CharacterRelationManager → HeroRelations
  DiplomacyModel（有效关系 / 上下限 / 系数）────────┘
  CampaignEvents.OnHeroRelationChanged（变更广播）
  SaveableCampaignTypeDefiner（类 id 31 / 186 注册）
```

- **上游 / 持有者：** [Campaign](../Campaign) 在自身构造里创建并持有 `CharacterRelationManager`，后者在构造时 `new HeroRelations()`；`AfterLoad()` 在读档后触发旧档清理。整张关系表随 `Campaign` 一起被 [SaveableFieldAttribute](../../save-system/SaveableFieldAttribute/) 机制序列化。
- **关联对象（键的来源）：** [Hero](../Hero)——`_relations` 的键是 `Hero.Id.GetHashCode()`。`Hero.GetRelation` / `Hero.SetPersonalRelation` / `Hero.IsEnemy` / `Hero.IsFriend` 都最终落到这里（示例见 [Hero](../Hero) 页面“社会关系”一节）。
- **计算层：** [DiplomacyModel](../DiplomacyModel) 决定有效关系（基础值叠加家族/王国修正）、关系上下限以及正变化的随机化系数；`ChangeRelationAction` 与 `Hero.SetPersonalRelation` 都依赖它做夹紧与“有效英雄对”解析。
- **正确变更入口：** [ChangeRelationAction](../../campaign-ext/ChangeRelationAction/) 是改关系的唯一推荐入口，会累加、夹紧并广播 `OnHeroRelationChanged`；[ChangeClanLeaderAction](../../campaign-ext/ChangeClanLeaderAction/) 在首领更替时读取旧关系设定新首领对部下的印象（`ChangeClanLeaderAction.cs:46-47`）。
- **事件：** [CampaignEvents](../CampaignEvents) 的 `OnHeroRelationChanged` 由 `ChangeRelationAction.ApplyInternal` 在写回后触发，是其它系统（UI、任务、对话标签）感知关系变化的唯一渠道。
- **家族上下文：** [Clan](../Clan) / [Kingdom](../Kingdom) 通过 `DiplomacyModel` 影响“有效关系”，但**不改变** `HeroRelations` 里存储的基础值。

## 风险

- **绕过事件链与存档一致性**：直接写 `_relations` 或调 `SetRelation`（即便你通过反射拿到实例）只动字典，不会触发 `OnHeroRelationChanged`，地图 UI、任务进度、对话标签都收不到变化；且该写入跳过了 `SetHeroRelation` 的 `hero1 != hero2` 断言与上层夹紧，可能产生非法或自环关系。
- **基础值 ≠ 有效值，造成误判**：用 `CharacterRelationManager.GetHeroRelation` 拿到的原始整数去做“敌我 / 可否联姻 / 任务通过”判定，会漏掉 `DiplomacyModel` 叠加的家族与王国修正，与玩家在界面上看到的关系不一致。需要玩法语义时用 `Hero.GetRelation`。
- **死亡英雄悬挂引用**：英雄死亡后若没清关系，`_relations` 里会留下指向已消逝角色的哈希键；`CharacterRelationCampaignBehavior` 通过 `Campaign.Current.CharacterRelationManager.RemoveHero(hero)`（`CharacterRelationCampaignBehavior.cs:88`）清理，但如果你自己绕过并重建关系表，可能残留死键导致读档时无法对应到 `AliveHeroes`（`ClearOldData` 正是为此兜底）。
- **直接改字段破坏对称键**：关系是按 `GetHashCodes` 的固定顺序（Id 较大者做外层键）对称存储的。手写键值或只删一侧会破坏“一对英雄一条记录”的约定，读时 `TryGetValue` 找不到、写时重复冗余，最终与存档不一致。
- **0 值语义**：`SetRelation` 在 `value == 0` 时会把该条目从字典里**移除**（且若外层子字典空了会一并删除外层键）。把关系“清零”和“设为 0”在这里是同一动作——若你依赖“存在但为 0”的状态，直接改字典得不到这个区分。
- **读档重建顺序**：`HeroRelations` 是 `CharacterRelationManager` 的 `[SaveableField(1)]`，随 `Campaign` 分阶段反序列化。自定义 `CampaignBehavior` 若在 `OnGameLoaded` 之前访问关系值，可能拿到未完成重建的表；应等 `AfterLoad` / 加载完成事件后再读。

## 成员说明

下面按主题列出 `HeroRelations` 的关键成员。**“用途”**指它真正持有/计算/序列化什么；**“副作用”**指调用它会改变哪些关联状态；**“何时调用”**指典型使用时机。注意它本身是 `internal`，由 `CharacterRelationManager` 私有调用，下方标出的调用方都是外层公开入口。

### 数据存储

| 成员 | 用途、副作用与时机 |
| --- | --- |
| `_relations`（`[SaveableField(1)]`，`Dictionary<long, Dictionary<long, int>>`） | 关系值的唯一权威存储。外层键 = 关系双方中 `Hero.Id` 较大者的 `GetHashCode()`，内层键 = 另一方哈希，值 = 基础个人关系整数。**这是被序列化进存档的字段**。不要直接替换或写它。 |
| `GetHashCodes(Hero, Hero)` → `(long, long)`（private） | 把两个英雄排成固定顺序：Id 较大者哈希做 `Item1`（外层键），较小者做 `Item2`（内层键）。保证“对称存储、一对英雄一条记录”。写入与读取都必须经过它，手动构造键值会破坏对称性。 |

### 查询与写入

| 成员 | 用途、副作用与时机 |
| --- | --- |
| `GetRelation(Hero, Hero)` → `int`（public） | 返回两个英雄之间的**基础**关系整数；不存在该记录时返回 `0`。**不做阵营修正、不广播事件**。经 `CharacterRelationManager.GetHeroRelation` 暴露给上层；要“有效关系”请改用 `Hero.GetRelation`。 |
| `SetRelation(Hero, Hero, int)`（public） | 写入 / 删除一条基础关系。`value != 0` 时写入（必要时创建内层字典）；`value == 0` 时从该英雄的子字典移除条目，若子字典随之变空则连外层键一起删。只动字典、不夹紧、不广播事件。经 `CharacterRelationManager.SetHeroRelation` 暴露。 |
| `Remove(Hero)`（public） | 把一个英雄从**所有**关系对里抹掉：先删外层键（该英雄作为较大 Id 方），再遍历所有内层字典删掉该英雄的哈希。英雄死亡时由 `CharacterRelationManager.RemoveHero` → 此方法进行清理，防止悬挂引用。 |

### 清理与序列化辅助

| 成员 | 用途、副作用与时机 |
| --- | --- |
| `ClearOldData()`（public） | 扫描整张关系表，删除哈希无法对应到任何 `Campaign.Current.CampaignObjectManager.AliveHeroes` 的无效条目（外层与内层各扫一遍）。**仅在读入早于 v1.1.0 的存档时**由 `CharacterRelationManager.AfterLoad` 调用，是旧档兼容的兜底清理。 |
| `AutoGeneratedInstanceCollectObjects` / `AutoGeneratedGetMemberValue_relations`（自动生成） | 由 `AutoGeneratedSaveManager` 调用，把 `_relations` 登记进存档对象收集流程并取回字段值。属于存读档基础设施，不应手动调用。 |

## 示例

### 示例 1：区分“基础关系”与“有效关系”地读取

```csharp
using TaleWorlds.CampaignSystem;

Hero heroA = Hero.MainHero;
Hero heroB = Hero.Find("hero_rival_lord");

if (heroB != null)
{
    // 底层存储值：仅两人之间的基础个人关系，不含家族/王国修正
    int baseRelation = CharacterRelationManager.GetHeroRelation(heroA, heroB);

    // 玩法有效关系：经 DiplomacyModel 叠加阵营修正后的值，任务/对话/AI 用的就是这个
    int effectiveRelation = heroA.GetRelation(heroB);

    bool isEnemy  = heroA.IsEnemy(heroB);   // 取决于 DiplomacyModel 的中立上下限
    bool isFriend = heroA.IsFriend(heroB);
}
```

`CharacterRelationManager.GetHeroRelation` 直接映射到 `HeroRelations.GetRelation` 的原始整数；`Hero.GetRelation` 才是叠加了阵营修正的“有效关系”，两者可能不同。

### 示例 2：正确改变关系（走 ChangeRelationAction）

```csharp
using TaleWorlds.CampaignSystem;
using TaleWorlds.CampaignSystem.Actions;

Hero targetLord = Hero.FindFirst(h => h.IsLord && h.MapFaction != Hero.MainHero.MapFaction);

if (targetLord != null)
{
    // 玩家与某英雄关系 +30：内部读旧值、经 DiplomacyModel 系数、夹紧到 [-100,100]，
    // 写回并广播 OnHeroRelationChanged（含亲属连带），这是唯一推荐的改动入口
    ChangeRelationAction.ApplyPlayerRelation(targetLord, 30);

    // 任意两个英雄之间的关系“变化量”（不是设成绝对值）：旧值 + (-10) 再夹紧
    Hero ally = Hero.Find("hero_ally");
    if (ally != null)
    {
        ChangeRelationAction.ApplyRelationChangeBetweenHeroes(heroA, ally, -10);
    }
}
```

切勿用 `CharacterRelationManager.SetHeroRelation` 或反射直写 `_relations` 来“优化”——那样会跳过事件广播与合法裁剪。若确实需要只更新存储值且不广播事件，可用低层的 `Hero.SetPersonalRelation`（它会经 `CharacterRelationManager.SetHeroRelation` 并夹紧到关系上下限，但仍不触发 `OnHeroRelationChanged`）。
