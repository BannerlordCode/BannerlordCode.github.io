# CampaignObjectBase

**命名空间：** TaleWorlds.CampaignSystem
**模块：** TaleWorlds.CampaignSystem
**类型：** public class CampaignObjectBase : MBObjectBase
**源文件：** Bannerlord.Source/bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem/CampaignObjectBase.cs

## 概述

该类型是战役领域里“既可被存档、又可被对象管理器按 `StringId` 检索”的一族实体的公共基类：它直接继承 `MBObjectBase`，在父类的对象图收集逻辑之上叠加了战役层对象的收集钩子，使派生对象在存档时被正确遍历引用。在本版本源中，[MobileParty](../MobileParty) 是它的直接子类；而 [Hero](../Hero)、[Clan](../Clan)、[Settlement](../Settlement)、[Kingdom](../Kingdom) 等则直接继承自 `MBObjectBase` 而非本类，因此本类更准确的定位是“需要参与战役对象图收集的那些实体”的细分基类。

## 心智模型

`CampaignObjectBase` 不是 Model，而是一层“对象基类”：它本身几乎不携带业务逻辑，核心职责是把战役世界里那些既要进存档、又要被 [MBObjectManager](../../campaign-ext/MBObjectManager) 统一登记并靠 `StringId` 检索的实体归到同一个根下。实例并非从 `Campaign.Current` 取得（那是取模型与行为的入口），而是在战役初始化时由对象系统构造、以 `StringId` 注册进 [MBObjectManager](../../campaign-ext/MBObjectManager)，运行时通过具体子类的静态集合（如 `MobileParty.All` 即 `Campaign.Current.MobileParties`）或 `MBObjectManager.Instance.GetObject(id)` 取回。它在存档期由 [SaveableCampaignTypeDefiner](../SaveableCampaignTypeDefiner) 注册为类型 id 23，并借覆写的 `AutoGeneratedInstanceCollectObjects` 把自身引用的其它战役对象加入待序列化集合。当你需要新建一个“会进存档的战役实体”时，应继承本类（或 `MBObjectBase`）并补 `[SaveableField]`；若只是想扩展规则计算，应改走 Model/Behavior，而不是往本类塞纯计算逻辑。

## 何时使用 / 何时不要使用

- **使用**：需要新建一个“要被存档、并经由对象管理器按 `StringId` 检索”的战役实体（典型如一支部队/一个可移动主体）时，继承 `CampaignObjectBase` 并为其字段标注 `[SaveableField]`，再按 [MBObjectManager](../../campaign-ext/MBObjectManager) 的登记约定注册。
- **不要使用**：不要把本类当成规则/数值的扩展点（那是 [CampaignBehaviorBase](../CampaignBehaviorBase) 与各类 `*Model` 的职责），也不要为了“算点什么”而派生它；不要把 `Campaign.Current` 当作获取本类实例的通用入口（正确入口是具体子类的静态集合或 `MBObjectManager.Instance`）；若你的新实体不需要进存档对象图，直接继承 `MBObjectBase` 即可，不必套这层基类。

## 依赖图

上游类型与系统：

- [MBObjectBase](../../core/MBObjectBase) —— 直接基类，提供 `StringId` / `Id`（`MBGUID`）与对象管理器登记能力。
- [MBObjectManager](../../campaign-ext/MBObjectManager) —— 持有并登记所有 `MBObjectBase` 派生实例，可按 `MBGUID` / `StringId` 取回。
- [Campaign](../Campaign) —— 具体战役对象（如 `MobileParty`）通过 `Campaign.Current.MobileParties` 等集合对外暴露。
- [SaveableTypeDefiner](../../save-system/SaveableTypeDefiner) —— `SaveableCampaignTypeDefiner` 的基类，定义存档类型注册机制。

下游与协同系统：

- [MobileParty](../MobileParty) —— 本版本源中唯一的直接子类，声明为 `MobileParty : CampaignObjectBase`。
- [SaveableCampaignTypeDefiner](../SaveableCampaignTypeDefiner) —— 在 `DefineClassTypes` 中以 `AddClassDefinition(typeof(CampaignObjectBase), 23)` 把本类登记进存档系统（类型 id 23）。
- [CampaignBehaviorBase](../CampaignBehaviorBase) —— 各战役行为遍历并操作派生实例（如遍历 `MobileParty.All` 推进每日逻辑）。
- [Hero](../Hero) / [Clan](../Clan) / [Settlement](../Settlement) / [Kingdom](../Kingdom) —— 同属战役层持久化实体，但本版本直接继承 `MBObjectBase`，可作为对照理解本类的细分定位。

## 风险

- **未在 MBObjectManager 登记 / StringId 重复**：派生实例若在构造后未以唯一 `StringId` 注册进 [MBObjectManager](../../campaign-ext/MBObjectManager)，`GetObject(id)` 将取回 null 或错误对象，运行时空引用；重复 `StringId` 会覆盖登记、造成对象错乱。
- **漏标 `[SaveableField]` 导致引用丢失**：派生类若新增一个指向其它战役对象（如某 `Hero`、`MobileParty`、`Settlement`）的字段却未标 `[SaveableField]`，该引用既不会被序列化、也不会被 `AutoGeneratedInstanceCollectObjects` 收集，读档后变成 null，表现为“引用凭空消失”。
- **破坏对象图收集约定**：本类靠覆写 `AutoGeneratedInstanceCollectObjects` 把引用的战役对象加入 `collectedObjects`；派生类若自行覆盖该方法却忘记调用 `base`，会导致上层引用链断裂、整片对象子图不被存档。
- **在战役加载完成前访问**：具体子类集合（如 `MobileParty.All`）与 `MBObjectManager.Instance` 在战役初始化/读档流程结束前可能为 null 或空；在 `MainMenu`、子模块加载早期调用会空引用。
- **误用 `Campaign.Current` 作为入口**：`Campaign.Current` 暴露的是模型与实体集合，并不存在本类型的统一通用入口；直接在本类型上找“取实例方法”会落空，应按具体子类走。

## 成员说明

### 存档对象图收集（本类新增）

- **`AutoGeneratedStaticCollectObjectsCampaignObjectBase(object o, List<object> collectedObjects)`**（internal static）
  - 用途：存档系统入口用的静态收集器——把任意 `object` 转型为 `CampaignObjectBase` 后，转调其实例级收集方法，把该对象引用的其它待序列化对象塞进 `collectedObjects` 列表。
  - 副作用：仅向 `collectedObjects` 追加元素，不改动任何世界状态。
  - 调用时机：由 `AutoGeneratedSaveManager` 在序列化某类型定义时作为 `CollectObjectsDelegate` 绑定调用（见 [SaveableCampaignTypeDefiner](../SaveableCampaignTypeDefiner)）。

- **`AutoGeneratedInstanceCollectObjects(List<object> collectedObjects)`**（protected override）
  - 用途：实例级对象图收集。先调用 `base.AutoGeneratedInstanceCollectObjects` 走 `MBObjectBase` 的收集逻辑，再收集本类新增引用的战役对象，确保存档遍历不漏掉派生自本类的实体。
  - 副作用：向 `collectedObjects` 追加被引用的对象；若派生类新增 `[SaveableField]` 引用，需保证该方法（自动生成）能覆盖到，否则引用不会被收集。
  - 调用时机：存档写入阶段，由 `AutoGeneratedSaveManager` 通过静态收集器间接触发。

### 继承自 MBObjectBase 的关键成员

- **`StringId`**（属性，`string`，来自 `MBObjectBase`）
  - 用途：对象在 [MBObjectManager](../../campaign-ext/MBObjectManager) 中的唯一字符串标识，是游戏数据（XML/模板）中引用该对象的键。
  - 副作用：无；写它即改变登记键，重复会导致覆盖登记。
  - 调用时机：构造/登记时设置；检索（如 `GetObject(typeName, objectName)`）与序列化定位都依赖它。

- **`Id`**（属性，`MBGUID`，来自 `MBObjectBase`）
  - 用途：对象的全局唯一标识，供 `MBObjectManager.Instance.GetObject(MBGUID)` 按 id 直接取回对象实例。
  - 副作用：无。
  - 调用时机：对象登记时由对象系统分配；存档引用与跨对象指针（如 `MobileParty` 的所属方）都通过它解析。

## 示例

遍历战役中所有由本类派生的部队实例，并读取其继承自 `MBObjectBase` 的标识：

```csharp
foreach (MobileParty party in MobileParty.All)   // MobileParty.All => Campaign.Current.MobileParties
{
    string id = party.StringId;                  // 来自 MBObjectBase
    MBGUID guid = party.Id;                       // 全局唯一标识，用于存档引用
    // party 即是 CampaignObjectBase 的一个具体派生实例
}
MobileParty mainParty = MobileParty.MainParty;   // 等价于 Campaign.Current.MainParty
```

按 `MBGUID` 从对象管理器取回一个实例并向下转型到具体子类：

```csharp
MBGUID guid = MobileParty.MainParty.Id;
MBObjectBase obj = MBObjectManager.Instance.GetObject(guid); // 返回 MBObjectBase
MobileParty sameParty = obj as MobileParty;                  // 转型到具体派生类
if (sameParty != null)
{
    // 现在可以操作这个 CampaignObjectBase 派生对象
}
```

## 怎么用

**怎么拿到。** 类型声明在 `bannerlord-1.4.5/Bannerlord.Source/bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem/CampaignObjectBase.cs:6`（`public class CampaignObjectBase : MBObjectBase`）。

**全文只有 17 行，且没有任何一个 `public` 成员。** 它的全部内容是两个自动生成的方法：`internal static void AutoGeneratedStaticCollectObjectsCampaignObjectBase(...)` 与 `protected override void AutoGeneratedInstanceCollectObjects(...)` —— 后者的方法体只有一句 `base.AutoGeneratedInstanceCollectObjects(collectedObjects);`。

**所以这是一个纯粹的存档基类，不是能用它干活的类型。** 它的作用是给存档系统提供「收集对象图」的递归入口，让派生类的字段（哪怕是嵌套的引用类型）能被遍历到。

**它唯一的实际派生者是 `MobileParty`。** `TaleWorlds.CampaignSystem.Party/MobileParty.cs:25` 是 `public sealed class MobileParty : CampaignObjectBase, ILocatable<MobileParty>, IMapPoint, ITrackableCampaignObject, ITrackableBase, IRandomOwner` —— **sealed**，所以你不能从 `MobileParty` 再往下派生；而从 `CampaignObjectBase` 直接派生等于自己实现那套存档遍历，通常没必要。

**一段可直接跑的存取读**（走 `MBObjectManager`，因为它是 `MBObjectBase` 派生）：

```csharp
MobileParty party = MBObjectManager.Instance.GetObject<MobileParty>("mobileparty_main_1");
bool alive = party != null && party.IsActive;
Debug.Print("alive = " + alive, 0);
```

**不要 `new CampaignObjectBase()` 再指望它被用上。** 那个无参构造是隐式的，new 出来的对象没有 `StringId`、不进对象管理器，是个对游戏毫无影响的孤儿。

**它没有 `SyncData` 覆写，也没有 `Serialize`。** 这与行为类（Behavior）那条线完全不同 —— Behavior 靠 `SyncData(IDataStore)` 自己存字段，而 `CampaignObjectBase` 这条线靠的是 `AutoGeneratedStaticCollectObjects` 反射遍历。**你要在派生类里加需要存档的字段时，得确认自动生成的收集器覆盖到了它，否则读档后静默归零。**

**最常见的坑：未在 `MBObjectManager` 登记 / `StringId` 重复。** 派生实例若在构造后未以唯一 `StringId` 注册进 `MBObjectManager`，`GetObject<T>(id)` 就查不到，或查到另一个对象。这条已在「风险」首条展开。
