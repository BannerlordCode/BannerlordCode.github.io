## Overview

`IMBSoundEvent` is the bridge to the **FMOD audio runtime**. It declares six members (`:10`-`:27`) with two jobs that do not look alike: register a sound file or byte buffer and receive a numeric code (`:11`, `:14`), and play an already-known code at a world position, optionally with a parameter (`:17`, `:20`, `:23`, `:26`). The file is 28 lines, the type is `internal`, and `[ScriptingInterfaceBase]` sits at `IMBSoundEvent.cs:5`.

**The single most important fact about this interface is that its creation members return an `int` that the managed wrapper throws away.** `MBSoundEvent.CreateEventFromExternalFile` is declared `public static void` (`MBSoundEvent.cs:43-46`) and forwards to `MBAPI.IMBSoundEvent.CreateEventFromExternalFile(...)` without returning the native result; `PlayEventFromSoundBuffer` likewise returns `void` (`MBSoundEvent.cs:38-41`). So a mod using only the public API of `MBSoundEvent` **never receives a sound code**, and therefore can never use the four `play_sound*` members of this interface directly.

The route that does work is a different one: `MBSoundEvent.PlaySound(string soundPath, ref SoundEventParameter, Vec3)` (`MBSoundEvent.cs:26-31`) resolves the name through `SoundEvent.GetEventIdFromString(soundPath)` (`SoundEvent.cs:47`), which belongs to `ISoundEvent` (`ISoundEvent.cs:13`) — **not** to `IMBSoundEvent` — and then plays it via the one parameter symbol this interface does expose, `PlaySoundWithParam` (`:26`).

## Mental Model

Think of it as **a broadcast desk whose patch bay is behind a locked door**. The desk itself works: you can push a fader and hear something. But the bay that would let you register a new sound file and get its channel number is wired to a cable the managed wrapper does not expose — the plug is there (`IMBSoundEvent.cs:11`, `:14`), the socket returns a number, and `MBSoundEvent.cs:38`/`:43` drop it on the floor.

The consequence is a mental model that inverts the usual one. You do **not** "create a sound, keep the id, play it later" — that is what the interface suggests and it is not available. What you actually do is **name a sound and let the runtime resolve it every time**: `SoundEvent.GetEventIdFromString` (`SoundEvent.cs:47-50`) is a lookup performed per call, not a cached registration you own.

That also removes the leak concern that the interface shape would otherwise suggest. Because there is no reachable registration step, there is nothing to leak: the `int` codes this interface hands out are produced and discarded inside the module. The real cost of the missing registration path is not a leak — it is that a mod cannot ship a sound from its own buffer and reference it by handle.

The second boundary: the parameter object is mostly internal. `SoundEventParameter` is a `public struct` with a primary constructor `(string paramName, float value)` (`SoundEventParameter.cs:7`) and a public `Update(string paramName, float value)` (`:15`), but its `ParamName` (`:9-10`) and `Value` (`:12`) fields are **`internal`**. A mod constructs it through the constructor or `Update`, and cannot read the fields back.

## How to use

**How to obtain it.** Use `public static class MBSoundEvent` (`MBSoundEvent.cs:7`), which is public and needs no detour. The interface is `internal` (`IMBSoundEvent.cs:7`) behind `internal static IMBSoundEvent IMBSoundEvent;` (`MBAPI.cs:40`), and `TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10` grants `InternalsVisibleTo` only to `TaleWorlds.MountAndBlade.AutoGenerated`, `TaleWorlds.MountAndBlade.Multiplayer` and `TaleWorlds.Generator.Bannerlord`.

**A typical use.** A mod plays a sound by its event name, which is the only path that survives the `void` return:

```csharp
using TaleWorlds.Library;
using TaleWorlds.MountAndBlade;

Agent agent = null;
foreach (Agent a in Mission.Current.AttackerTeam.ActiveAgents)
{
    agent = a;
    break;
}
if (agent == null)
{
    return;
}

Vec3 at = agent.Position;
Debug.Print("played = " + MBSoundEvent.PlaySound("event:/mymod/custom_impact", at), 0);
```

Vary the sound with a parameter object, built through its public constructor:

```csharp
using TaleWorlds.Library;
using TaleWorlds.MountAndBlade;

SoundEventParameter parameter = new SoundEventParameter("Volume", 0.4f);
Vec3 at = Mission.Current.Scene.GetLastFinalRenderCameraPosition;
Debug.Print("played = " + MBSoundEvent.PlaySound("event:/mymod/custom_impact", ref parameter, at), 0);
```

**What to watch out for.** Reaching for the registration members because the interface offers them. The instinct "register once, reuse the code" is exactly what `IMBSoundEvent.CreateEventFromExternalFile` (`:11`) invites, and it is a dead end from a mod assembly: the public wrapper returns `void` (`MBSoundEvent.cs:43`), so `int code = MBSoundEvent.CreateEventFromExternalFile(...)` **does not compile**. The consequence of working around it by calling the string overload in a hot path is a per-call name lookup through `SoundEvent.GetEventIdFromString` (`SoundEvent.cs:47`) — correct, but not free, and not the cache you thought you had.

## Risks and crash boundaries

- **A mod assembly cannot call this interface.** `internal interface IMBSoundEvent` (`IMBSoundEvent.cs:7`), `internal static` field (`MBAPI.cs:40`), `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`).
- **Both creation members return `void` at the managed boundary.** `MBSoundEvent.cs:38` and `:43`. **Writing `int code = MBSoundEvent.CreateEventFromExternalFile(...)` does not compile** — the `int` the interface returns (`IMBSoundEvent.cs:11`, `:14`) never reaches the caller.
- **`PlayEventFromSoundBuffer` is named as a play but registers** (`MBSoundEvent.cs:38`). Calling it per frame would re-register each time if it returned a handle; since it returns nothing, a mod simply cannot use it.
- **Two of four play symbols have no wrapper method.** `PlaySoundWithIntParam` (`:20`) and `PlaySoundWithStrParam` (`:23`) are absent from `MBSoundEvent.cs:9`-`:46`. Use `PlaySoundWithParam` via the wrapper.
- **`SoundEventParameter`'s fields are internal.** `ParamName` (`SoundEventParameter.cs:9-10`) and `Value` (`:12`) are both `internal`; construct it with the primary constructor (`:7`) or `Update` (`:15`), and you cannot read the values back.
- **A null `Scene` is silently accepted.** `MBSoundEvent.cs:40`, `:45` substitute `UIntPtr.Zero`, so a registered event is scoped to no scene.
- **The `bool` return is not self-describing.** All four play symbols return `bool` (`:17`, `:20`, `:23`, `:26`); this file does not state the success condition. Do not branch gameplay on it.
- **Name resolution happens per call.** The `string` overload resolves through `SoundEvent.GetEventIdFromString` (`MBSoundEvent.cs:28`, `SoundEvent.cs:47-50`) on every invocation, so a name miss costs the same as a hit.
- **Not a save participant.** No `[Serializable]`, no sync surface; sounds are local presentation. Use the mission sound path ([`IMBMission`](../IMBMission), `make_sound` at `IMBMission.cs:153`) when a sound must be predictable across peers.
