# IMBBannerlordConfig

**Namespace:** TaleWorlds.MountAndBlade
**Module:** TaleWorlds.MountAndBlade
**Type:** `internal interface IMBBannerlordConfig`
**Base:** none
**File:** `bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/IMBBannerlordConfig.cs`

## Overview

`IMBBannerlordConfig` is the smallest working bridge in this bucket: a 10-line file, one interface, **one method**. `ValidateOptions()` binds the native symbol `validate_options` (`IMBBannerlordConfig.cs:9`). That is the whole of it — no getters, no setters, no queries.

It exists because Bannerlord's settings are split across two worlds. The managed side owns [`BannerlordConfig`](../../mission-ext/BannerlordConfig), a 649-line static class full of `[ConfigProperty]`-annotated fields that it reads from and writes to the game's config file. The native side keeps its **own copy** of those same options in its own parameter system. `ValidateOptions()` is the one-way notice that says: the managed values just changed, native — please re-validate what you hold. It is called from exactly two places, and both are managed-side mutation points: at the end of `BannerlordConfig.Initialize()` (`BannerlordConfig.cs:581`) and at the end of `BannerlordConfig.Save()` (`BannerlordConfig.cs:605`).

## Mental Model

### What it is / which layer

- It is a **notification channel, not a configuration API**. Read it as a doorbell, not a dial. You cannot read an option through it and you cannot set one; all you can do is ring.
- The direction is one-way: managed writes its config, then rings this bell. Nothing comes back. `ValidateOptions()` returns `void` (`IMBBannerlordConfig.cs:9`), so the native side's VERDICT — accepted, clamped, rejected — never reaches the caller.
- It sits below the settings layer entirely. Compare [`IMBActionSet`](../IMBActionSet), which answers questions; this one asks nothing and is told nothing.

### The consequence that matters

**The wrapper is where all the value is.** [`BannerlordConfig`](../../mission-ext/BannerlordConfig) is a `public static class` (`BannerlordConfig.cs:11`) with 649 lines of public properties, and it calls the bridge itself at exactly two points. A mod therefore has complete access to the *settings surface* through public API — `BannerlordConfig` properties are public and settable — and **no access at all** to the notification that tells native the settings moved. That asymmetry is the practical consequence: you can change a setting from a mod and it will be written and saved, but the revalidation that makes native agree only runs when `BannerlordConfig.Initialize()` or `BannerlordConfig.Save()` does.

Both wrapper call sites are reachable from a mod without difficulty: `Save()` is `public static` (`BannerlordConfig.cs:588`), so calling `BannerlordConfig.Save()` from mod code does ring the bell. `Initialize()` is also `public static` (`BannerlordConfig.cs:497`), but it re-reads the config file wholesale — which is not what you want when your intent was "tell native my new value".

### What is not here

There is no `Get`, no `Set`, no `IsValid`. If you are looking for "read a Bannerlord setting through the bridge", that never existed: settings live in the managed `BannerlordConfig` properties, and native's copy is reachable only by the engine itself.

## How to use

**How to obtain it.** You cannot. The interface is `internal` (`IMBBannerlordConfig.cs:7`), the `MBAPI` field is `internal static` (`MBAPI.cs:66`), and `TaleWorlds.MountAndBlade` grants `InternalsVisibleTo` only to `TaleWorlds.MountAndBlade.AutoGenerated`, `TaleWorlds.MountAndBlade.Multiplayer` and `TaleWorlds.Generator.Bannerlord` (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). A mod assembly that writes `MBAPI.IMBBannerlordConfig.ValidateOptions()` does not compile.

The door out is [`BannerlordConfig`](../../mission-ext/BannerlordConfig), which is `public static class BannerlordConfig` (`BannerlordConfig.cs:11`) — and the door out is easy, because the useful operation here is not the notification, it is `BannerlordConfig.Save()`, which sends the notification for you.

**A typical use.** Set a documented Bannerlord option from mod code and save, which is what makes native re-validate:

```csharp
using TaleWorlds.MountAndBlade;

public static class MyModOptions
{
    public static void Apply()
    {
        // BannerlordConfig's properties are public and settable
        // (public static class at BannerlordConfig.cs:11). Setting one only
        // changes the managed copy...
        BannerlordConfig.ShowBlood = false;

        // ...and BannerlordConfig.Save() is public static (BannerlordConfig.cs:588);
        // it writes the config file and then rings validate_options at
        // BannerlordConfig.cs:605, which is what tells native to re-validate.
        BannerlordConfig.Save();
    }
}
```

Read a setting without touching the bridge at all, which is the shape most mod code actually wants:

```csharp
using TaleWorlds.MountAndBlade;

public static class MyModOptions
{
    public static int ReadBattleSize()
    {
        // Straight off the managed config surface — no bridge, no notification.
        return BannerlordConfig.BattleSize;
    }
}
```

**What to watch out for.** The most common mistake is setting a `BannerlordConfig` property and expecting native to notice. It will not, until something calls `Save()` (or `Initialize()` runs at startup). A mod that writes a property during `OnModuleGameStart` and then reads a native-derived value in the same frame sees the old number. Second, and less obvious: do **not** reach for `Initialize()` as a way to "push" your values. `Initialize()` re-reads the config file from disk (`BannerlordConfig.cs:497`), so it will overwrite the property you just set with whatever is in the file — unless the save happened first. `Save()` is the correct sequence, `Initialize()` is the wrong one.

The compile-time refusal, which is the honest demonstration for an internal bridge:

```csharp
using TaleWorlds.MountAndBlade;

// Does not compile — shown deliberately.
//   error CS0122: 'IMBBannerlordConfig' is inaccessible due to its protection level
public static class ConfigProbe
{
    public static void Poke()

        MBAPI.IMBBannerlordConfig.ValidateOptions();   // internal interface, internal field
    }
}
```

The supported substitute — one method call on the public wrapper performs the same notification:

```csharp
using TaleWorlds.MountAndBlade;

// The single legitimate reason a mod would want validate_options at all:
// make native pick up a configuration change. BannerlordConfig.Save() does it
// as a side effect at BannerlordConfig.cs:605.
public static class MyModOptions
{
    public static void ApplyAndPush(bool showBlood)
    {
        BannerlordConfig.ShowBlood = showBlood;
        BannerlordConfig.Save();   // writes the file, then rings validate_options
    }
}
```

And the wrong-but-tempting call, annotated so nobody copies it:

```csharp
using TaleWorlds.MountAndBlade;

public static class MyModOptions
{
    public static void DoNotDoThis(bool showBlood)
    {
        BannerlordConfig.ShowBlood = showBlood;
        // WRONG: Initialize() re-reads the config file (BannerlordConfig.cs:497),
        // so it overwrites the property just set with the on-disk value. The
        // notification at BannerlordConfig.cs:581 is a side effect of reading,
        // not a way to push a value to native.
        BannerlordConfig.Initialize();
    }
}
```

## Risks and crash boundaries

- **A mod assembly cannot call this interface.** `internal interface` (`IMBBannerlordConfig.cs:7`) plus `internal static MBAPI` field (`MBAPI.cs:66`) plus `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). Compile-time failure, the one friendly outcome.
- **No feedback channel.** `ValidateOptions()` is `void` (`IMBBannerlordConfig.cs:9`). If native clamps or rejects the new value, nothing surfaces to the caller and nothing throws. Do not build retry logic on the assumption that a second `Save()` would report differently.
- **Setting a property is not enough.** The managed copy changes immediately; native's copy changes only when `Save()` (`BannerlordConfig.cs:605`) or `Initialize()` (`BannerlordConfig.cs:581`) runs. A mod that reads a native-derived value in the same tick sees the old number.
- **`Initialize()` overwrites, it does not push.** It re-reads the config file (`BannerlordConfig.cs:497`) and, when any property failed to parse, calls `Save()` from inside itself (`BannerlordConfig.cs:577-580`) — which means a malformed config can cause `Initialize()` to write, then validate, then `Save()` again to validate a second time (`BannerlordConfig.cs:605`).
- **Not a save participant in the game-save sense.** It has no `[Serializable]` state; the config file it accompanies is a separate settings store, not a savegame.
- **Not thread-safe and not intended to be.** Both call sites are on the config initialization path, single-threaded by construction. Calling `Save()` from a background thread races the file write at `BannerlordConfig.cs:604`.

## Cross-Version Notes

The v1.4.5 file is 10 lines with exactly one `[EngineMethod]` binding, `validate_options`, and the same file name and single-method shape appear under the same `Bannerlord.Source/bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/` layout in the `bannerlord-1.3.0` and `bannerlord-1.3.15` trees. The native symbol string is the stable contract; the interface's C# shape is deliberately minimal and is unlikely to grow, because reading native options back is a design the engine did not choose. What *does* change between versions is the set of `BannerlordConfig` properties, and therefore which managed mutations are worth ringing this bell after. **VERIFIED MEASURED for v1.4.5** (10 lines, 1 member, `BannerlordConfig.cs:581` and `:605` call sites); the sibling version trees were not read member-by-member for this page.
