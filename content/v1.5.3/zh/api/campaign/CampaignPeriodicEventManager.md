# CampaignPeriodicEventManager

**Namespace:** TaleWorlds.CampaignSystem
**Module:** TaleWorlds.CampaignSystem
**Type:** `public class CampaignPeriodicEventManager`
**Base:** 无（内部类，由 `Campaign` 构造）
**Source:** `bannerlord-1.5.3/TaleWorlds.CampaignSystem/CampaignPeriodicEventManager.cs`

## 概述

`CampaignPeriodicEventManager` 是战役周期事件的唯一调度器。它自己几乎不暴露 public API——对外只有 `CreatePeriodicEvent` 一个静态工厂；其余 `OnTick`、`MobilePartyHourlyTick`、`TickPeriodicEvents`、`TickPartialHourlyAi` 都是 `internal`，由 [Campaign](../Campaign) 在自己的 tick 链里按固定顺序调用。你写 mod 时**不需要直接拿它**，但你需要知道它的存在，才能解释「为什么 DailyTick 没在我预想的时间触发」。

## 心智模型

它是两级调度：

**第一级：用户事件。** `Campaign.Tick()` 在 `_dt > 0f || CurrentTickCount < 3` 时调 `OnTick(dt)`，其内部 `SignalPeriodicEvents()` 只有在「距上次调度超过最小间隔」时才真正遍历 `Campaign.Current.CustomPeriodicCampaignEvents`，对每个 [MBCampaignEvent](../MBCampaignEvent) 调 `CheckUpdate()`，然后把 `isEventDeleted` 的移除掉。

**第二级：分组轮转。** 同一个 `Tick()` 里还有三条线：

- `MobilePartyHourlyTick()` → 队伍的小时级 ticker；
- `TickPeriodicEvents()`（在 `_dt > 0f` 下）→ `PeriodicHourlyTick()` + `PeriodicDailyTick()` + `PeriodicQuarterDailyTick()`，分别驱动聚落、英雄、事件等原生系统的每日/每半小时逻辑；
- `TickPartialHourlyAi()` → 商队、守军、民兵、村民等队伍的**部分小时** AI 思考（按 `DeltaHours * 0.99` 摊到多帧）。

注意顺序：`OnTick` 在 `MobilePartyHourlyTick` **之前**，而 `TickPeriodicEvents` 在它们之后。所以你在 `DailyTickEvent` 里改队伍状态，影响的是同帧后续的聚落/英雄 tick，而不是之前的队伍 tick。

**常见误用与坑**

1. `CreatePeriodicEvent` 在 `Campaign.Current == null` 时直接 NRE——它是静态方法，没有延迟初始化。
2. 以为 `OnTick` 每帧都跑。实际被 `MinimumPeriodicEventInterval` 节流，且外层还有 `_dt > 0f` 门槛。
3. 在 `TickPeriodicEvents` 派生的原生回调（如聚落每日 tick）里改聚落经济——这个回调发生在 `DailyTickEvent` 之后，会与你自己的每日逻辑产生顺序依赖。
4. 把 `DeltaHours` 当帧时间用：它是**距上次调度的小时数**，暂停时为 0。

## 成员与调用时机

- `static MBCampaignEvent CreatePeriodicEvent(CampaignTime triggerPeriod, CampaignTime initialWait)`：唯一的 public API。内部 `new MBCampaignEvent(...)` 后立刻加进 `Campaign.Current.CustomPeriodicCampaignEvents` 并返回。**必须传两个 `CampaignTime`，在战役启动完成后调用。**
- `internal void OnTick(float dt)`：由 `Campaign.Tick()` 调，转发到 `SignalPeriodicEvents()`。mod 侧看不到也不该调。
- `internal void MobilePartyHourlyTick()`：驱动 `_mobilePartyHourlyTicker.PeriodicTickSome(DeltaHours)`，即 `CampaignEvents.HourlyTickParty` 家族。
- `internal void TickPeriodicEvents()`：`PeriodicHourlyTick` + `PeriodicDailyTick` + `PeriodicQuarterDailyTick`。原生 `DailyTickEvent` / `HourlyTickEvent` / `QuarterHourlyTickEvent` 都由这条线上的 `MBCampaignEvent` 触发。
- `internal void TickPartialHourlyAi()`：分摊的队伍 AI 思考（商队/守军/民兵/村民），回调形态是 `CampaignEvents.TickPartialHourlyAi`。
- `protected virtual void AutoGeneratedInstanceCollectObjects(List<object> collectedObjects)`：存档收集钩子，把管理器内部的可序列化成员登记进去。继承它做自定义管理器时不要忘。

## 真实示例

```csharp
// 战役启动完成后注册一个自定义周期
public class MyFamineBehavior : CampaignBehaviorBase
{
    private MBCampaignEvent _daily;

    public override void RegisterEvents()
    {
        _daily = CampaignPeriodicEventManager.CreatePeriodicEvent(
            CampaignTime.Days(1f), CampaignTime.Days(0.5f));
        _daily.AddHandler(OnDay);
    }

    private void OnDay(MBCampaignEvent ev, object[] args)
    {
        Settlement town = Campaign.Current.Settlements.FirstOrDefault(s => s.Town != null);
        if (town != null)
            Debug.Print("famine check at " + town.Name + " / prosperity " + town.SettlementProsperity);
    }
}
```

## 风险与边界

- **加载顺序敏感**：`CreatePeriodicEvent` 依赖 `Campaign.Current`，而 `Campaign.Current` 在 `SetLoadingParameters` 里才被赋值。在 `MBSubModuleBase.OnGameStart` 里调用是安全的，在 `OnSubModuleLoad` 里会崩。
- **注册窗口**：事件列表在战役生命周期内一直可写（不像 behavior 那样只允许启动期添加），但读档不会保留已有 `MBCampaignEvent`——每次战役启动都要重建。
- **调用顺序即语义**：你的 `DailyTickEvent` 回调发生在原生 `PeriodicDailyTick` 之外的自有事件上；如果你的逻辑依赖「聚落今天的 prosperity 已经算完」，必须自己在回调里显式调用模型重算，否则拿到的是昨天的值。
- **最小间隔节流**：连续快速推进（快进 ×4）时，事件不是「每帧一次」而是「每最小间隔一次」，触发点由游戏时间决定。以游戏时间为唯一真值来源，不要用帧数推算间隔。
- **内部 API 不稳定**：`OnTick` / `TickPeriodicEvents` 等是 `internal`，Harmony patch 它们属于脆弱路径，跨版本升级需重新核对。

## 依赖关系

- [MBCampaignEvent](../MBCampaignEvent) — 调度器管理的对象类型，也是它对外工厂的返回值
- [Campaign](../Campaign) — 构造管理器并在 `Tick()` 里按顺序调用它的各个内部方法
- [CampaignEventDispatcher](../CampaignEventDispatcher) — 与本调度器并列在 `Tick()` 中被调用，负责把原生回调广播给 behavior
