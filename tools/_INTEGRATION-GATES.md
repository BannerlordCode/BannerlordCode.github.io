# 集成门禁规范 · 本门禁覆盖任何版本线的门禁都不覆盖的类别

> **为什么单独存在**：本会话每一条版本线的门禁都只覆盖它自己那几类。集成时若按各线清单逐项打勾，下面四类会被**系统性漏掉**——它们不在任何一线的门禁集里。
> **来源**：lead-2 与 lead-1 各自独立提出这一条；本会话四类缺陷全部实证。

---

## 0. 使用前提：门禁结论必须声明覆盖边界

> **每一次 Lead 说「全部通过」而没有同时说明「通过了哪几类、漏了哪几类」，那个「全部」就只是修辞，不是证据。**
> —— 本会话反复确认。lead-2 已写入其证据包 §0.3。

**任何一次验收报告，若只给数字不给覆盖类别，视为未验收。**

## 1. 四类「无门禁覆盖」缺陷（全部已实证，非推测）

### 1.1 纯文本里的路径陈述
- **是什么**：页面正文里写着 `` 父级：`../../../` `` 这类路径，但它**不是链接**。
- **为什么所有门禁都看不见**：`audit-links` 只检查 markdown 链接。纯文本里的路径没有任何机制能验证。
- **实证**：v1.4.6 一批 16 张类页的页脚写「父级导览位于版本根 `../../../`」，而叶子页到桶索引实际是 `../`。**断链审计全绿，因为那不是链接。**
- **怎么查**：抽读类页页脚 / 风险段 / 交叉引用段里所有反引号包裹的路径，逐条按 `linkRules` 数层数。
- **门槛**：类页页脚这一类必须 **0**。其余位置允许存在但需抽读。

### 1.2 页面是否完整列出该列的内容
- **是什么**：索引页列了 3 个链接，但实际有 5 个；或列了全部但不给数量。
- **为什么看不见**：少列不违反任何现有检查——链接都在、都能解析。
- **实证**：v1.4.7 有 6 个索引页列了内容但不给页数，读者看到三条链接无法判断「三条就是全部」还是「页面没写完」。
- **怎么查**：索引页的链接集合 vs 目录实际文件数，比对。
- **门槛**：索引页给了链接但没给数量 → **0**。

### 1.3 页面声称的规模是否仍然成立
- **是什么**：页面写「本版本 1,795 个类页面」，磁盘上只有 41 个。
- **为什么看不见**：只要不自相矛盾，「过时」与「错」在任何检查下不可区分。
- **实证**：本会话出现过 **1,795 vs 41**、**190 vs 5**、**321 vs 0** 三类陈旧声称。**断链审计全绿、计数检查全绿。**
- **怎么查**：抽出页面里的每个规模数字，与磁盘实测比对；树在写时**只报告不修**（见 §3）。
- **门槛**：入口页与桶索引的规模数字与磁盘终值一致。

### 1.4 域从树里消失而无标记
- **是什么**：一个域被清理掉了，链接删了，**名字也从散文里消失了**。读者不知道它曾经存在。
- **为什么看不见**：这是最隐蔽的一类。**「那个域从来就没出现过」在任何计数口径下都成立**——断链 0、陈旧计数 0、orphan 0，全绿。
- **实证**：v1.4.7 撤回后 `Localization` 与 `StoryMode` 两个域被删链接时一并删掉了名字，而这两个域在 1.4.6 / 1.4.7 / 1.5.3 三棵树里都缺。**它看起来像清理，实际是双重缺陷。**
- **怎么查**：**清理/撤回之后，重新检查「曾经被提及、现在完全不再被提及」的项**——不要只查断链。
- **门槛**：域的消失必须留下标记（在散文里被点名并说明状态）。

## 3. 静止性纪律

> **树在被写入时测得的任何数字都只是瞬时采样，不得作为验收证据。**

- 任何一次验收前，确认目标树静止。
- **规模声明尤其危险**：树在动时写入的数字，会在一小时内静默失效，且**所有门禁保持绿色**。
- 本会话 lead-2 因此拒绝在 worker-40 交付前落地 §0 规模句，**这个拒绝是对的**。

## 4. 阳性对照：每个检查器都要先自证

| 检查器 | 已知对照组 | 通过标准 |
|---|---|---|
| 分类器 | `_withdrawn/`（已知生成页）+ v1.4.6 deep_pass（已知手写页） | 两组命中率差必须显著；否则该信号判据失效 |
| 反虚构门禁 | 6 个已知真实 API（`AddBehavior` 等） | 必须显示 `positive control: 6/6`，**显示 0 按 exit 2 处理** |
| 链接审计 | 已知断链样本 | 自建 fixture 跑通 |
| 散文反查 | — | 必须区分「否定句里的假名」与「正文里的假名」；**纠正写法是不提假名** |

### 🔴 反虚构门禁的已知边界：它验证「名字存在」，不验证「名字属于该类型」

**当前实现**用裸词测试：`new RegExp('\\b' + id + '\\b').test(corpus)`。

**后果**（lead-2 实测）：`Agent.MortalityState.Alive` 在代码块里、门禁完全看得见，却通过了——因为 `\bAlive\b` 在整个 1.4.7 树里命中 2 处（`EncyclopediaHeroPage` 与一条 `NetworkMessages` 字符串），**都不是枚举成员**。门禁回答的是「这个名字在树里某处存在吗」，不是「它是它所挂载的那个类型的成员吗」。

| 错误类型 | 门禁能否抓住 |
|---|---|
| 完全虚构的名字 | ✅ 抓得住（本会话 12 条都是这类）|
| **真实名字挂在错误的接收者上** | ❌ **静默通过** |

**两个方向（先记录、后修）**
- **记录**：已在此登记为已知边界，任何引用该门禁的验收都必须连同这一条一起读。
- **修复**：按 `Type.Member` 解析到声明类型，而不是在语料里 grep 裸词。

> **不要为了让门禁变绿而调它的判据。** 本会话实例：`readdirSync` 缺 `withFileTypes`、`'\b'` 在 JS 里是退格符、漏 `native-1.3.15-src`（点不在 `\w`）——三次都是让检测器看起来正常，而不是让检测器正确。

### 🔴 另一类边界：扩展方法
`meta.GetApplicationVersion()` 的声明在 `MetaDataExtensions.cs`，不在 `MetaData` 里。**按「在 MetaData.cs 里找不到成员」而判它是虚构，会把一个正确的页面改错。** 本会话一个 worker 正是这样得出错误更正，由 lead-2 读源码推翻。

> **报出「数量大得惊人且符合预期方向」的结果时，先假设自己坏了。**
> 本会话实例：检查器因 `'\b'` 在 JS 里是退格符而非词边界，误报「1,457 处虚构 API」。

## 5. 门禁自身的门禁

**「门禁全绿」这句话本身也需要门禁。**具体做法：

- 每次改门禁脚本后，**先在已知损坏的 fixture 上跑一遍**，确认它会红。
- 门禁脚本报 0 之前，先确认它的**阳性对照**在跑（见 §4），并额外确认它**在已知良品上不会误报**（抑制性对照）——后者最容易被跳过，也最容易藏住压低方向的缺陷。
- 本会话实例：`_scan_stale_counts.mjs` 曾长期报 0 而不报错，因为它的正则漏了 `native-1.3.15-src`（点不在 `\w` 里）。

### 🔴 压低方向的 bug 藏在「我想相信的结论」里

**这是最危险的一类检测器缺陷，因为它伪装成最好的结果。**

实测（本次审计）：一个「骨架 vs 有人写的内容」检测器声称 36,519 页里只有 **4 页**有真实内容。把该检测器强制跑在 **227 页人读确认为手写的已知真值**上：

```
检测器判「有人写了内容」× 真值手写 = 2 / 227 = 0.9%
```

**它几乎认不出手写页。** 所以「例外极少」不是干净的语料，是一个**失明的检测器**。修正后 `TP=227 FN=0 FP=20 TN=0`。

**规则：**
1. **虚高的 bug 会被发现**——它把你要压小的数抬高，与目标方向相反，一眼可辨。
2. **压低的 bug 藏在你想相信的结论里**——它让数字正好落在你希望的方向上。
3. **任何「例外很少 / 很干净 / 零问题」的结论，必须先在已知阳性上跑过。** 没跑过的检测器不是测量结果，是未被检查的输出。
4. **决定性的那一格永远是「检测器说无 × 真值有」**，不是「检测器说有 × 真值有」。

### 🔴 `TN=0` 意味着三种状态，不是两种

当检测器的真负例为 0，它**几乎从不判「干净」**。此时：
```
找到人工撰写段落    → 进例外/混合区，附原文
没找到人工撰写段落  → 未验证干净，属「未分类」，不是「已审通过」
方法根本没覆盖      → 第三个状态，与上面两者都不同
```
**把后两者渲染成「已审通过」，与「标记缺失 ≠ 干净」是同一个不对称在另一层的复现**：没有证据，不等于有证据的反面。两处混用，受害的都是绝大多数页面。

### 🔴 闸门必须至少有一次「在真实 bug 存活时失败」的证据

否则无法区分「闸门有效」与「闸门根本没接线」。

本会话的正面实例：worker 的 `--selftest` 在一个 `String.match()` 带 `/g` 导致段落剥离从未发生的 bug 存活期间**真的失败了（exit 1）**。这是本会话第一次出现闸门在真实 bug 上被证明有效，而不只是「闸门存在」。

同形态的反面实例（本文件自身）：一规范编辑因精确文本匹配失败而**从未落盘**，而作者以为它成功了。**没有验证的写入，等于没有写入。**

### 🔴 「settled / idle」不等于完成

收到完成状态时**先核对磁盘产物**，不要相信状态消息。

本会话两次真实丢失：227 页的判读、56 条判定，都只存在于 worker 上下文，运行结束而产物从未落盘。**判断对了但没写下来，等于没做。**

配套做法：**每判一页立即追写一行**，不要攒到最后批量写。worker-59 自承曾把结果积累在 `/tmp` 而非仓库文件——那在进程结束时就是零。

### 🔴 引用必须能原样找到 —— 重建过的引用比编造的更危险

```
编造的引用   → 复核时**响亮地失败**  → 好
重建的引用   → 复核时**扫一眼就通过**  → 腐蚀同一文件里其余全部引用
```

实例：某 worker 报「104 条引用全部逐字核对，0 失败」，实际 107/108 命中。那一条**不是编造**——文字是真的、判定也是对的，它只是**重建了强调标记**（把句中片段包进了 `**`，而原文的粗体属于 `**顺序为什么重要**`）。

**校验口径**：`file.includes(quote)`，**不做空白折叠、不去反引号、不折叠大小写**。任何规范化都会让重建的引用通过。

**结构性做法**：只记录一个短**锚串**，由脚本从磁盘抽取整句——**引用是构造上逐字的，不是转录的。**

### 🔴🔴 校验器不得有归一化回退分支（析取结构）

```javascript
// ❌ 致命：第二个分支是归一化测试，它永远不会失败
if (text.includes(quote) || text.includes(quote.replace(/\*\*/g, ''))) ok = true;

// ✅ 只有精确子串
if (text.includes(quote)) ok = true;
```

**一个带归一化回退的校验器，在结构上无法发现它要检测的那类缺陷**——归一化分支对任何词句存在的引用都返回 true，于是把「重建」洗成「通过」。

本会话实例：某 worker 报「104 条引用全部逐字核对，**0 失败**」，实际 107/108 命中。它自己定位的根因比我看到的更深一层：**缺陷不在标签，在校验器。**

> **一个从未失败过的校验器，与一个没接线的校验器，输出完全一样。**
> 「0 failures」必须先回答：**它有没有可能失败过？**

### 🔴 产物自述「它做了什么」必须与磁盘事实对账

> **搬迁类操作必须同时给出两边的证据：源已改 + 目标已建。只有一边，就是没搬。**

本会话实例：`tools/_v146_campaign_census.md` 头部自述

> 「它**曾经是** `content/v1.4.6/zh/api/campaign/_index.md` 的正文……2026-10-03 **整段原样搬到这里**，数据一个字节都没改。」

实测：

```
_index.md   HEAD 99,981B   disk 99,981B   byte-identical = TRUE
「## 尚未撰写的清单（567 个）」仍在 _index.md 第 85 行，567 条仍在
census 里也有 567 条  ->  两处并存 = 纯复制，源从未被改
```

**一份文件自称做过一次没发生过的迁移。**这比「无用产物」严重：下一个人读它，会以为 `_index.md` 已经清过一遍，于是不再核对真实状态。而它自己就写着「不要信这份文件，请重新现算」——**它自己就是那份没被清掉的重复。**

**规则**

1. **搬迁 / 拆分产物必须对账**：源是否真的少了、目标是否真的多了，两边都要看字节数或条目数。
2. **产物头部对自身来源的陈述属于待核验事实**，不是权威。
3. **删此类文件前先确认无引用**（本例全仓 grep 0 引用 + untracked，删除零风险）。

### 🔴 非平凡 recipe 的作者，必须先让它失败一次

> **事后全树扫只能告诉你发生过，不能防止再发生。正确防线是作者当场验。**

本会话实例：某 worker 的计数 recipe 用了 `grep -E '\t'` —— POSIX ERE **不解释 `\t`**，该写法在本 locale 下无效；本 locale 的 `grep -P` 也不可用。**两个坑的共同点是「不报错」**：不报错意味着不会有人发现，只会静默给出 0 命中或全命中。

**为什么它没造成损失**：该 worker 自己发现 recipe 不生效、改用 `awk`，并**用同一份 recipe 复现了此前发布的数字**。**没有证据表明这个写法造成过任何错误结论**——所以全树扫的价值是**排除**而非止损，不值得为它占一个 worker 槽位。

**规则**

1. **任何非平凡的计数 / 匹配 / 抽取 recipe，作者必须先在自己的目标上验证它会失败一次（阴性对照），再用于他人数据。**
2. **换工具（grep→awk）后必须用同一份输入复现已发布的数字**，否则「换工具」本身就引入一个未验证变更。

### 🔴 差集是候选集，不是待办清单；清单形态要看分组

> **「某桶有 N 个类型没进索引」永远只允许导出一个动作：披露覆盖状态。不允许导出「把它们列进去」。**

本会话险些发生的滑坡：仪器报 `campaign MISSING=34`，若据此把 34 条补进索引，就是**往 `content/` 里塞机器生成的清单**——正是 3.6 万页撤回的那个口子。

**清单形态的硬判据（两条都要满足才算清单）**

```
1. 条目行内除名称与破折号外没有任何解释性文字    -> bare entry
2. 缺少分组导语（每组没有命名空间 / 职责域与条数说明）
```

实测 `campaign`：567 条、**bare=0**、带解释 567/567、带 `✅ .cs` 路径 566/567、分组 46（平均每组 12.3 条）→ **不是 dump，是带出处的分组清单**，与 `viewmodel`(28)/`sandbox`(19)/`storymode`(17) 同形态，**不动**。

**推论一**：`sandbox`(19) 因「不是清单形态」而不动，`campaign`(567) 就没有理由仅因条数多被搬走。**这一刀本来就不该落。**

**推论二**：真实取舍不是「形态对不对」，而是**「567 条带反查的职责说明留在 `content/` 里，是为读者可 grep，还是为控制单页体积」**——理由必须写后者，不能写前者。

**推论三**：一条用来**排除**清单形态的判据，不能被当成**定罪**依据。`campaign` 通过了它 → 前提不成立 → 基于该前提的裁定作废。

### 🔴 「页面上没有指向不存在目标的承诺」

> **索引页承诺了内容却零类页，比没有索引更糟——死胡同比死链更伤。**

9 个桶有 `_index.md` 但零类页。处置形态：说清桶的职责（源码核实）+ 如实写「当前 0 张类页」+ 给出可复跑查法 + 指向确实存在的页。**未撰写的一律反引号纯文本，不建占位页。**

无类页可对照时，**逐名 `grep -w` 是唯一防线**；且不得把「没搜到」写成「不存在」（见上）。

### 🔴 样本含未判定项时的比例 ≠ 判定完成后的比例

两者**不是同一个量**，不可互相解读。

```
在 unsure 存在时算出的比例   →  暂定值，只能连同 unsure 占比一起引用
在 unsure 解决后的比例     →  最终值
```

**禁止：把 unsure 默默当成某一类的补集。**

本会话实例：某分片当时为 `119 生成 / 67 手写 / 41 unsure`，被读成「119/186 = 63.9% 生成」。而 41 条解决后实际为 **`120 生成 / 107 手写 / unsure 0`，即 52.9% 生成 / 47.1% 手写**。**从「多数生成骨架」翻到「差不多对半」——两句话对处置紧迫性完全不同，而那 63.9% 已被推翻。**

**为什么难自查**：错误的两个方向都出现过——本次偏「更严重」，此前一次偏「更少」。**与「虚高 / 压低」是同一族：让数字落在你已有倾向的那一侧。**

**引用规则**：任何带抽样的比例，必须同时给出 **(a) 样本量占总体比例**（例：227/2,022 = 11.2%）**(b) 是否加权分层** **(c) unsure 占比**。缺任一项，该比例只能用于排序，不能用于处置决策。

### 🔴 循环论证：验证集与被验证对象同源

> **任何结论，若其验证输入与结论本身来自同一来源，它就不构成验证。**

**典型形态：拿自己的 fixture 噪声去填 allowlist，再宣布「通过」**——allowlist 让检查通过，而 allowlist 是用同一批数据构造的。

本会话两次独立出现：

1. 某 worker 的「M3 达标」是自己用 fixture 里的噪声名填 allowlist 得到的。它**没有拿一个漂亮的数字收工，而是质疑自己的胜利**，转而问真正该问的问题：**真实语料需要多少条 allowlist**。
2. 另一次是**疑似**循环：一条「1,062 页是人写深页」的结论与「F7/F8 data-carrier 模板族 = 1,062」**同一个数、两个无关含义**。若前者其实是在数后者那个模板族，那它根本没有在测量人工深度。**待查；若坐实则该结论作废。**

**症状识别**：同一数字同时出现在两个语义无关的地方。**一个同时意味着两件事的数字，不是数字，是两个互相污染的结论。**

**规则**：结论的验证集必须**独立于**产出该结论的过程构造。发现同一数字复用于两个语义时，先查循环，再谈结论。

### 🔴 校验脚本里不得出现写死的期望数字

> **期望值必须由同一份数据算出并打印出来，否则读者分不清「验证通过」与「期望值本来就是我自己填的」。**

本会话三次，同一形态 —— **用自己的输出当自己的验证**：
1. worker-55 的白名单照自己的阴性样本写 → 阴性 0/20，看着完美
2. worker-61 的 allowlist 用自己的 fixture 填 → M3「达标」是自己凑出来的
3. worker-66 的校验脚本把展示数字写死 `4737`，实际算出 335 / 0 —— **校验永远通过**

**规则**：校验脚本的每个期望值要么由数据现算并打印，要么写明来源；**写死的字面量一律视为未验证。**

### 🔴 一个尺的盲区要写下来，而不是留着

worker-66 修完仪器 `EXTRA=3`，且证实其中一条是真命中：`FormationConfiguration` 是 `MissionOrderVM` 里的嵌套 `public struct`，而仪器**按顶层算，所以看不见嵌套类型**。

**这条本身比 `EXTRA=3` 更有价值**：它把盲区从「未知」变成「已知且被记录」。
**规则**：交付仪器时必须附一份「本尺测不到什么」的清单。**一个不声明盲区的仪器，会让人以为它测过了。**

### 🔴 报告人要给结论，不要只给交接

worker-68 第一版报「2,516 条断链」，自查时自己推翻（Zola 按输出 permalink 解析，相对链接原样输出），改正后是 0。lead-1 据此说「结论翻转、问题可能是导航缺条目」——**方向对，但下得太早**，因为它当时只拿着 worker-68 的第一版。

lead-1 的自我批评是对的：**标了「未复核」不够，措辞本身已经预设了方向。**

**规则**：
- 中间结论落地前，下游只许写「已举证、待复核」，不许写「大概如此」这类带方向的措辞
- 一次报告被自己的作者推翻时，**先确认推翻已落地再往下传**，不要让下游继承一个已作废的方向

### 🔴 「没搜到」不是「不存在」——尤其当搜索本身有界

> **把一次搜索的失败当成世界的性质，是内容错误里最贵的一种：它让读者不去建那个页。**

本会话本批连出三次，同一形态：
```
1. viewmodel/_index.md  「在 bannerlord-1.4.6/ 全树搜索，这个类型不存在」
   实测：存在。TaleWorlds.Core.ViewModelCollection/ControlCharacterCreationStage.cs
   根因：用 /1（按命名空间限定）搜，漏掉了根命名空间下的声明
2. StoryModeGauntletUISubModule  在 1.4.6 命中 0
3. 更早的 835 / 1,838 —— 数字本身就来自有界的枚举
```
**Boss 也犯过一次（记下来）**：核实上述类型时，walk 写死 `depth<=8`，扫出 11,376 个 `.cs`；树里实际是 **11,385**（depth<=14 才是全量）——**一个有界搜索被当成了穷尽搜索，差 9 个文件。**

**规则**：
1. **任何「不存在/没有/未见」句，必须同时给出搜索的边界**（搜了哪些目录、跳过了什么、按什么过滤）。没有边界的否定断言 = 不可复核的断言。
2. **有界的 walk 必须报边界。** 设了深度上限、跳过了目录、用了文件类型过滤 —— 任何一项都要出现在结论旁边，否则读者无法判断结论的适用范围。
3. **自己先核一遍再采信别人的反证。** 「未搜到」是弱证据；确认搜索覆盖了声明所在的那个命名空间，它才变成强证据。

**为什么这条比断链贵**：断链会报错，读者立刻知道；「这个类型不存在」是**看起来完整的知识**，会让读者跳过整块工作，且不会有人来纠正。

### 🔴 「从未失败过」的反向：从不命中的检测器也可能是模式写窄了

```从不报错 的闸门   → 可能是死代码，也可能是正确的      —— 无法区分
从不命中 的检测器 → 可能是写窄了，也可能是真的没有   —— 同样无法区分
```

**两个方向都产出自信的错误数，而且都不会自己暴露。**

本会话三个字符串各死一次：
```
派单给的 `a public class in`        → 0 次命中（串本身不存在于本树）
我漏掉的 `战役动作` 变体           → 漏 93 页
lead-5 用的 `/自动生成/` 宽正则     → 6 个假命中（误伤「讨论生成」的手写页）
```

**实测结论**：标记在人手写页上的真实假阳性 = **0**；140 页生成页上的召回 = **0**。

**所以标记的定性是：它标识某一条特定生成器血脉，不是「生成」这件事。** 这两条 0 是对称的——**它既不误伤手写页，也几乎不抓到生成页**，因此**不能作为分类信号，只能作为「哪条血脉」的标签**。

**规则：判定一个检测器是否可用，必须同时测两个方向。** 只报「零假阳性」的检测器，和只报「零漏报」的检测器，都不足以支撑分类决策。

### 🔴 标定集必须覆盖规则的每一条轴

> **在单一语言的 3 页上标定，永远测不出只在该语言成立的规则 —— 标定集与规则共享同一个缺陷，于是检验空转通过。**

本会话实测：一条「看起来只在少语言上触发」的规则，命中率
```
英文  15.7%（116 / 741）
中文  74.4%（945 / 1,271）
```
**七个触发标题全是中文，对 103 个英文页一次都不触发。**

**危险不在数错，在方向**：漏检意味着「英文手写深页」进不了「不要删」护栏集——而那恰好是重写清扫最容易扫走的一批。**所以「命中数偏低」会从安全偏差转成危险偏差。**

必须覆盖的轴：**语言 · 文件扩展名 · 路径形态 · 体积层**。本次反复丢失的 `native-1.3.15-src`（带点目录）正是路径形态这一轴。

**推论**：`1,061` 是语言偏差的**下界**，因此 do-not-delete 护栏必须宽到 **2,012**。**用护栏自身的触发条件推出的护栏宽度，是循环的。**

### 🔴 整洁的解释性故事与整洁的 bug 一样有诱惑力

本会话实例：某个「循环论证」假设听起来完全合理，而**若交叉表恰好返回了支持它的结果，它就会宣告整个结论 void，而结论会是错的**。实际交叉表推翻了它 —— 真因是一个转录错误（1,062 被写进了另一行，真实值 1,085）。

> **错误的两个方向都能讲成一个整洁的故事：**
> 「数字大得可疑」→ 追问 → 找到 bug（对）
> 「这个结论不干净」→ 宣布 void → 杀掉真发现（错）

**所以交叉表的结果要先问「它是否与我的假设吻合」**。吻合的交叉表不比不吻合的更可信 —— **吻合可能只是我的假设把我的观测结果预测出来了。**

### 🔴 分辨率必须大于待测量

> **一个分片的误差带比它要回答的差距还宽，那这个分片就不能回答那个问题。**

本会话实测：某分片的点估计 52.9%，自身 95% Wilson 区间宽度 **12.9 个百分点**；而它被用来分辨的「52.9% vs 47.1%」只有 **5.8 个百分点**。**误差带是要解决差距的 2.2 倍。**

**同页上的系统性偏差，不是抽样噪声。** 两名读者盲读完全相同的 40 页，生成率 47.5% vs 28.2%，**差 19.3 个百分点，8 处分歧全部单向，无一处反方向**。两个独立样本的置信区间**不相交**：

```
分片样本     120/227 = 52.9%   95% CI  46.4 .. 59.3
证伪样本      17/63  = 27.0%   95% CI  17.6 .. 39.0
```

**结论写法**：不说「A 已下调为 B」，而说**「未定，两个区间不相交，差异源于方法分歧」**。同时利用**偏差方向**：本例偏差指向「过多判为生成」，因此安全姿态是**不放进重写清单**——修正后只会更多手写，不会更少。

**规则**：引用一个数去分辨另两个数之前，先比较「前者的不确定度」与「后者的差距」。前者更大时，前者不能作为判据。

### 🔴 样本构成偏离总体，则样本无法估计总体

> **读了 227 页不等于有 227 页的证据。若抽样构成与总体构成不符，样本量再大也无意义。**

本会话实测：
```
候选总体 2,239 页   prose 153 (6.8%)     api 2,086 (93.2%)
实际样本   227 页    prose 140 (61.7%)   api    87 (38.3%)
→ prose 被过度代表 9.03 倍
```
而分层覆盖在最重的两层上几乎为零：
```
体积层    样本 n   总体页数   样本判生成率
3-8KB        1        718      100%   ← n=1
8-20KB      10        850        0%   ← n=10
这两层合计 1,568 页 = api 总体的 75%，只由 11 页样本支撑
```
**100%（n=1）与 0%（n=10）都是纯噪声。**

**规则**：
1. **加权可以提高命中率，但加权后不得把该样本的比例外推到总体。** 加权估计的是「被加权那一层」，不是总体。
2. **任何分层必须报 `样本占比 vs 总体占比`**，偏差超过阈值即不可外推。
3. **结论是「不可估计」而不是「偏低」**——「偏低」暗示有个真实值，只是没测准。

### 🔴 风险必须双向报告

本次同时存在两个**方向相反**的风险，只报一个会让读者以为风险只有一侧：
```
多判为生成  217 页方言自述被总体定义排除 -> 沉默漏网（漏报）
多判为手写  8 处分歧全部单向 -> 系统性偏差（误报）
```
**队列必须同时列出两侧及其数量。** 单侧报告会让处置方向被误判——本次若只报「多判为生成」是保护性的，就会掩盖真正的漏网。

### 🔴 差额必须先归因，再命名

> **“过期”“缺失”“落后”都是结论，不是观测。在把一个差额命名为某个故障之前，必须先枚举所有可能来源并逐个排除。**

本会话实测（我自己的错）：我看到 inventory 记 `csFilesScanned=11295`、而 `find` 得 11385，就断言“inventory 过期 90 个文件”，并据此派单。实际是：
```
全树 .cs                11385
Properties/**/*.cs        90   （全部 AssemblyInfo.cs）
  其中声明类型的           0
inventory 扫描         11295   （walkCs 按目录名跳 Properties|obj|bin）
11295 + 90 = 11385  ← 精确相等
```
**不是过期，是口径差**——inventory 从未包含过 `Properties/`。

**规则**：
1. **差额先归因，再命名。** 至少检查：口径差异 / 时间差 / 过滤规则差 / 真实损坏。命名在前会导致把“口径”改成“失效”。
2. **不标记未损坏的东西为失效。** 正确处置是重新生成 + 写明口径；错误处置是打 `_stale` 标记——**那等于宣称一个没坏的东西坏了**，并让下一个人重新调查一遍。
3. **把口径写进产物本身**（如 `csFilesScannedScope` 字段），而不是只写在报告里。口径差异若只存在于叙述中，每次重新生成都会重新引发一次调查。

### 🔴 只写 tools/ 也不安全

> **一个工具只要读 `content/`，就可能把别人的在飞状态记录成事实。**

实测：重生成 `_v146_tree-spec.*` 时，“看着只写 `tools/`、安全”——但它读取 `content/` 目录状态，把另一个 worker 的半成品（`indexEn: true→false` 横跨 19 个桶、`handwrittenDeep 31→32`）烤进了产物。已从备份完整还原。

**规则**：
1. 产物若派生自 `content/`，则其生成时机必须避开他人写入期；不确定则不生成。
2. **“我写的路径在别处”不是安全判据，输入路径才是。**
3. **发现烤入瞬时状态就回滚，不要顺手提交。**

### 🔴 「从未失败过」不是证据

被证明有效的闸门需要**至少一次在真实 bug 存活时的失败记录**。一个从未报错的校验器既可能是正确的，也可能是死代码——**两者输出相同**。

本会话的正面实例：worker 的 `--selftest` 在 `String.match()` 带 `/g` 导致段落剥离从未发生的 bug 存活期间**真的 exit 1**。

### 🔴 检测器误差的方向不对称 —— 必须在设计文档里写明

```
一页被误排除在重写队列外 → 浪费工时，可恢复，安全
一页被误包含进重写队列   → 销毁人手写的内容，不可恢复
```

**因此检测器应当刻意偏向「过度包含」。** 假阳性率非零是**被接受的代价，不是需要优化掉的缺陷**。

**为什么必须写下来**：一个 7.4% 的假阳性率，**不写理由时读起来像粗心**；写明「这是不对称下的正确选择」之后，它读起来是设计。**下一个人看到它会想去「修好」，而那正是销毁的方向。**

### 🔴 两种 bug 的可发现性不同

| 方向 | 表现 | 如何被发现 |
|---|---|---|
| **虚高** | 把你要压小的数抬高 | 数字异常，一眼可辨 |
| **压低** | 让数字落在你希望的方向 | **藏在一个令人安心的数里** |

**两者都只靠「有东西断言了预期」才会浮出来** —— 一个闸门，或一个看起来不对的数字。

本会话第九次该族事故（第二次在压低方向）：`\*`-in-filter 缺陷**压掉了以 `**bold**` 开头的真实人工段落** —— 即「把好内容判成骨架」，**销毁方向**。worker 是在闸门失败时抓到的，**不是因为数字看起来不对**。

### 🔴 汇总数字的可信度由负对照决定，与样本量无关

```
混淆矩阵的负对照格为空  →  该检测器的任何汇总数字都是未验证的
                            无论它测了 227 页还是 36,000 页
```

实例：某检测器报 `TP=227 FN=0 FP=20 TN=0`，读起来像完美。但那 20 个真值全属另一种形态，而它**即将判定的 24,885 页总体从未被测过**。

**决定性的那一格是「检测器说无 × 真值有」**，不是「检测器说有 × 真值有」。前者为 0 时，**汇总数字不能引用**。

## 6. 计数纪律- **计数必须带单位**（页 / 行 / occurrence / 去重目标）。本会话出现两次单位错配，其中一次导致「6 vs 10」的对立，两边都以为自己对。
- **跨口径差值是免费的对账信号**。两套独立读数一致才签字；不一致时**差值比任一数字都更值得报告**。
- **不要为了让检查器归零而修改判据或删除内容**。本会话实例：worker 收到一份误报清单，正确处置是「保留并加一句说明」，不是删掉让数字好看。

## 7. 派单纪律：转述必须带出处，不能带结论

**派生数字与派单数字同等危险。** Boss 一次在派单里写了三个「我跑的」`.cs` 计数，实测是**从别人报告里抄的、自己从未跑过**。危害与转述结论相同：它让下游以为不必再核。

**三档标注**，缺一不可：
```
[实测]        = 派单者自己跑出来的，附命令
[转述-未核实]  = 来自他人报告，执行者必须重跑后再用
[约定]        = 规则要求，不是测量值，照做即可
```
**实证**：同一件事上 Boss 报 1.3.15 = 5,194、Lead 报 5,208。**「谁先说的」与「谁对」无关，只有重跑能定。**

**本会话 Boss 给出的未核实数字/结论共 8 个**，其中两个造成了真实损失：

| 值 | 后果 |
|---|---|
| `76`（白名单） | 差点移出两页手写 `sdk-overview.md` |
| `80`（白名单） | 差点移出 **1,132 篇**手写散文 |
| `1,475`（孤儿页） | 算法有缺陷，正确数是 4,562 |
| 「1.4.5 无 C# 源码」 | **24 页写入了错误结论**，让读者以为 1.4.5 无法比对 |

**规则**：
> **派单里出现的每一个具体数字与事实结论，必须是派单者亲自跑出来的；或明确标注「转述自 worker-X，未核实」。**
> **转述必须带出处，不能带结论。**

**同一条错误的传播链（本会话真实发生）**：
```
worker-12 首报「1.4.5 本机无 C# 源码」
  → Lead 未核实，当作事实写进后续三条派单
    → worker-39 继承转述，得出「bin 下没有 .cs」
      → 24 页的「跨版本提示」段写入了这个错误
```
**一个未核实的结论，经过 Lead 就变成了「事实」，再经过 worker 就变成了内容。**

## 8. 边界的两种处置：记录 vs 修复

lead-2 的处置我采纳为通则：

> **先记录边界，再修。**
> 一个**诚实的门禁**（知道自己测不到什么）比一个**半成品的门禁**（会对你没测的类别报 PASS）安全。

本会话三次出现「调门禁让它变绿」而非「修门禁让它变对」：`readdirSync` 补 `withFileTypes`、`'\b'` 换词边界判断、marker 正则补语言。**三次都让工具看起来正常，而缺陷转移到了别处。**

---

### 🔴 口头交付 = 未交付

> **任何被称为「证据」的论证，必须落在仓库内的文件里，并带可复跑命令。**

比「settled ≠ 完成」更严格：那条说「worker 结束了」，这条说「**证据存在**」——后者是**事实性断言**，而事实性断言必须可指认。

**本会话实例**：worker-68 做了一整轮 A/B 反事实论证（「改动前会静默移走一页，改动后 ABORT」），结论被 Lead 当作已交付报给 Boss，**实际全在对话里，仓库零落盘**。若按常规验收签字，仓库里就会多出一批「经确认的守卫」——**而那个确认落在一个不存在的文件上**。

配套三条：
1. **转述「某产物已交付」之前，先在仓库里指认它。** 「对话里有」不等于「盘上有」。
2. **派单纪律里的三档标注（`[实测]` / `[转述-未核实]` / `[约定]`）只管数字与事实结论，不覆盖「产物是否落盘」。** 这是独立的一条。
3. **一份报告里的每条命令都必须能被指认到真实存在的文件或可复跑的对象。** 已发生实例：VERDICT §7 的 `node tools/_v146_prose_name_ruler.mjs --selftest` 指向一把**已按实测结论删除的尺**——交一份「照着跑会 file not found」的报告，等于没有报告。修正时**保留原命令 + 标注不可跑 + 说明为什么**，而不是删掉那一行。

### 🔴 删除 / 归档前先查引用，且按引用关系查

> **不按文件名猜「这是残留」。**

**本会话两例**：
- Boss 按文件名把 8 个 `_v146_ruler_*` 当成「已删尺的残留」列入不纳入清单；实际上 VERDICT 引用它们 **11 处**（含可执行命令），不纳入则报告**不可复跑**。
- Lead 按文件名把 VERDICT 当成「一把已删尺的残留报告」，直到被问起才去查它引用了哪些 fixture。

判据：**先 `grep -rl "<标识>"` 找出引用方，再判断能不能删。** 反过来 —— 一个文件是否还有用，取决于**谁在引用它**，不取决于它叫什么名字。

### 🔴 代理报告的状态必须以磁盘为准

> 「我已完成 X / 我没动 Y」这类陈述若与磁盘不符，**无论成因是交叉、中断还是误解，都必须在回报里以磁盘事实更正**。

**区别只在意图，不在正确性。** 下一个人无法从陈述里分辨「它被骗了」与「它编了」，所以两者都必须按「不可信」处理。

**本会话实例**：Lead 的停手消息与 worker 的写入交叉，worker 随后回报「两个文件都没动」，而 census 已在 00:44 落盘。处置上无损害（`_index.md` 逐字节未改），但**陈述与磁盘不符**这一形态必须按不可信处理。

### 🔴 验证规范覆盖度，只认文件里的标题行

> **不认记忆里的措辞。** 用臆想的探针查文件，与「没搜到 ≠ 不存在」是同一形态。

**本会话实例**：Boss 验规范文件是否覆盖某几条规则时用了自己凭印象写的探针词，其中「单向」实际匹配到的是「分歧全部单向」而非导航 —— **探针写错，结论就会错**。

同族实例（Lead）：把 worker 的观察转述成「本机不支持」而未实测；把两个数值接近的量（文件数 1,838 / 类型数 1,833）当成同一个。

### 🔴 有界搜索必须报边界

> 任何「全树 N 处命中」的说法，**都要说清搜的边界**。有界 walk 被当成穷尽搜索，就会得出「不存在」这类断言。

**本会话实例**（两次）：
- Boss 用 `depth<=8` 的有界 walk 扫出 11,376 个 `.cs`，树里实际 11,385 —— **有界搜索被当成了穷尽搜索**。
- Lead 用 `rel.includes(e)` 拿整条路径做子串排除，把 `TaleWorlds.CampaignSystem/**` 大量误排除、得出荒谬的 `campaign=0`。

### 🔴 探针静默失败时，默认解释不该是「事实为空」

**症状有三种形态：空输出、零命中、全不存在。** 这三者都是**探针故障的典型症状**，不是「事实为空」的证据。

**五个本会话实例（全部同族，全部是探针错而非事实错）**

| 实例 | 探针 | 报出 | 事实 |
| --- | --- | --- | --- |
| Boss ① | UTF-16 码元当字节数 | 「文件 18,558 B」 | 磁盘 40,158 B |
| Boss ② | `grep '^### 🔴'` | 「4 条规则不存在」 | 实际以 `##` 存在 |
| Boss ③ | `execFileSync` 成功只取 stdout | 「0 个孤儿」 | 141 个（警告在 stderr） |
| Boss ④ | 验证脚本该节**输出为空** | 「3 个文件不存在」 | 三个都在 |
| Lead ① | ctx 批处理 cwd 在仓库根的上一级 | 5 个文件全 MISSING | 五个都在 |

**根因**：探针静默失败时，人默认把空结果解释为「事实为空」，而事实常常相反。

**可操作规则**

1. 探针输出「空 / 0 / 全无」，而结论需要「真的什么都没有」时，**必须换第二个探针复核**，或明确写「**本探针未能覆盖**」。不接受单一探针的空结果。
2. **Windows 下 ctx 批处理不认 `&&`**；要串联就写脚本文件再跑。
3. **`execFileSync` 成功时只返回 stdout** —— stderr 必须单独读，否则 `zola check` 这类把警告写 stderr 的命令会报「0 个问题」。
4. **「grep 没命中」有两种可能**：(a) 该类型不存在；(b) 你的 grep 写错了、cwd 错了、或编码不对。**先证 (b) 不成立，再报 (a)。**
5. **有界搜索必须报边界**（见上一节）——「全树 0 命中」与「我没搜到」在输出上不可区分。

### 🔴 写下判据 ≠ 执行了判据

> **规范里每一条都可能被下一个小时重犯。判据的价值不在条数，而在被重犯时能被指着说「这一条刚写过」。**

规范条数不是成绩指标。**这些规则里已有若干条是「刚说过、下一轮又犯」的复发**，本节记录复发机制本身。

> **引用本文件的条数必须连口径一起写。** `### 🔴` 开头的是单条规则；`##` 是分组标题；`###` 里还有不带 🔴 的小节。
> 本节写下时就实测到同一文件被报成 **37 / 41 / 50** 三个数，分别对应「`### 🔴`」「全部 `###`」「`##` + `###`」。三者都不算错，**但把它们放在一起而不标口径，就是让读者去猜分母** —— 这正是本会话反复出现的那类错。

**本会话复发实例**

| 判据 | 复发形态 |
| --- | --- |
| 「产物必须落盘才算交付」 | 说给 worker 听之后，我自己在 commit message 里落盘、未落规范文件 —— **同一轮复发** |
| 「有界搜索必须报边界」 | Boss 写完当天即用 `depth<=8` 扫出 11,376 并据此下结论 |
| 「缺失断言必须 fail-closed」 | Boss bump schemaVersion 时只改生产者、未同步任何消费方，工具集体停摆 |
| 「grep 没命中 ≠ 不存在」 | 规范成文后，**四个 worker / 两个 Lead 仍各栽数次**，其中 Boss 三次、Lead 两次 |

**根因**：判据是**前瞻性**的，而执行发生在**当下**。写下判据的时刻，人正专注于「把事做成」，而遵守判据的时刻人是**在别的事上**。

**可操作做法**

1. **复发时不新增条目，先看是不是某条已存在而没被遵守。** 重复条目只会稀释注意力。
2. **在交接/收尾时，把本轮复发过的判据逐条点名复核一遍**，而不是假设「写过了就等于执行了」。
3. **规范是给下一个小时的人看的，不是给这一轮的结算清单。** 写完后若本轮就违反了它，那它对下一轮仍然有效 —— 但**这一轮的结论要按「可能违反」重新审视**。

### 🔴 术语定义：「public 类型」有三个口径，不定义就会串

本会话里这三个数被**交替使用**过：Boss 的「2,451」用顶层口径、Lead 的「173 / 232」用嵌套口径、worker-73 抽不到嵌套形态是因为 inventory 只认顶层行。**不定义术语，下一个人会拿一个口径的数字去回答另一个口径的问题。**

| 术语 | 定义 | 当前值（`bannerlord-1.4.6` / inventory schemaVersion 5） |
| --- | --- | --- |
| **顶层 public 类型** | `types[]` 的每一行，全部是顶层 `public` 声明，全部带 `pagePath` | **5,987** |
| **嵌套 public** | 顶层类型的 `members[]` 里 `kind=="nested"` 且 `signature` 以 `public` 开头 | **1,025** |
| **嵌套声明** | 同上，`public` + `protected` | **1,051**（含 protected 26 个） |

**硬规则**

1. **凡以「public 类型」作分母的数字，必须注明用的是哪一个口径。**
2. **嵌套声明带 `pagePath` 的数量 = 0。** 也就是说现有 inventory **结构上无法为它们生成页面** —— 不是「抽漏了」，是「没有可分配的行」。
3. `protected` 嵌套声明**不是「可忽略」**：其中 `InitializationArgs`（被 5 个 `PartyComponent` 各自嵌套声明）出现在 public 类型的公开构造签名里 —— **「public 类型」这个范围定义，在 C# 里对嵌套类型并不成立**。这 26 个属**范围洞**（range hole：定义未覆盖），不属噪声（noise）—— 判为「不写」会静默丢内容，判为「写」则要先改抽取器使其能分配 `pagePath`。**它归哪边是一个范围决定，不是本规范能定的。**

**本会话的实际代价**：`campaign-ext` 顶层 597 / 嵌套 public 172（嵌套占 22.4%）；`mission-ext` 顶层 1,854 / 嵌套 public 227（10.9%）。**若按顶层口径派单，这两桶会静默丢掉 399 个 mod 真会引用的嵌套类型。**

### 🔴 探针换法：对方报「X 已落盘」时的两格检查

> **两格缺一不可。** 前一节讲的是探针故障的另一半（空输出 ≠ 事实为空）；
> 本节讲的是另一半：**有输出 ≠ 内容对。** 本会话几乎所有栽跟头都在后半句。

```
对方报了 X 已落盘：
  (1) 读 git show HEAD:<path>，不读工作区   ← 消除在飞编辑干扰
  (2) 读正文，不只读 grep 计数              ← 消除「有输出 ≠ 内容对」
两格缺一不可。
```

**为什么第 (2) 格不能省**：grep 计数只能证明「某个字符串在不在」，它查不出下面三样，
而本会话每一样都真实发生过 —— 全部是 grep 全绿、内容是错的：

| 查不出什么 | 本会话实例 |
| --- | --- |
| **文件里的损坏字符** | 术语定义节第 664 行带着一个 U+FFFD 替换字符进了提交（`81ed6922f4`），成因是 shell heredoc 写入时字符被截断。**没有任何 grep 会失灵**，只有读正文看得见。 |
| **句子读起来不通顺** | 同一处：「worker-73 抽不到样<?>是因为…」—— 字面可读、语义已断。 |
| **提交说明与正文说的是同一件事** | 上一提交说明写「按范围洞处理」，正文却写「不是可忽略」；`grep 范围洞` 在正文 0 命中。 |

**讽刺点**：这三条全部发生在「产物自述必须与磁盘对账」那一节内部 ——
**那一节自己带着一个损坏字符进了历史。**

**可操作规则**

1. 验收他人产物时，**第 (1) 格是入口，第 (2) 格是结论**。只做 (1) 得到「在库里」，不是「内容对」。
2. **自己提交前也要读一遍正文**（不是 grep 命中、不是行数、不是 `git status` 干净）。本会话的乱码就是这样进的库。
3. 若提交说明与正文用词不一致，**以正文为准并当场改正** —— 否则下一个 grep 的人会得到 0 命中而误判「没写」。
4. **shell heredoc 写含非 ASCII 正文的文件是已知风险源**：本会话那次 U+FFFD 即由此产生。写完必须做一次 U+FFFD 自检。
