**FORMULAIC_PURPOSE（中文套话）** —— 在**至少一半**的 `**用途：**` 行命中即废：

```

```markdown

## 2.5 「声明存在但没有调用方」—— 写成事实，不要写成用途

搜到某成员在 1.4.5 里**零调用点**、或只被极少数派生类用到时，
**正确做法是把「它其实没人用」写进页面**，而不是想象一个调用场景把它用起来。

> 这不是缺陷，是对 modder 更有用的事实。「这个钩子引擎自己从来不调，你要用得自己找地方挂」
> 比一段编出来的用法有用得多。

v1.4.5 实测样例：
- `GetVirtualStageCount` —— 8 处 `public override`，但全树**零调用点**
- `_cameraPosition` —— 只被 3 个派生视图用到

**这是铁律 3 的完整形态**：铁律 3 禁的是「编造成员」，但还有一种更隐蔽的 ——
「成员是真的，但为了写满示例而给它编一个不存在的用途」。这两种都要避开。

## 3. 🔴 三条铁律（本项目用真实代价换来的，违反即作废重写）

### 铁律 1 — 禁止用脚本产出 `content/` 下的 `.md`
脚本可以**只读地打印参考数据**（列成员、grep 定义、打印源码行），但**页面必须逐句手写**。
不要写「生成器 .mjs 产出页面」这类东西，也不要跑仓库里任何 `generate-*` / `gen-*` / `batch-gen-*`
之类会写 `content/` 的脚本。

### 铁律 2 — 禁止用「分支含空串的交替组 + 量词」，即 `(a|b|)*` 这类写法
它在 grep（尤其 PowerShell / `rg` 的默认 BRE 路径）上**静默返回 0 命中**，
而「0 命中」与「类型不存在」在输出上完全同形。
判定「某类型是否存在」的**唯一合法证据形式**是：
```
引源码行 + 文件:行号
```
> 例：`Bannerlord.Source/bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/MissionLogic.cs:7  public abstract class MissionLogic : MissionBehavior`

**每条检索规则都要配一个已知为真的阳性对照**：先拿一个你**确知存在**的类型跑同一条命令，
确认命令能打出来，再相信它的 0 命中。

### 铁律 3 — 当示例需要「编造一个成员」才能成立时，停下
问一句：**这个行为在 v1.4.5 上做得成吗？**
本项目已经因此报废过两批页面 —— `MBBindingList` 的 7 个编造方法名、
`MissionBehavior` 的 `_elapsed` + `OnMissionTick`。
两者的共同错误路径都是：**先想象了一段行为，再补上支撑它的成员**。
而「补成员」恰好是让门禁变绿的最短路径 —— 所以门禁绿了不代表页是真的。

> **实测：前 2 页 8 个错成员，约 40% 的成员是凭印象写的。**
> 注意这与铁律 2 是**两件事**，后者更严重：
> ```
> (a|b|)*  : 查了，但模式写错 → 静默返回 0   ← 有异常信号（全 0），阳性对照能抓住
> 40%     : 压根没查          → 门禁查不出来，因为这些名字在代码库里真实存在
>                                ← 没有任何异常信号：门禁绿、格式齐、大小正常
> ```

真遇到了：改写成「v1.4.5 上做不到 / 只有 native 侧才有」并写进 `## 风险与边界`，
或者在页里显式标注不确定。**不要编。**

## 4. 反编造门禁（anti-fabrication）

```
node tools/lib/anti-fabrication.mjs --content <你的目录> --source ../bannerlord-1.4.5
```

- 它扫你的目录里**所有** `.md`，把每个 ```` ```csharp ```` 块里形如 `.MemberName(` 的调用，
  拿去在源码全量 `.cs` 语料里正则查。查不到 → `FABRICATED`。
- 读取器自己写的示例类（`MyCampaignBehavior` 这类）在 `readerOwnedIdentifiers` 里被跳过，不算。
- 阳性对照固定 6 个：`AddBehavior` `SyncData` `IsLoading` `OnGameStart` `PushScreen` `PopScreen`。
  **必须 `positive control: 6/6 found`**。不是 6/6 就说明门禁瞎了，它的 miss 无意义 ——
  此时报「判断不了 + 卡在阳性对照」，不要硬写。
- **耗时约 70 秒**（要建全量源码语料）。耐心等，不要因为慢就 kill。
- `--content` / `--source` 是真参数，会真正限定扫描范围。

### 🔴 门禁是「全语料词边界匹配」，**不是**按类型作用域匹配 —— 它会放行假朋友

`checkPage` 把所有 `.cs` 拼成一个语料串，然后对每个示例里的 `.MemberName` 跑
`new RegExp('\\b' + id + '\\b')` 打到**整个语料**上（`anti-fabrication.mjs` 的 `checkPage`/`runGate`）。

> 也就是说：**只要 Bannerlord 里任何一个类型上有这个成员名，门禁就放行** ——
> 哪怕它压根不属于你写的那一页的类型。

真实案例（本批 worker-89 自查发现）：他在示例里写了 `.GetTier(`，
门禁没报 —— 因为源码别处确实有个 `GetTier`，但**不在**他写的那一族的类型上。
门禁是绿的，页面是错的。

**所以：门禁绿 ≠ 页是真的。正例存在 ≠ 你要用的那个类型上有它。**

正确做法（也就是 worker-89 自己做的）：对每个要写进示例的成员，
**去那个类型自己的声明文件里确认它确实存在**，而不是只确认「源码里某处有这个字符串」。
阳性对照要配成**类型作用域**的阳性对照，不能只配全局的。

### 怎么读它的输出

本批开工前，**你的目录里已经有历史遗留的 FABRICATED**（例：`zh/api/campaign-ext` 开工前全局 201 条）。
所以：

> **验收标准 = 属于你那 20 个文件名的 FABRICATED 条数 = 0。**
> 全局数字含别人的旧账，不作数。输出里逐行按文件名过滤后再报。

开工前先存一份基线，交稿时对比，证明**没有把旧的编造留着、也没有新增**：

```powershell
node tools/lib/anti-fabrication.mjs --content <你的目录> --source ../bannerlord-1.4.5 |
  Select-String "<Type1>|<Type2>|..." > $env:TEMP\<你的前缀>-before.txt
```
