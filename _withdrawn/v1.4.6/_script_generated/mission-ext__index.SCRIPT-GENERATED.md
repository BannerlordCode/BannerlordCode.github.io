# mission-ext：TaleWorlds.MountAndBlade 的完整 API 面

> **本页是清单，不是类页。** 读者的典型路径是「我要让 mod 在战斗里改点东西」→ 进 [mission](../mission) 桶 → 在那四个入口类上撞到墙 → 被甩到这里。旧版这一页只列了二十来个待写名字，而本桶的 public 顶层类型数以千计，于是读者只能靠猜。**现在这里列的是全量。**

## 这个桶对应源码里的什么

权威映射 `tools/_dir-map-canonical.json`（`schemaVersion` 为 5）里，`TaleWorlds.MountAndBlade` → `mission-ext` 是一条**最长的兜底前缀规则**。含义是：凡是命名空间以它开头、又没被 `ViewModelCollection` / `CustomBattle` 这类更长规则截走、也没落进噪声排除清单的类型，全部归进本桶。

规模按两种口径分别数，**单位不同，不能互相校准**：

| 口径 | 数字 | 数的是什么 |
| --- | --- | --- |
| **public 顶层类型（声明级，本页清单的总条目）** | **1,852 个类型** | 每个 `.cs` 文件里顶层（不在其它类型体内）的 `public` 类型声明，按「命名空间 + 名字」去重 |
| ├ 其中委托类型 | 19 个 | `public delegate` 声明，单独成组，见下 |
| └ 其中非委托类型 | 1,833 个 | class / struct / interface / enum，全量列在下方清单里 |
| internal 顶层类型 | 54 个类型 | 按内容判据不建页，列在最后一节说明原因 |
| **.cs 文件（文件级，仅作参照）** | **2,002 个文件** | 文件自身声明的命名空间落进本桶的文件数（1,993 个有显式命名空间声明，9 个没有命名空间声明、按所在目录归桶） |
| 单个命名空间 `TaleWorlds.MountAndBlade` | 656 个类型 | 其中非委托 639 个、委托 17 个 |
| 被更长规则截走、不属于本桶 | — | `*.ViewModelCollection*` → [viewmodel](../viewmodel)；`*.CustomBattle*` → [custombattle](../custombattle)；`*.Multiplayer*`、`*.DedicatedCustomServer*` 按噪声清单排除 |

**两种口径为什么不许互相校准**：一个文件可以声明多个类型，也可以一个类型都不声明（本桶有 96 个文件属于后者，多是只有嵌套类型的文件）。所以「1,852 个类型」和「2,002 个文件」谁也不能推出谁。

**这 1,852 个类型与仓库内建档清单一致。** `tools/_v146_inventory.json` 对本桶记 1,854 条，比这里的唯一类型数多 2 条：`GeneratedUIPrefabCreator` 与 `Program` 这两个名字各在两个命名空间里各声明了一次，建档时按同名冲突规则拆成两份页面。本页按「命名空间 + 名字」去重，所以是 1,852。

**另外提醒一句**：其中 235 个类型落在两个自动生成的 UI 绑定命名空间里（`AutoGenerated` 带数字后缀那两个），是引擎生成的界面绑定代码，mod 基本不会直接引用，检索时可以跳过。

## 与 mission 桶的分工（两个方向都能走）

这是 mod 作者最容易搞混的一处。两者同源（都来自 `TaleWorlds.MountAndBlade`），靠权威映射里的**入口类覆写表**按类型名分成两桶——那张表就是专门为几个 mod 写战斗逻辑时必然要继承或持有的类型开的口子。

- [mission](../mission) 桶是**入口类 carve-out**，故意小：只放 `Mission`、`MissionBehavior`、`Agent`、`Formation`、`MissionState` 这五个，完整 API 面在**本页**。
- **本页（mission-ext）是完整 API 面**：战斗流程骨架、攻城与器械、单位与队伍关系、以及大量内部协作对象。

**判断一个需求属于哪边，问一句**：我是要「拿到一个东西并改它」，还是「要知道引擎下一步要干什么」？前者看 [mission](../mission)，后者看本页。

## 已手写的类页（3 张）

同桶叶子页按桶索引的链接规则写成 `./<TypeName>`。下面的说明**逐字照抄**各页 `## 概述` 的开头段落，不另造。

### [Team](./Team)

`Team` 是战斗里的一方（或一方之下的盟友）。它把四样东西收在一起：**十个 Formation 槽位**（`FormationsIncludingSpecialAndEmpty` 十个，`FormationsIncludingEmpty` 只有前八个，剔掉了 General 与 Bodyguard）、**成员 Agent 列表**（`TeamAgents` 全量、`ActiveAgents` 在场）、**命令通道**（两个 `OrderController` 加事件）、以及**队伍 AI**（`TeamAI`、`QuerySystem`、`DetachmentManager`）。

它实现 `TaleWorlds.Core` 里的 `IMissionTeam`，而那个接口只要求一个成员：`BattleSideEnum Side { get; }`。所以 mod 想拿到「以 `IMissionTeam` 形式」的对象时，实际拿到的就是这个类。

### [MBGameManager](./MBGameManager)

`MBGameManager` 是「Mount & Blade 游戏」这一层的生命周期总控，继承 [GameManagerBase](../core-extra/GameManagerBase)。它自己几乎不持有游戏状态——`IsEnding` 和 `IsLoaded` 两个布尔是仅有的字段级成员——**它做的事情是把基类的十来个抽象生命周期方法，转成对 `Module.CurrentModule.CollectSubModules()` 收集到的全部子模块的扇出调用**。真正的游戏逻辑住在各个模块里。

`public abstract`，而且这是本批次五个类型里**唯一一个真正可继承的类型**。它的构造函数是 `protected`，派生类实例化后由 `MBGameManager.StartNewGame(gameLoader)` 接管加载流程。游戏本体里真实存在的派生类有四个：`SandBoxGameManager`（`SandBox`）、`CustomGameManager`（`TaleWorlds.MountAndBlade.CustomBattle`）、`EditorGameManager`（`TaleWorlds.MountAndBlade`）、`MultiplayerGameManager`（`TaleWorlds.MountAndBlade.Multiplayer`）。

### [ItemType](./ItemType)

`ItemType` 是 `TaleWorlds.MountAndBlade.Diamond` 程序集里的一个 **`internal enum`**，共 26 个成员（`Invalid` 到 `ArmorExtra`，数值 0..25）。它是 Diamond 那一套大厅/库存数据协议里的物品大类标记。

**这一页要先把最重要的话说清楚：mod 代码引用不了它。** 声明就是 `internal enum ItemType`，而 `TaleWorlds.MountAndBlade.Diamond` 工程里没有任何 `InternalsVisibleTo`。mod 侧真正能用的物品分类是 `TaleWorlds.Core` 里 `ItemObject` 的嵌套枚举 `ItemObject.ItemTypeEnum`，那个是 public 且有完整页面。所以本页的价值在于**读懂引擎内部那条转换链**，以及**避开一个高频名字混淆**。

## 怎么自己复核这份清单

清单不是抽样，所以可以重跑。先看文件级底数：

```bash
cd C:/WorkSpace/Bannerlord && find bannerlord-1.4.6 -name '*.cs' | wc -l   # → 11385
```

**1,852 这个声明级数字没有一行 shell 命令能直接算出来**，它需要逐文件解析顶层类型声明。本页的数是这样来的：按 `C:` 无关的源码根 `bannerlord-1.4.6` 递归读全部 11,385 个 `.cs`，取每个文件里第一行 `namespace` 声明作为归属，只认缩进恰好一个制表符的顶层类型声明（类体内的嵌套类型不计），按「命名空间 + 名字」去重；委托那一组的名字取 `<返回类型>` 之后紧邻左括号前的那一组。两种归属方式（读文件里的 `namespace` 关键字 / 从目录路径反推命名空间）在 `TaleWorlds.MountAndBlade` 这一个命名空间上分别给出 656 与 646 个类型，差异来自「文件所在目录与它声明的命名空间不一致」的少数文件——**本页采用前者，因为它就是 C# 编译器实际生效的那个**。

归桶规则只认 `tools/_dir-map-canonical.json`：噪声排除 → `rules` 最长前缀 → 入口类覆写表，顺序不能颠倒。**排除 `excludeNamespaces` 时只按命名空间前缀匹配**（`ns === e || ns.startsWith(e + '.')`），**`excludeSuffixes` 按路径段匹配**——拿整条路径做子串匹配会把 `TaleWorlds.CampaignSystem` 下面大量文件误排除。

想验证某个名字确实在本桶：`grep -rn "class <名字>" bannerlord-1.4.6/`，再看它声明的命名空间前缀是不是 `TaleWorlds.MountAndBlade`。清单里的每个名字都用这条命令反查过。

**已知的口径分歧（据实记录，不在这里调和）**：权威映射的排除清单里写了「命名空间段上匹配 `AutoGenerated` 加数字后缀」，但仓库内的建档清单并没有真的排除它们——本桶 235 个自动生成 UI 绑定类型因此留在清单里。本页跟建档清单保持一致，因为页面生成是按那份清单走的。
