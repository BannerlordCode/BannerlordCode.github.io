# IMBGame

**Namespace:** TaleWorlds.MountAndBlade
**Module:** TaleWorlds.MountAndBlade
**Type:** `internal interface IMBGame`
**Base:** none
**File:** `bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/IMBGame.cs`

## Overview

`IMBGame` is the managed-to-native seam for **the two moments a Bannerlord session actually begins**: tearing down whatever state exists and asking the engine to start fresh, and handing the engine the module data it must load. The file is 13 lines and carries exactly two `[EngineMethod]` bindings (`IMBGame.cs:9`, `IMBGame.cs:12`), named after the native symbols `start_new` and `load_module_data`.

Those two symbols sit at the very top of the game lifecycle — before any `Mission`, before any `Campaign` state, before the renderer has a frame. That placement is the whole story of this interface, and it is why it is the least usable bridge in the module. Its only managed callers are `MBGameManager.StartNewGame()` and `MBGameManager.LoadModuleData(bool)`, both `protected static` (`MBGameManager.cs:36-44`), inside a `public abstract class MBGameManager : GameManagerBase` (`MBGameManager.cs:10`). The bridge is public-reachable only through inheritance.

## Mental Model

### What it is / which layer

- It is the **outermost layer of the Mount & Blade simulation stack** — above Campaign, above Mission, above Scene. Compare [`IMBActionSet`](../IMBActionSet) or [`IMBAgentVisuals`](../IMBAgentVisuals), which are called thousands of times per battle; `IMBGame` is called a handful of times per process lifetime.
- Think of it as the **ignition key and the fuel pump combined**: `StartNew()` resets the engine, `LoadModuleData(bool)` pours in the module. Neither is something gameplay code wants mid-battle.
- The `bool isLoadGame` parameter of `LoadModuleData` is the branch the engine cares about, not you: it selects between a fresh-boot read of module data and a savegame-aware read. Passing the wrong one is not detectable from the managed side, because the method returns `void`.

### The consequence that matters

**The wrapper is `protected`, not `public`.** `MBGameManager.StartNewGame()` and `LoadModuleData(bool)` are `protected static` (`MBGameManager.cs:36`, `MBGameManager.cs:41`), and `MBGameManager` is abstract (`MBGameManager.cs:10`). So the accessibility chain is three deep: `internal interface` → `internal static MBAPI` field → `protected static` wrapper. A mod gets access **only by deriving from `MBGameManager`**, which means becoming the game's entry point, not calling into it. There is no public method on this wrapper you can call from a `MissionBehavior` or a `SubModule` and reach native.

That is a different failure from most bridges. For an ordinary internal interface you go around it via a public wrapper; here you go around it by **not starting the game at all** — the engine already started it before your code ran.

### When to use / when not

- **Use**: nothing, directly. If you have found yourself wanting `StartNew()` mid-session, what you actually want is `GameStateManager` and a `GameState` you push yourself, not an engine restart.
- **Do NOT** call either method outside the game-manager startup path. `StartNew()` resets engine state that `GameStateManager`, the renderer, and every loaded module assume is already valid; calling it from a running mission is the definition of an inconsistent world.
- **Do NOT** assume calling it twice is safe.** Both methods return `void` with no success channel. There is no `IsLoaded`, no exception, and no way to ask afterwards whether the call did what you meant.

## How to use

**How to obtain it.** You cannot reference it at all. The interface is `internal` (`IMBGame.cs:6`), the `MBAPI` field is `internal static` (`MBAPI.cs:56`), and `TaleWorlds.MountAndBlade` grants `InternalsVisibleTo` only to `TaleWorlds.MountAndBlade.AutoGenerated`, `TaleWorlds.MountAndBlade.Multiplayer` and `TaleWorlds.Generator.Bannerlord` (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). Even after you get past that, the wrapper is `protected static` (`MBGameManager.cs:36`, `MBGameManager.cs:41`) on an abstract class, so a mod would additionally have to subclass `MBGameManager` — which is where the engine's own startup happens, and is not a modding surface.

**A typical use.** The real pattern is: you inherit `MBGameManager`, and by the time you could call these, the engine has already called them for you. Read the ambient game state instead of restarting it:

```csharp
using TaleWorlds.Core;
using TaleWorlds.MountAndBlade;

// A mod's own game manager participates in startup; it does not drive the
// engine start. MBGameManager.StartNewGame() (MBGameManager.cs:36) and
// LoadModuleData(bool) (MBGameManager.cs:41) are protected static and were
// already invoked by the engine before any mod code runs.
public sealed class MyGameManager : MBGameManager
{
    protected override void OnGameStart()
    {
        base.OnGameStart();

        // Read the state the engine produced. Do not call StartNew() here:
        // it would reset engine state that GameStateManager already relies on.
        GameState current = GameStateManager.Current.State;
        Debug.Print("game started in state: " + current.GetType().Name, 0);
    }
}
```

**What to watch out for.** The single most common mistake is treating `IMBGame` as the way to "reload the game state" from a menu or a save-load button. It is not: `StartNew()` does not load a save, and `LoadModuleData(bool isLoadGame)` only tells the engine whether to read module data in savegame mode — it does not read the save. Both are engine-startup primitives that were correct once, already ran, and are now behind you. Also note both return `void`: a call that fails produces no managed exception, only broken world state.

## Examples

The negative example, which is the honest one: the call a modder is tempted to make, and why it does not compile.

```csharp
using TaleWorlds.MountAndBlade;

// Does not compile — shown deliberately.
//   error CS0122: 'IMBGame' is inaccessible due to its protection level
//   error CS0122: 'MBAPI.IMBGame' is inaccessible due to its protection level
public static class RestartAttempt
{
    public static void Restart()
    {
        MBAPI.IMBGame.StartNew();          // internal interface, internal field
        MBAPI.IMBGame.LoadModuleData(false);
    }
}
```

The correct way to react to game-state changes — drive a `GameState` instead of restarting the engine:

```csharp
using TaleWorlds.Core;
using TaleWorlds.MountAndBlade;

// Pushing a game state is the supported way to change what the player is doing.
// It is the opposite of IMBGame.StartNew(): additive, not a reset.
public static class GoToMap
{
    public static void OpenMap()
    {
        if (GameStateManager.Current.State is MapState)
            return;

        GameStateManager.CreateState<MapState>();
        Debug.Print("map state pushed; no engine restart involved", 0);
    }
}
```

## Risks and crash boundaries

- **A mod assembly cannot call this interface.** `internal interface` (`IMBGame.cs:6`) plus `internal static MBAPI` field (`MBAPI.cs:56`) plus `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). Compile-time failure, which is the friendly case.
- **Even inside the assembly, the wrapper is `protected`.** `MBGameManager.StartNewGame()` and `LoadModuleData(bool)` are `protected static` on an abstract class (`MBGameManager.cs:10`, `:36`, `:41`). Reaching them means subclassing the game's entry point.
- **No failure channel.** Both members return `void`. A native-side refusal surfaces as broken world state, never as a catchable managed exception.
- **`StartNew()` is not a reload.** It discards engine state; it does not restore a save. Calling it mid-session produces a world that is neither the old session nor a new one.
- **`LoadModuleData(true)` is not "load my save".** The flag only changes the engine's module-data read path (`IMBGame.cs:12`); the savegame read itself is elsewhere.
- **Not a save participant.** No `[Serializable]`, no fields, no sync surface. It is a stateless pair of entry calls.
- **These are startup calls.** Both are meant to be hit once, during startup. Any second call is outside the contract the engine was written against.

## Cross-Version Notes

The v1.4.5 file is 13 lines with two `[EngineMethod]` bindings, `start_new` and `load_module_data`, and the `LoadModuleData(bool isLoadGame)` parameter has carried an `isLoadGame` flag across the `bannerlord-1.3.0`, `bannerlord-1.3.15` and `bannerlord-1.4.5` trees. What stays stable is the **native symbol string**, not the C# shape: the symbol is the contract, so a wrapper may be renamed or re-signed without breaking its binding. The load path has grown new flags in later versions — the parameter list on `load_module_data` is the part most likely to widen, so do not assume the single-`bool` signature is version-independent. **VERIFIED MEASURED for v1.4.5** (13 lines, 2 members, `MBGameManager.cs:36-44` call sites); the other version trees were not read member-by-member for this page.
