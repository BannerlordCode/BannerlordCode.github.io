# IMBBannerlordChecker

**Namespace:** TaleWorlds.MountAndBlade
**Module:** TaleWorlds.MountAndBlade
**Type:** `internal interface IMBBannerlordChecker`
**Base:** none
**File:** `bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/IMBBannerlordChecker.cs`

## Overview

`IMBBannerlordChecker` is the **struct-layout assertion bridge**: the two methods that let the managed tree prove that a `struct` shared with the native engine has exactly the layout the native side expects. It is 14 lines with two `[EngineMethod]` bindings — `get_engine_struct_size` (`IMBBannerlordChecker.cs:10`) and `get_engine_struct_member_offset` (`IMBBannerlordChecker.cs:13`).

Its only caller is `SizeChecker` in the generated `TaleWorlds.MountAndBlade.AutoGenerated` assembly, and both of the methods that call it are decorated `[Conditional("_RGL_KEEP_ASSERTS")]` (`TaleWorlds.MountAndBlade.AutoGenerated/TaleWorlds.MountAndBlade.AutoGenerated/SizeChecker.cs:8`, `:14`). That attribute compiles the call **out of the assembly entirely** unless the `_RGL_KEEP_ASSERTS` symbol is defined. In a normal shipping build this bridge is never called at runtime; in a developer build it is the thing that catches a struct whose managed layout has drifted from the native one.

## Mental Model

### What it is / which layer

- It sits at the **boundary between the managed `struct` declarations and the native engine's own copies of them**. The engine declares `AgentState`, `BodyProperties`, `MissionInitializerRecord`, `EquipmentIndex` and friends as native structs, and mirrors them in C#. This interface is how the two copies are compared.
- `SizeChecker.cs` makes the shape unmistakable: the managed side passes its own `sizeof` result as `managedSize`, and the call is *named* `GetEngineStructSize` — the native side answers with the native size. The comparison logic that would act on a mismatch is not in the managed file we can read, so the bridge itself just reports; what consumes the answer is native-side or generated code.
- It is a **verification seam, not a feature surface**. Nothing in gameplay depends on it, and nothing in a save depends on it. If the answer changes, the build is wrong, not the world.

### The consequence that matters

**You will never see these calls at runtime, and that is the design.** `SizeChecker.CheckTypeSizeAux` and `CheckTypeOffsetAux` are `[Conditional("_RGL_KEEP_ASSERTS")]` (`SizeChecker.cs:8`, `:14`), which means the C# compiler removes the call sites from the IL of the AutoGenerated assembly in a shipping build. So an empty or inert `MBAPI.IMBBannerlordChecker` in a retail game is **correct behaviour, not a broken bridge** — a modder who null-checks it and concludes something is wrong has misread the conditional.

The second consequence is the one that bites a modder: this is one of the few bridges with **no public wrapper at all**. `SizeChecker` is `internal class SizeChecker` in an assembly whose name (`TaleWorlds.MountAndBlade.AutoGenerated`) is one of exactly three that `InternalsVisibleTo` names (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). There is no `public static class SomethingChecker` you can route through. The answer to "how do I call this?" is: you do not.

## How to use

**How to obtain it.** You cannot, and there is no wrapper to route through — that is the difference between this interface and most of the others in this bucket. Three independent walls stand between a mod and `get_engine_struct_size`:

1. The interface is `internal` (`IMBBannerlordChecker.cs:7`), and the `MBAPI` field is `internal static` (`MBAPI.cs:62`).
2. `TaleWorlds.MountAndBlade` grants `InternalsVisibleTo` only to `TaleWorlds.MountAndBlade.AutoGenerated`, `TaleWorlds.MountAndBlade.Multiplayer` and `TaleWorlds.Generator.Bannerlord` (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`) — so a mod assembly naming the type does not compile.
3. Even the caller is invisible: `SizeChecker` is `internal class SizeChecker` in the generated assembly (`TaleWorlds.MountAndBlade.AutoGenerated/TaleWorlds.MountAndBlade.AutoGenerated/SizeChecker.cs:6`), so there is no public method to call even from a friend assembly's perspective unless you are one of those three.

**A typical use.** There is no legitimate direct call. The supported activity is making your own shared struct layout explicit and correct in the way `AssemblyInfo.cs` does — with `[DefineAsEngineStruct]` — so that *your* struct is the thing being verified, rather than trying to verify the engine's:

```csharp
using TaleWorlds.DotNet;

// In your module's AssemblyInfo.cs. A [DefineAsEngineStruct] declaration is what
// puts your struct into the same shared-layout contract that SizeChecker verifies
// in assert-enabled builds (SizeChecker.cs:8-17).
[assembly: DefineAsEngineStruct(typeof(MyModSharedState), "My_mod_shared_state", false, null, null)]

public struct MyModSharedState
{
    public int First;
    public float Second;
    // Keep this layout order explicit: field order here is field order native.
}
```

If you genuinely need to know a native struct's size, measure it on the managed side and compare it against your own expectation in a test, which is what the engine does in an assert build:

```csharp
using System.Runtime.InteropServices;

public static class LayoutProbe
{
    // The managed size is available directly; the native size is what
    // get_engine_struct_size would return, and is not reachable from a mod.
    public static int ManagedSize() => Marshal.SizeOf<MyModSharedState>();
}
```

**What to watch out for.** Do not read an inert `MBAPI.IMBBannerlordChecker` in a shipping game as a failed bridge — `SizeChecker`'s call sites are compiled out by `[Conditional("_RGL_KEEP_ASSERTS")]` (`SizeChecker.cs:8`, `:14`). The mistake worth avoiding is the opposite one: shipping a struct whose managed layout you assumed matches native. This interface is exactly the tool that would have caught it, and the fact that you cannot reach it means **the discipline has to live in your own assembly metadata**, not in a runtime check.

## Examples

The compile-time refusal, which is the most useful thing this page can demonstrate:

```csharp
using TaleWorlds.MountAndBlade;

// Does not compile — shown deliberately.
//   error CS0122: 'IMBBannerlordChecker' is inaccessible due to its protection level
public static class SizeProbe
{
    public static int Ask(string engineStructName)
    {
        // SizeChecker is internal too, so there is no second door either.
        return MBAPI.IMBBannerlordChecker.GetEngineStructSize(engineStructName);
    }
}
```

What a mod does instead — declare your own shared struct so it enters the same verified contract, and check the managed side explicitly:

```csharp
using System.Runtime.InteropServices;
using TaleWorlds.DotNet;

// 1) Declare it as an engine struct so the engine knows the layout is shared.
//    Same attribute the engine uses for its own structs, e.g.
//    [assembly: DefineAsEngineStruct(typeof(AgentState), "Agent_state", false, null, null)]
//    at TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:11
[StructLayout(LayoutKind.Sequential)]
public struct MyModSharedState
{
    public int Counter;
    public float Weight;
}

// 2) Measure the managed side. This is the value SizeChecker.cs:11 hands to
//    get_engine_struct_size for comparison; doing it yourself is what a mod
//    can actually do.
public static class LayoutProbe
{
    public static int ManagedSize() => Marshal.SizeOf<MyModSharedState>();

    public static int CounterOffset() => (int)Marshal.OffsetOf<MyModSharedState>(nameof(MyModSharedState.Counter));
}
```

## Risks and crash boundaries

- **A mod assembly cannot call this interface at all.** `internal interface` (`IMBBannerlordChecker.cs:7`) + `internal static MBAPI` field (`MBAPI.cs:62`) + `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). Compile-time failure.
- **No public wrapper exists.** This is the load-bearing fact: unlike [`IMBActionSet`](../IMBActionSet) or [`IMBEditor`](../IMBEditor), there is no public class you can be redirected to. The caller is `internal class SizeChecker` (`SizeChecker.cs:6`). "Use the public wrapper" is not available advice for this page.
- **The calls are compiled out in shipping builds.** `[Conditional("_RGL_KEEP_ASSERTS")]` on both helpers (`SizeChecker.cs:8`, `:14`) means an inert bridge in a retail game is expected, not broken.
- **No exception channel.** Both members return a value — an `int` and an `IntPtr`. An engine-struct name the native side does not recognise yields whatever native returns, not a catchable managed error.
- **Raw pointer return.** `GetEngineStructMemberOffset` returns `IntPtr`, so consuming the value incorrectly yields a meaningless pointer rather than a diagnostic.
- **Layout drift is the real hazard, not a crash.** If a managed mirror of a shared struct does not match native field-for-field, nothing throws; the engine reads the wrong bytes. This bridge is the only thing that would surface it, and it only runs in assert-enabled builds.
- **Not a save participant.** No `[Serializable]`, no state.

## Cross-Version Notes

The v1.4.5 file is 14 lines with two `[EngineMethod]` bindings, `get_engine_struct_size` and `get_engine_struct_member_offset`, and the identical file name and shape appear under the same `Bannerlord.Source/bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/` layout in the `bannerlord-1.3.0` and `bannerlord-1.3.15` trees. The **native symbol strings** are the stable part; the `SizeChecker` call sites are generated code and are subject to regeneration as `[DefineAsEngineStruct]` types are added, so the *number* of check sites can change between versions even when the bridge does not. The set of `[DefineAsEngineStruct]` entries in `AssemblyInfo.cs` is the thing most likely to grow — v1.4.5 declares `AgentState`, `AgentMovementMode`, `BodyProperties`, `MissionInitializerRecord`, `EquipmentIndex` and others (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:11-25`). **VERIFIED MEASURED for v1.4.5** (14 lines, 2 members, `SizeChecker.cs:6-17` call sites); the sibling version trees were not read member-by-member for this page.
