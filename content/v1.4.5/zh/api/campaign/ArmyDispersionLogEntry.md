# ArmyDispersionLogEntry

**Namespace:** `TaleWorlds.CampaignSystem.LogEntries`
**Module:** `TaleWorlds.CampaignSystem`
**Type:** `public class ArmyDispersionLogEntry : LogEntry, IEncyclopediaLog, IChatNotification, IWarLog`
**Base:** `LogEntry`
**File:** `bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem.LogEntries/ArmyDispersionLogEntry.cs`

## 概述

`ArmyDispersionLogEntry` 是「军团为什么散了」的完整记录。与 [ArmyCreationLogEntry](../ArmyCreationLogEntry) 相比，它实现了**四个**成员（多一个 `IChatNotification`），存**四个**字段，核心价值在于 `GetEncyclopediaText()` 里那棵 `DispersionReason` 的 `switch`——每个被显式处理的解散原因各有各的文案，从「因凝聚力耗尽而解散」到「已无船只，幸存者靠临时木筏和浮木向岸」。

它也是 [ArmyDispersionMapNotification](../ArmyDispersionMapNotification) 的文本来源，官方调用点把同一个 `GetEncyclopediaText()` 结果同时喂给日志与地图通知。

注意一个容易数错的细节：`Army.ArmyDispersionReason`（`Bannerlord.Source/bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem/Army.cs:31`）在 1.4.5 有 **16 个**枚举成员，但 `GetEncyclopediaText()` 只写了 **12 个显式 case**（`Unknown` 与 `_` 兜底共用同一句文案）。`FoodProblem`、`NotEnoughTroop`、`NoActiveWar`、`Inactivity` 四个值没有专属文案，会落到 `_` 兜底上显示「已解散」。

## 心智模型

和 `ArmyCreationLogEntry` 一样是**构造后不再变化的不可变记录**，但它多一层「可见性判定」的重心：

1. **构造器决定它会不会打扰玩家。** 四个字段里最关键的是 `_isVisibleNotification`：

   ```csharp
   _isVisibleNotification = army.LeaderParty.MapFaction == Hero.MainHero.MapFaction && army.Parties.IndexOf(MobileParty.MainParty) >= 0;
   ```

   **两个条件缺一不可**：军团领主与玩家同 `MapFaction`，**且玩家本部确实在这支军团的 `Parties` 列表里**。第二个条件比看上去重要——玩家只是同阵营的旁观者（军团在隔壁集结）时 `IndexOf` 返回 -1，聊天栏不会响。而地图通知用的是**另一个**条件（见下），两者不重叠。

2. **`NotificationType` 走「外交」通道而非「军事」通道。** `=> DiplomaticNotification(_armyLeader.HeroObject?.Clan ?? null, null)`。注意 `_armyLeader` 上的 `?.`：`HeroObject` 可能为 null（见风险），`Clan` 也可能为 null。`DiplomaticNotification(IFaction, IFaction)` 只判 `faction1 == Clan.PlayerClan || faction2 == Clan.PlayerClan`，第二个参数恒为 null，所以实际就是「领主氏族是不是玩家氏族」。这与 [ArmyCreationLogEntry](../ArmyCreationLogEntry) 完全不 override `NotificationType`（用基类默认 `ChatNotificationType.Default`）形成对照。

3. **文案分支表覆盖 12 个枚举值。** `Army.ArmyDispersionReason` 的 16 个成员里有 12 个各有文案，从「因凝聚力耗尽而解散」到「已无船只，幸存者靠临时木筏和浮木向岸」；剩下的 `FoodProblem` / `NotEnoughTroop` / `NoActiveWar` / `Inactivity` 落进 `_` 兜底。`Unknown` 和 `_` 共享 `"{=5CJOMH90}{ARMY} has been disbanded."`。`{ARMY}` 不是裸名字，而是先构造一个 `"{=nbmctMLk}{LEADER_NAME}{.o} Army"` 再 `SetTextVariable("LEADER_NAME", _armyLeader.Name)`，最后整段塞进 `{ARMY}`——**这是百科页可点击链接的嵌套写法**。

4. **战争日志判定与成立条目同构。** `IsRelatedToWar` 的实现逐字和 `ArmyCreationLogEntry` 一样：只看领主 `MapFaction` 是否等于 `stance.Faction1` 或 `Faction2`，`effected` 恒 null。

## 真实示例

官方唯一构造形态，从 [DefaultLogsCampaignBehavior](../DefaultLogsCampaignBehavior).OnArmyDispersed 照抄：

```csharp
ArmyDispersionLogEntry entry = new ArmyDispersionLogEntry(army, reason);
LogEntry.AddLogEntry(entry);
if (army.LeaderParty.MapFaction == Hero.MainHero.MapFaction && army.Parties.IndexOf(MobileParty.MainParty) < 0)
{
    Campaign.Current.CampaignInformationManager.NewMapNoticeAdded(
        new ArmyDispersionMapNotification(army, reason, entry.GetEncyclopediaText()));
}
```

统计玩家亲历的军团解散，按原因分组（用 `LogEntryHistory` 枚举，**不是** `LogEntry` 上的静态方法）：

```csharp
foreach (LogEntry log in Campaign.Current.LogEntryHistory.GameActionLogs)
{
    if (log is ArmyDispersionLogEntry dispersion && dispersion.IsVisibleNotification)
    {
        Debug.Print(dispersion.GameTime + " reason=" + dispersion.DispersionReason + " text=" + dispersion.GetEncyclopediaText(), 0);
    }
}
```

按战争过滤解散记录（`GetLogsForWar` 在 [DiplomacyHelper](../../system/DiplomacyHelper) 上）：

```csharp
foreach ((LogEntry entry, IFaction effector, IFaction effected) in DiplomacyHelper.GetLogsForWar(stance))
{
    if (entry is ArmyDispersionLogEntry dispersion)
    {
        Debug.Print(dispersion.ToString() + " effector=" + effector.Name + " effected=" + (effected == null ? "null" : effected.Name), 0);
    }
}
```

## 风险与边界

- **`NotificationType` 会 NRE。** 它写的是 `_armyLeader.HeroObject?.Clan`，`?.` 只保护了 `HeroObject` 之后的部分，**`_armyLeader` 本身为 null 时直接 NRE**。而同一类型的 `IsVisibleInEncyclopediaPageOf` 偏偏判了 `_armyLeader != null`——两个方法对同一个字段的空值假设不一致，说明作者预期它非 null，但代码没有兜住。构造器 `army.ArmyOwner.CharacterObject` 在 `ArmyOwner` 为 null 时就会产生 null 快照。
- **`_isVisibleNotification` 是快照，不会更新。** 玩家在日志写入之后加入军团，`IsVisibleNotification` 仍是 false，反之亦然。
- **`effected` 永远为 null。** 与 `ArmyCreationLogEntry` 同。
- **`_encyclopediaLinkWithName` 存了但没人读。** 它进存档、参与引用收集，却不被本类型任何方法引用。别指望它能给你军团名字。
- **`ToString()` 与 `GetNotificationText()` 每次都分配两棵 `TextObject`。** 内层的 `"{LEADER_NAME}{.o} Army"` 和外层的 13 分支结果都是新建的。UI 列表里若逐条调用，开销不可忽略。
- **`GetEncyclopediaText()` 的 `switch` 覆盖 12 个值加 `_` 兜底，而枚举本身有 16 个成员。** `FoodProblem` / `NotEnoughTroop` / `NoActiveWar` / `Inactivity` 会落到与 `Unknown` 共用 key `{=5CJOMH90}` 的兜底文案上。派生类若想补全，需要 override 整个方法而不是加分支。
- **存档 id 跳号。** 字段 id 是 30、32、33、34——**31 被跳过了**。新增字段不要顺着填 31。
- **构造器会解两层引用。** `army.ArmyOwner` → `.CharacterObject`；`army.EncyclopediaLinkWithName` 同层。`army` 为 null 直接 NRE，无校验。
- **聊天栏与地图通知的条件是互斥的两套。** 聊天栏要「玩家在军团里」（`IndexOf >= 0`），地图通知要「玩家不在军团里」（`IndexOf < 0`）且同 `MapFaction`。别把两个条件当成同一个。
- **7 天过期写死在 override 里。** 与 `ArmyCreationLogEntry` 一样是冗余声明，改要靠派生。

## 跨版本提示

`bannerlord-1.4.5/Bannerlord.Source/bin/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem.LogEntries/ArmyDispersionLogEntry.cs` 是 124 行、12 个公开成员，`SaveableField` id 为 30/32/33/34（31 未使用）。1.4.6 同名文件公开表面与之逐成员一致。1.3.15 侧无同名文件。

`Army.ArmyDispersionReason` 的枚举成员一旦改名或增补，本类型的 `switch` 会静默落到 `_` 兜底；为此 1.4.5 还配了 [ArmyDispersionReasonEnumResolver](../ArmyDispersionReasonEnumResolver) 做旧存档的枚举名迁移（`"LowPartySizeRatio"` → `NotEnoughTroop`）。
