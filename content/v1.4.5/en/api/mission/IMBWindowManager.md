## Mental Model

Think of it as **a projector and a light-box in the same room**, sharing one calibration offset that is wrong half the time. `WorldToScreen` is the projector: it throws a point at the screen. `ScreenToWorld` is the light-box: it pushes a finger onto a pixel and tells you what world point is behind it. Both need the same `Camera`, and both go through the same projection matrix.

The trap is that the projector has **two calibrations**. The interface's `world_to_screen` (`:13`) is raw — it returns coordinates in the full framebuffer. The engine's UI is not laid out against the full framebuffer; it is laid out against the *usable area*, which shrinks when the aspect ratio mismatches and black bars appear. `MBWindowManager.WorldToScreenInsideUsableArea` (`MBWindowManager.cs:14-20`) therefore subtracts half the horizontal and vertical difference, where `Screen.RealScreenResolutionWidth` is the full width and `ScreenManager.UsableArea.X` is the usable fraction.

The consequence: **anchoring UI to raw `WorldToScreen` output drifts by half the letterbox size whenever the aspect ratio is not the design one.** It is correct on exactly one window shape and wrong everywhere else, and it is the kind of bug that reads as "the tooltip is slightly off-centre" rather than as a failure. Reach for `WorldToScreenInsideUsableArea` unless you specifically want framebuffer coordinates.

The second boundary is the extra `w` out-parameter. `world_to_screen` takes `ref float screenX, ref float screenY, ref float w` (`:13`) and returns a `float`. The `w` is the homogeneous divide factor — it tells you whether the point is in front of or behind the camera, which is the only way to reject a world point that projected "successfully" but is actually behind the viewer.

## How to use

**How to obtain it.** `public class MBWindowManager` (`MBWindowManager.cs:7`) is the public wrapper and needs no detour. The interface is `internal` (`IMBWindowManager.cs:7`) behind `internal static IMBWindowManager IMBWindowManager;` (`MBAPI.cs:52`), and `TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10` grants `InternalsVisibleTo` only to `TaleWorlds.MountAndBlade.AutoGenerated`, `TaleWorlds.MountAndBlade.Multiplayer` and `TaleWorlds.Generator.Bannerlord`.

**A typical use.** A mod that pins a world marker to screen coordinates uses the usable-area overload, because that is the one whose output matches the coordinate space the UI is built in. `Camera.Position` is a property (`Camera.cs:22`) and `Camera.CreateCamera()` is the verified factory (`Camera.cs:61`):

```csharp
using TaleWorlds.Engine;
using TaleWorlds.Library;
using TaleWorlds.MountAndBlade;

Vec2 resolution = MBWindowManager.GetScreenResolution();
Camera camera = Camera.CreateCamera();

Vec3 target = new Vec3(120f, 0f, 80f);
float screenX = 0f, screenY = 0f, w = 0f;
bool projected = MBWindowManager.WorldToScreenInsideUsableArea(camera, target, ref screenX, ref screenY, ref w);
if (projected)
{
    Debug.Print("marker at " + screenX + "," + screenY + " on " + resolution, 0);
}
```

**On getting the live mission camera.** The engine *injects* the mission camera rather than exposing an accessor: `MissionAgentStatusVM(Mission mission, Camera missionCamera, Func<float> getCameraToggleProgress)` receives it as a constructor parameter (`MissionAgentStatusVM.cs:675`) and passes it to `new MissionAgentTakenDamageVM(_missionCamera)` (`:684`), which stores it and hands it to `MBWindowManager.WorldToScreen(_missionCamera, ...)` (`MissionAgentTakenDamageItemVM.cs:107`). In this source tree there is **no public `Mission` member that returns that camera** — see the report note. If you need the live camera, capture it from a view-model layer that is handed one; the projection helpers themselves are happy with any `Camera`.

**What to watch out for.** The single most common mistake is using raw `WorldToScreen` for UI anchoring instead of `WorldToScreenInsideUsableArea`. The consequence is a marker or tooltip offset by half the letterbox on every window shape except one, which is exactly why it survives testing on a single resolution. If you *do* need framebuffer coordinates — a screenshot overlay, for instance — then raw is correct and the usable-area overload would be the bug.

## Examples

Project an agent to screen coordinates for a world-space marker, rejecting points behind the camera:

```csharp
using TaleWorlds.Engine;
using TaleWorlds.Library;
using TaleWorlds.MountAndBlade;

Camera camera = Camera.CreateCamera();
Agent agent = null;
foreach (Agent a in Mission.Current.AttackerTeam.ActiveAgents)
{
    agent = a;
    break;
}
if (agent == null)
{
    return;
}

float screenX = 0f, screenY = 0f, w = 0f;
bool onScreen = MBWindowManager.WorldToScreenInsideUsableArea(camera, agent.Position, ref screenX, ref screenY, ref w);
Debug.Print("agent on screen = " + onScreen + " at " + screenX + "," + screenY, 0);
```

Test whether a world point would be visible at a fixed depth, which is the right question for a ground marker:

```csharp
using TaleWorlds.Engine;
using TaleWorlds.Library;
using TaleWorlds.MountAndBlade;

Camera camera = Camera.CreateCamera();
Vec3 groundPoint = new Vec3(120f, 0f, 80f);
float x = 0f, y = 0f, w = 0f;
bool visibleAtDepth = MBWindowManager.WorldToScreenWithFixedZ(camera, camera.Position, groundPoint, ref x, ref y, ref w);
Debug.Print("ground marker visible = " + visibleAtDepth + " at " + x + "," + y, 0);
```

Turn a screen pixel back into a world point on a chosen plane — the inverse of projection, used by click-to-world interaction:

```csharp
using TaleWorlds.Engine;
using TaleWorlds.Library;
using TaleWorlds.MountAndBlade;

Camera camera = Camera.CreateCamera();
Vec2 resolution = MBWindowManager.GetScreenResolution();

Vec3 worldPoint = new Vec3(0f, 0f, 0f);
MBWindowManager.ScreenToWorld(camera, resolution.x * 0.5f, resolution.y * 0.5f, 0f, ref worldPoint);
Debug.Print("centre of screen at plane z=0 is " + worldPoint, 0);
```

## Risks and crash boundaries

- **A mod assembly cannot call this interface.** `internal interface IMBWindowManager` (`IMBWindowManager.cs:7`), `internal static` field (`MBAPI.cs:52`), `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). `MBWindowManager` is public and needs no such detour.
- **Raw projection is not UI coordinates.** `world_to_screen` (`:13`) returns framebuffer pixels; the usable-area correction lives only in the managed wrapper (`MBWindowManager.cs:14-20`). Anchoring UI to the raw call drifts by half the letterbox.
- **The `w` out-parameter is the only depth test.** Nothing rejects a behind-camera point by itself; ignoring `w` means off-screen markers still "project successfully" to a coordinate.
- **`ScreenToWorld` takes a caller-chosen `z`** (`:25`). It describes a plane, not a ray; picking the wrong plane is the usual cause of a click landing in the wrong place.
- **`GetScreenResolution` is the full resolution** (`:28`), not the usable area. Dividing by it while assuming usable-area space reintroduces the same half-letterbox offset.
- **The erase symbol lives on the wrong-looking interface.** Clearing the console is `MBAPI.IMBWindowManager.EraseMessageLines` (`:10`), invoked from `MessageManager.cs:44-47`. There is no `IMBMessageManager` erase member to find.
- **Frame-order dependent.** `PreDisplay` (`:22`) means "about to present"; issuing draw work after it lands a frame late.
- **Not a save participant.** No `[Serializable]`, no sync surface.
