# GatherArmyAction

**命名空间：** `TaleWorlds.CampaignSystem.Actions`
**Type:** `public static class GatherArmyAction`
**Source:** `TaleWorlds.CampaignSystem/Actions/GatherArmyAction.cs`

## 概述

`GatherArmyAction` 是战役层里专门负责「军团完成集结」这一世界状态变更的静态 Action 类。当你需要让整个战役系统承认「某位领袖的队伍已经在某个地图点把军团聚起来了」时，正确的做法是调用它，而不是自己去写军团对象上的字段、或者手动去触发事件总线。这个类在源码里只有 24 行，公开面非常窄：一个公开入口 `Apply`，一个私有实现 `ApplyInternal`。公开入口接收领袖队伍与集结点，把「玩家是否亲自参与」折算成一个 `float` 参数后交给内部实现；内部实现从领袖队伍身上取出军团对象，然后通过战役事件分发器把这次集结广播出去。也就是说，所有关心「军团已集结」这件事的监听者，只有走这条路径才会被通知到。如果你绕开它直接改状态，系统的其它部分不会收到任何信号，你手里的状态和系统认定的状态就会分叉，之后无论是读档校验还是事件驱动的逻辑都会对不上。

这个类同时也是理解整套 Action 家族设计的最小样本：它把「入口 → 内部实现 → 事件广播」这条链路压缩到了十几行里，看懂了它，再看那些有七八个入口的大 Action 类就不会迷路。

## 心智模型

这个类是一个「多个语义化入口 → 单一内部实现」结构的**退化形态**：它只有**一个**公开入口，而不是常见的三四个。锚表里一共只有三条：类声明、私有实现 `ApplyInternal`、公开入口 `Apply`。诚实地看，它就是一个薄封装 —— 但薄封装仍然有它存在的价值，因为「谁在什么时候广播了什么」这件事被收敛到了一个点上，调用方只需要表达意图，不需要知道广播是怎么发出去的。

内部实现比公开入口**多一个参数**：`ApplyInternal` 接收 `float playerInvolvement = 0f` 这个带默认值的参数，而公开入口 `Apply` 的签名里没有它。公开入口自己算好这个值再传下去：领袖队伍等于主队伍时传 `1f`，否则传 `0f`。这就是为什么 mod 应该调用语义化入口而不是私有实现 —— 你不需要（也无法从外部）复刻这段判定，入口已经替你把「玩家参与度」这个维度填好了。若你以后真的需要自己决定这个值，那也只能在源码层面改内部实现，而不是在 mod 里绕过去。

对 mod 来说结论很简单：把 `GatherArmyAction.Apply` 当成一个语义化动词来用，输入是两个实体（领袖队伍、集结点），输出是「事件被广播」这个副作用。不要在调用前后再去手动补一次事件，也不要试图自己维护军团对象的字段。这一条规律对所有 Action 类都成立：语义化入口负责表达意图与补齐默认参数，内部实现负责真正的状态写入与广播。

## 怎么用

### 怎么拿到它

静态类，直接 `GatherArmyAction.Apply(…)` 调用；不需要实例，也没有构造函数。

### 典型用法

- **剧情 / 任务脚本**：你的任务让某位领主把部队拉到某个坐标集结，而任务完成条件需要系统承认「军团已集结」，此时调用 `Apply`，传入该领主的队伍与目标点。
- **玩家侧的集结确认**：当玩家自己的队伍就是领袖时，调用同一个入口即可，内部会把玩家参与度算成 `1f` 再往下传，你不需要做任何额外处理。
- **配套自己的监听器**：你写了监听「军团已集结」的监听器，就必须在触发侧走 `Apply`，否则监听器永远不会被回调。
- **调试与复现**：想复现某个集结之后的状态，用 `Apply` 触发一次，比手动构造军团对象更接近真实链路。
- **教学 / 演示**：写示例 mod 时，它是演示「Action 类如何收敛状态变更」最省事的例子。

### 最容易踩的坑

- **只有一个公开入口**：不要去找「带玩家参与度参数的公开重载」，锚表里没有；`playerInvolvement` 只存在于私有实现里。
- **集结点是接口不是具体类**：第二个参数的类型是 `IMapPoint`，不要把它和某个具体的地图点实现混为一谈，也不要传一个语义上不成立的坐标。
- **不要在调用之外自己再发一次事件**：广播只发生在 `ApplyInternal` 里，重复广播会让监听者收到两次同样的集结。
- **内部实现不检查领袖队伍是否真的属于某个军团**：它直接从队伍上取出军团对象就往下传，所以调用前请自己确认这个前提成立。
- **不要把参数顺序写反**：第一个是领袖队伍，第二个是集结点，两者类型完全不同，写反了编译就过不去，但在动态拼调用时容易出错。

## 关键成员

- **`GatherArmyAction`**（`GatherArmyAction.cs:8`）— 静态类本体；源码里没有实例成员也没有构造函数，全部能力都通过静态方法暴露。
- **`ApplyInternal`**（`GatherArmyAction.cs:11`）— 私有实现，接收领袖队伍、集结点，以及带默认值 `0f` 的 `playerInvolvement`；它从领袖队伍取出军团对象，再交给事件分发器广播，是所有入口的收敛点。
- **`Apply`**（`GatherArmyAction.cs:18`）— 唯一的公开入口；自己判断领袖队伍是否等于主队伍并折算成 `1f` / `0f`，然后把两个实体参数与折算结果一起传给 `ApplyInternal`。

## 真实示例

```csharp
// 场景：某个领主队伍要在指定地图点完成集结。
// leaderParty 与 gatheringPoint 就是锚表签名里出现的两个实体参数。
public static void GatherAtPoint(MobileParty leaderParty, IMapPoint gatheringPoint)
{
    if (leaderParty == null || gatheringPoint == null)
    {
        return;
    }

    // 走语义化入口：玩家参与度由入口自己折算，不要手动补事件。
    GatherArmyAction.Apply(leaderParty, gatheringPoint);
}
```
