# MBObjectBase

**Namespace:** `TaleWorlds.ObjectSystem`
**Module:** `TaleWorlds.ObjectSystem`
**Type:** `public class MBObjectBase`
**Source:** `TaleWorlds.ObjectSystem/MBObjectBase.cs`

## 概述

`MBObjectBase` 是 Bannerlord 整个实体层的根。`Hero`、`Settlement`、`Clan`、`ItemObject`、`CharacterObject`、`Faction` 全部继承它，`TaleWorlds.ObjectSystem` 里的 `MBObjectManager` 也只为管理这一族对象而存在。它提供三样东西：一个可保存的字符串标识（`StringId`）、一个 GUID（`Id`），以及一整套「对象什么时候进入系统、什么时候可以用了」的生命周期钩子——`OnRegistered` / `Initialize` / `AfterInitialized` / `OnBeforeLoad` / `PreAfterLoad` / `AfterLoad`。

默认实现是「什么都不做」的：所有 `virtual` 钩子在基类里是空体，`IsReady` 不会因为基类逻辑而变成 true，只有真正走完注册 + 初始化流程的对象才会被标成 ready。`Hero`、`Settlement` 等派生类在这些钩子里接上自己的索引维护、反向引用表重建和事件触发。

## 心智模型

一个对象的生命周期大致是：`new`（构造函数里 `StringId` 通常已定，`Id` 还是 `MBGUID.Empty`）→ `MBObjectManager.Instance.RegisterObject<T>()` → `OnRegistered()`（`IsRegistered = true`，随后调 `AfterRegister()`）→ `Initialize()`（`IsInitialized = true`，随后 `AfterInitialized()` 在 `IsRegistered` 为真时把 `IsReady` 置 true）→ 游戏正常使用。注销时 `OnUnregistered()` 把 `IsRegistered` 置回 false。

读档是另一条路径：`[LoadInitializationCallback]` 挂的私有 `BeforeLoad()` 调 `OnBeforeLoad()`，基类实现会在对象已注册时把它重新塞回 `MBObjectManager` 并置 `IsInitialized`；随后 `PreAfterLoadInternal()` → `PreAfterLoad()`，再 `AfterLoadInternal()` → `AfterLoad()`。这三段钩子里派生类要做的是「重建运行期索引和缓存」，而不是「重新赋值」，因为值已经被保存系统恢复了。

常见误用有三类。一是**在构造函数里访问全局集合**：此刻对象还没进 `MBObjectManager`，`Campaign.Current` 往往也是 null。二是**在 `Initialize()` 里发事件**：此时对象图可能还没装配完成，监听者拿到的引用不完整；事件应该放到 `AfterLoad()` 或 Behavior 的 `OnSessionStart`。三是**依赖 `IsReady` 但自己没调 `AfterInitialized`**：派生类若覆盖了 `AfterInitialized()` 又忘了调 `base.AfterInitialized()`，`IsReady` 会永远是 false。

## 怎么用

### 怎么拿到它

`MBObjectBase`（`TaleWorlds.ObjectSystem/MBObjectBase.cs:11`）是所有 `MBObjectBase` 派生对象的根，`MBObjectManager` 的所有泛型方法都以 `where T : MBObjectBase` 约束（`MBObjectManager.cs:70`、`MBObjectManager.cs:227`、`MBObjectManager.cs:288`、`MBObjectManager.cs:319`）。mod 拿到的实例基本只有三种来源：

- **XML 反序列化**（最常见）：`MBObjectManager.LoadXML(string id, bool isDevelopment, string gameType, ...)`（`MBObjectManager.cs:530`）→ `LoadXml(XmlDocument doc, bool isDevelopment)`（`MBObjectManager.cs:1218`）→ `CreateObjectFromXmlNode(XmlNode node)`（`MBObjectManager.cs:1257`）→ 你的 `Deserialize(MBObjectManager objectManager, XmlNode node)`（`MBObjectBase.cs:82`）。游戏本体就是这么加载 `Monsters` / `Items` / `Skills` 这些表的。
- **代码里造**：`MBObjectManager.CreateObject<T>(string stringId)`（`MBObjectManager.cs:1405`），它 `new T()` → 赋 `StringId` → `RegisterObject<T>` → 广播 `IObjectManagerHandler.AfterCreateObject`。
- **全局查**：`MBObjectManager.Instance.GetObject<T>(string objectName)`（`MBObjectManager.cs:288`）、`GetFirstObject<T>()`（`MBObjectManager.cs:319`）、`GetObjectTypeList<T>()`（`MBObjectManager.cs:473`）。注意这三个找不到时都返回 `default(T)`，也就是 null（`MBObjectManager.cs:315-317`、`MBObjectManager.cs:346-348`）。

子类要覆写的是这四个虚函数：`Deserialize`（`:82`，读自己的 XML 字段）、`Initialize`（`:76`，`base` 只是把 `IsInitialized` 置 true）、`AfterRegister`（`:71`，注册完成回调）、`GetName`（`:112`，显示名）。

### 典型用法

定义一个自己的 `MBObjectBase` 派生类型，注册类型表、从 XML 加载、运行期按 stringId 查回：

```csharp
using TaleWorlds.ObjectSystem;
using System.Xml;

public class MyFaction : MBObjectBase
{
    public TextObject DisplayName { get; private set; }

    public override void Deserialize(MBObjectManager objectManager, XmlNode node)
    {
        base.Deserialize(objectManager, node);          // MBObjectBase.cs:82，负责 IsInitialized 和 StringId
        DisplayName = new TextObject(node.Attributes["name"].Value);
    }

    public override TextObject GetName()               // MBObjectBase.cs:112
    {
        return DisplayName;
    }
}

// 在 MBSubModuleBase.RegisterSubModuleTypes() 里注册；第三个参数是 typeId，别和引擎占用值撞
public override void RegisterSubModuleTypes()
{
    base.RegisterSubModuleTypes();
    MBObjectManager.Instance.RegisterType<MyFaction>("my_faction", "my_factions", 5100);
}

// 加载：id 是 Modules/<你的模块>/MyFactions.xml 的模块内路径
MBObjectManager.Instance.LoadXML("MyFactions", true, "Campaign");

// 取用：GetObject 找不到时返回 null（MBObjectManager.cs:288-317）
MyFaction faction = MBObjectManager.Instance.GetObject<MyFaction>("my_faction_empire");
if (faction != null)
{
    Debug.Print(faction.GetName().ToString(), 0);
}
```

### 最容易踩的坑

**以为 `StringId` 冲突了会抛异常，于是两个同名对象悄悄共存——不会，引擎会直接改写你那个对象的 `StringId`。** `MBObjectManager.RegisterObject(T obj, bool presumed, out MBObjectBase registeredObject)`（`MBObjectManager.cs:1781`）第一件事就是 `this._registeredObjects.TryGetValue(obj.StringId, out t)`；命中且不是同一个实例、也不是 `presumed` 时，它进入 `GetIdParts` 分支，把 `obj.StringId` 改写成 `item + num.ToString()` 并循环加号直到不冲突（`:1790-1800`）。后果是：你手上这个实例的 id 已经不是你在 XML 里写的那个了，`MBObjectManager.Instance.GetObject<MyFaction>("你写的id")` 返回 null，而只有重新读 `obj.StringId` 才能找到它——排查时看起来就像「对象注册丢了」。**唯一可靠的防法是在设计阶段保证 id 全局唯一，并在注册后断言 `obj.StringId == 你写的id`。**

同源的两个坑：`Deserialize` 基类实现直接取 `node.Attributes["id"].Value`（`MBObjectBase.cs:85`），XML 节点缺 `id` 属性就是 `NullReferenceException`；而 `IsRegistered` 是 `internal`（`:42`），mod 侧读不到，判断「对象是否真的进了管理器」只能用 `IsInitialized`（`:29`，setter 同样是 `internal`）或者直接 `GetObject` 查回来对比引用。

## 真实示例

无参构造是给 `MBObjectManager.CreateObject<T>(string stringId)` 用的——那个方法的泛型约束是 `where T : MBObjectBase, new()`。

```csharp
public class LedgerEntry : MBObjectBase
{
    public LedgerEntry()
        : base("ledger_placeholder")
    {
    }

    public LedgerEntry(string stringId, Hero owner)
        : base(stringId)
    {
        Owner = owner;
    }

    public Hero Owner { get; private set; }

    public override void Initialize()
    {
        base.Initialize();
        MBObjectManager.Instance.RegisterObject<LedgerEntry>(this);
    }

    protected override void OnBeforeLoad()
    {
        base.OnBeforeLoad();
        Index.Add(this.StringId, this);
    }

    protected override void AfterLoad()
    {
        base.AfterLoad();
        if (Owner == null)
        {
            Owner = Hero.MainHero;
        }
    }

    protected override void AutoGeneratedInstanceCollectObjects(List<object> collectedObjects)
    {
        base.AutoGeneratedInstanceCollectObjects(collectedObjects);
        collectedObjects.Add(this.Owner);
    }

    private static readonly Dictionary<string, LedgerEntry> Index =
        new Dictionary<string, LedgerEntry>();
}
```

无参构造是给 `MBObjectManager.CreateObject<T>(string stringId)` 用的——那个方法的泛型约束是 `where T : MBObjectBase, new()`。

```csharp
public override void Deserialize(MBObjectManager objectManager, XmlNode node)
{
    base.Deserialize(objectManager, node);   // 基类读 id 并置 IsInitialized
    Amount = int.Parse(node.Attributes["amount"].Value);
}
```

注意基类 `Deserialize` 会读 `node.Attributes["id"]`，如果你的 XML 节点没有 `id` 属性就会在基类里抛异常，而不是在你的代码里。

## 风险与边界

- **构造期没有上下文**：`new` 出来的对象还没进 `MBObjectManager`，也不在 `Campaign.Current` 的任何集合里。此处访问全局单例必然拿到不完整状态。
- **`IsRegistered` 是 internal**：mod 读不到它，只能读 `IsReady`。在自定义派生类里也别试图 `override` 它，源码里是 `internal set`。
- **`GetHashCode` 与 `Equals` 不对称**：哈希基于 `Id`，相等基于引用。对象在 `RegisterObject` 之前 `Id` 是空的，此时把它塞进 `HashSet` 之后再注册会导致集合行为异常。
- **读档钩子顺序固定**：`OnBeforeLoad` → `PreAfterLoad` → `AfterLoad`。在 `OnBeforeLoad` 里读 `Owner` 拿到的是 null，因为跨对象引用尚未恢复。
- **保存字段必须收集**：`AutoGeneratedInstanceCollectObjects` 漏掉的 `MBObjectBase` 字段在存档里会变成悬空引用，读档后为 null，游戏不会报错。
- **`Deserialize` 缺 `id` 会崩**：基类实现直接 `node.Attributes["id"].Value`，不做 null 检查。
- **单线程假设**：`MBObjectManager` 的登记与枚举都没有锁，所有这些钩子只在主线程的战役加载/初始化阶段被调。

## 跨版本提示

`MBObjectBase` 在 1.3.0 中不存在（`bannerlord-1.3.0/` 下无此文件）；1.3.15、1.4.5、1.4.6 三个版本的声明都是 `public class MBObjectBase`，可访问成员数量均为 23，跨版本无增删。1.4.5 的参考源位于 `bannerlord-1.4.5/Bannerlord.Source/bin/TaleWorlds.ObjectSystem/`，是去注释版本，成员面与 1.4.6 一致。
