## 2. 「2,012 页」是什么——以及它为什么不成立了

它指的是：旧三树里**没有**生成标记的页面（2,012 页）。我此前担心「其中约一半可能也是机器写的，但没有标记所以自动查不出来」，因此提议**按总体构成重采样做一次人读普查**，好知道该重写多少。

**在裁定 1 之下，这个问题自动消失**：全部 38,993 页都要逐页看过，那 2,012 页不需要单独识别——**轮到它们时就重写**。

> 教训：一个「先测量再行动」的问题，在「全部都要做」的前提下是多余的。

## 4. 抽取器：只是清单，不是作者

**用户的质疑成立，我接受。**

### 抽取器是什么

`tools/_v146_inventory.json` 等产物，用于**枚举某版本源码里有哪些 public 类型**，避免漏写。它：
- 只读源码
- 只写 `tools/` 下的 json
- **从不写 `content/`**

### 抽取器不是什么

- 它不生成任何文档
- 它的口径**不能**当作文档范围的分母——v1.4.6 我手工正则数出 13,162，抽取器给 5,987，**差 2.2 倍**，因为反编译产物里同一类型有大量 `partial` 重复声明，而抽取器按类型去重
- 它**不能**给嵌套类型分配页面路径（`pagePath` = 0），这一点此前被我描述成「范围洞 / 阻塞」，**属于我自己的框架问题，不是用户的**：想写 `Army.ArmyTypes`，读 `Army.cs` 就找到了，不需要任何工具批准

### 因此确立的方法

> **读源码 → 写文档。抽取器至多用来提醒「这张清单上还有 N 个没写」，
> 绝不作为写作方式、范围依据或完成判据。**

## 5. 单页标准（从 v1.4.6 已完成的 40 页归纳）

每一页必须包含：

1. **概述** —— 这个类型在游戏里扮演什么角色
2. **心智模型** —— 什么时候用、典型调用顺序、常见误用与坑
3. **每个 public 成员是做什么用的** —— 不是只列签名，要说明用途
4. **真实可编译示例** —— ≥3 行，含 `.Method(` 调用，签名逐个对过源码
5. **风险与边界** —— 生命周期、悬空引用、线程、平台差异，按该类型实际风险写

硬性要求：
- 事实来源只有 `bannerlord-<version>/` 下的 `.cs`
- **禁止任何脚本产出 `content/**` 下的 `.md`**
- 禁止样板句（`SomeValue` / `null; // 替换` / `service = ...` 等）
