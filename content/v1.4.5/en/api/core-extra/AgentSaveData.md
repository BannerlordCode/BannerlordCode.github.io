# AgentSaveData

**Namespace:** TaleWorlds.Core
**Module:** TaleWorlds.Core
**Type:** `public struct AgentSaveData(string characterStringId, MatrixFrame spawnFrame, string[] agentSpawnPointTags, int agentSeed)`
**Base:** none
**File:** `bin/TaleWorlds.Core/TaleWorlds.Core/AgentSaveData.cs`

## Overview

`AgentSaveData` is **one agent's identity snapshot as stored in a save**: it answers "when a batch of agents has to be restored from a save, which four things must I remember about each of them" — the character's StringId, the spawn [MatrixFrame](../MatrixFrame), the array of spawn-point tags, and the random seed that determines appearance. All four fields carry `[SaveableField(n)]` with indices 1 through 4, and **those indices are part of the save format; they cannot be changed**.

The role it plays is **the minimal serialisable description of an agent**, at the campaign save layer rather than the mission runtime. Its shape is worth noticing: this is a **C# 12 primary-constructor struct** (`public struct AgentSaveData(string characterStringId, ...)` at source line 7), three of its four fields are `readonly`, and only `SpawnFrame` is writable — because the spawn position is the one quantity that legitimately needs correcting after a load (through `UpdateSpawnFrame`).

## Mental Model

Treat it as **one row in the agent roster held by a save**, not as a description of a living agent. It takes no part in combat, never enters a mission, and holds no references to game objects — it is four pieces of pure data, and the only reference type among them (`string[]`) is merely an array of tag strings. To decide whether it is the right tool, ask one question: **does this information need to survive the game closing and reopening?** If yes, use this; if not, [AgentData](../AgentData) is enough.

**The single thing you most need to understand about this type is that it is "semi-generated".** `AgentSaveData.cs:26-53` holds five members whose names start with `AutoGenerated`: `AutoGeneratedStaticCollectObjectsAgentSaveData`, `AutoGeneratedInstanceCollectObjects`, and `AutoGeneratedGetMemberValueCharacterStringId`, `AutoGeneratedGetMemberValueSpawnFrame`, `AutoGeneratedGetMemberValueAgentSpawnPointTags`, `AutoGeneratedGetMemberValueAgentSeed`. **These were not written by a code generator — they are hand-written in the source.** `TaleWorlds.Core/AutoGeneratedSaveManager.cs:150-155` registers those five methods as delegates directly with the save system:

```csharp
CollectObjectsDelegate collectObjectsDelegate31 = AgentSaveData.AutoGeneratedStaticCollectObjectsAgentSaveData;
obj31.GetFieldDefinitionWithId(new MemberTypeId(1, 1)).InitializeForAutoGeneration(AgentSaveData.AutoGeneratedGetMemberValueCharacterStringId);
obj31.GetFieldDefinitionWithId(new MemberTypeId(1, 2)).InitializeForAutoGeneration(AgentSaveData.AutoGeneratedGetMemberValueSpawnFrame);
obj31.GetFieldDefinitionWithId(new MemberTypeId(1, 3)).InitializeForAutoGeneration(AgentSaveData.AutoGeneratedGetMemberValueAgentSpawnPointTags);
obj31.GetFieldDefinitionWithId(new MemberTypeId(1, 4)).InitializeForAutoGeneration(AgentSaveData.AutoGeneratedGetMemberValueAgentSeed);
```

*(That snippet is a source quotation, not an example from this page.)* **So the four `SaveableField` indices are hard-bound to those four `AutoGeneratedGetMemberValueXxx` callbacks.** Add a fifth field to the struct and you must also add an `AutoGeneratedGetMemberValueXxx` plus one more registration line in `AutoGeneratedSaveManager` — **adding the field alone makes the save system silently drop it.**

Three practical conclusions follow. First, **`UpdateSpawnFrame` is the only writable path, and it mutates**: `SpawnFrame` itself is not `readonly`, but because the type is a struct with value semantics, `UpdateSpawnFrame` modifies a copy — unless you assign the result back, the change is lost. Second, **`AutoGeneratedInstanceCollectObjects` gathers exactly one reference**: `AgentSpawnPointTags`. `CharacterStringId`, `SpawnFrame`, and `AgentSeed` are value types or an inline struct and therefore **do not** need to enter the reference table — that is the key to understanding why `collectedObjects.Add(...)` is a single line. Third, **in 1.4.5's managed source this type has neither a construction site nor a reader** (see the Risks section), and that fact dictates what you can actually do with it.

## One more thing this type is in 1.4.5: "registered, not wired"

This is something the page has to state plainly rather than paper over. `grep -rn "AgentSaveData"` across the whole managed C# tree of `bannerlord-1.4.5` hits only three kinds of location:

1. **Its own source** (seven occurrences in `AgentSaveData.cs`);
2. **`AutoGeneratedSaveManager.cs`** — the registration and field callbacks (`:150-155`, `:999`, `:1008`, `:1017`);
3. **`SaveableCoreTypeDefiner.cs`** — two definitions, `:58`'s `AddStructDefinition(typeof(AgentSaveData), 1012);` and `:119`'s `ConstructContainerDefinition(typeof(List<AgentSaveData>));`.

**`new AgentSaveData(` has zero hits tree-wide.** In other words: **the save system knows this type exists and knows how to read and write its four fields, but nothing in managed code actually constructs or consumes it.**

**What I cannot determine, stated as such**: whether the code that populates `List<AgentSaveData>` lives on the native side, in a module constructed reflectively at runtime, or was removed during a 1.4.5 refactor — **that cannot be decided from this managed source alone**. What is certain is only this: the type id is **1012** (`SaveableCoreTypeDefiner.cs:58`), the container is `List<AgentSaveData>` (`:119`), and it is traversed by three container read/write paths in `AutoGeneratedSaveManager` (`:999`, `:1008`, `:1017`). **Therefore this page offers no "how to make the game run through the AgentSaveData flow" example — on 1.4.5 it cannot be triggered from managed code.** The examples below demonstrate only the real shape of the type's own API.

## Real Example

The real shape of the type — note the value semantics, which force `UpdateSpawnFrame` to be written back:

```csharp
MatrixFrame spawnFrame = new MatrixFrame(Mat3.Identity, new Vec3(120f, -340f, 0f, 1f));

AgentSaveData entry = new AgentSaveData(
    "empire_villager_female",
    spawnFrame,
    new string[] { "spawn_point_01", "spawn_point_02" },
    MBRandom.RandomInt(0, 99999));

// CharacterStringId is a plain string, not an object reference -- that is why
// AutoGeneratedInstanceCollectObjects only collects AgentSpawnPointTags.
Debug.Print("id = " + entry.CharacterStringId, 0);
Debug.Print("seed = " + entry.AgentSeed, 0);
Debug.Print("tags = " + entry.AgentSpawnPointTags.Length, 0);
```

The value-semantics trap on `UpdateSpawnFrame` — the most practically useful block on this page:

```csharp
AgentSaveData before = new AgentSaveData(
    "empire_villager_female", MatrixFrame.Identity, new string[0], 12345);

// Mutating a method on a struct changes a copy, not the original.
before.UpdateSpawnFrame(new MatrixFrame(Mat3.Identity, new Vec3(5f, 6f, 0f, 1f)));

// before still holds MatrixFrame.Identity here -- you must write it back.
before = new AgentSaveData(
    before.CharacterStringId,
    new MatrixFrame(Mat3.Identity, new Vec3(5f, 6f, 0f, 1f)),
    before.AgentSpawnPointTags,
    before.AgentSeed);

Debug.Print("seed survived the rewrite = " + before.AgentSeed, 0);
```

Reproducing how the save system reads it — through the four field callbacks rather than by reading properties directly (shape taken from `AutoGeneratedSaveManager.cs:152-155`):

```csharp
public static class AgentSaveDataReader
{
    public static object ReadMember(AgentSaveData data, int saveableFieldId)
    {
        switch (saveableFieldId)
        {
            case 1:
                return data.CharacterStringId;
            case 2:
                return data.SpawnFrame;
            case 3:
                return data.AgentSpawnPointTags;
            case 4:
                return data.AgentSeed;
            default:
                return null;
        }
    }

    // Mirrors the generated collector: only the reference-typed field is tracked.
    public static List<object> CollectReferences(AgentSaveData data)
    {
        List<object> collected = new List<object>();
        collected.Add(data.AgentSpawnPointTags);
        return collected;
    }
}
```

## Risks and Boundaries

- **No producer and no consumer anywhere in 1.4.5's managed source.** `new AgentSaveData(` returns zero hits tree-wide, and every reference to `AgentSaveData` lands in itself, `AutoGeneratedSaveManager`, or `SaveableCoreTypeDefiner`. **A mod therefore cannot make the game exercise this flow from managed code.** Where the code that fills `List<AgentSaveData>` lives — **this cannot be determined** from this managed source: it may be native, reflectively constructed at runtime, or removed by a refactor. What is certain is only the type id 1012, the container type, and the three traversals in `AutoGeneratedSaveManager`.
- **Struct plus mutating method equals silent loss.** `UpdateSpawnFrame` modifies a copy. It is the most common source of error with this type, and **neither the compiler nor the runtime gives any hint**.
- **`SaveableField` indices are part of the save format.** Indices 1–4 are bound one-to-one to the four `AutoGeneratedGetMemberValueXxx` callbacks (`AutoGeneratedSaveManager.cs:152-155` binds them via `new MemberTypeId(1, 1)` through `(1, 4)`). **Changing an index makes old saves read the wrong field.**
- **Adding a field means touching three places.** A new `[SaveableField(5)]` needs a matching `AutoGeneratedGetMemberValueXxx` plus one more `GetFieldDefinitionWithId(new MemberTypeId(1, 5)).InitializeForAutoGeneration(...)` line in `AutoGeneratedSaveManager`. **Adding only the field makes the save silently drop it** — the direct price of those `AutoGenerated*` members being hand-written rather than generated.
- **Only the array enters the reference table.** `AutoGeneratedInstanceCollectObjects` only does `Add(AgentSpawnPointTags)`. If you change a value-typed field into a reference type (wrapping `AgentSeed` in a class, say), **you must add it to that method as well**, or the serialiser will not track it.
- **Three fields are `readonly`, one is writable.** This is not arbitrary: `SpawnFrame` is the only value that may legitimately need correcting after a load (spawn points shift when a battle restarts), while the other three are restored verbatim.
- **`CharacterStringId` is a string, not a reference.** On load the game resolves it itself via `MBObjectManager.GetObject<BasicCharacterObject>(CharacterStringId)`. **Changing the StringId of a saved character definition makes old saves unable to find that character.**
- **`AgentSeed` drives appearance reproduction.** The same `AgentSeed` must regenerate the same face and gear. **If you change the `BodyProperties` generation algorithm without touching `AgentSeed`, old saves will load a different-looking character** — no crash, but a silent visual change.
- **The registration id 1012 and the container are globally shared.** `SaveableCoreTypeDefiner.cs:58/119` is the single global definition, so **you cannot re-register the same type id for your own purposes.**
- **The `AutoGenerated*` members are not an API for mods.** Three `GetMemberValueXxx` methods are `internal` and simply unreachable from another assembly; the two `CollectObjects` methods are public only to serve the framework. **Building your own serialisation on top of them is a self-inflicted problem.**

## Cross-Version Notes

`AgentSaveData.cs` is 55 lines in 1.4.5, in that version's original-source form (file-scoped namespace, no `// Token:` comments, and **no `// <auto-generated/>` header** — which is itself the proof that those `AutoGenerated*` members are hand-written, since genuinely generated code carries that marker). The 1.3.x / 1.4.6 counterparts are decompiled output and will carry decompiler-generated `Equals` / `GetHashCode` / `ToString` boilerplate that does not exist here. **Three things are worth checking when migrating across versions**: whether the type registration id 1012 is stable (it is part of the save format — change it and every old save breaks); whether the four `SaveableField` indices and their order are stable; and, **most importantly**, whether this "registered but unwired" state changes in a later version. If a `new AgentSaveData(` call site appears downstream, the producer has been restored; conversely, if the type disappears from `SaveableCoreTypeDefiner`, the whole mechanism was removed. **This page does not guess — it points you at what to verify.**
