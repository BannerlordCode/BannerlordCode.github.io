# IMBDebugExtensions

**Namespace:** TaleWorlds.MountAndBlade
**Module:** TaleWorlds.MountAndBlade
**Type:** `internal interface IMBDebugExtensions`
**Base:** none
**File:** `bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/IMBDebugExtensions.cs`

## Overview

`IMBDebugExtensions` is the managed-to-native seam for **drawing debug geometry on the terrain and, separately, tweaking the native side's own parameters**. The file is 23 lines with five `[EngineMethod]` bindings: three renderers — `render_debug_circle_on_terrain`, `render_debug_arc_on_terrain`, `render_debug_line_on_terrain` (`IMBDebugExtensions.cs:10`, `:13`, `:16`) — and two parameter controls, `override_native_parameter` and `reload_native_parameters` (`IMBDebugExtensions.cs:19`, `:22`).

The wrapper is [`DebugExtensions`](../../mission-ext/DebugExtensions), a `public static class` (`DebugExtensions.cs:6`) that is **22 lines long and forwards exactly three of the five members** (`DebugExtensions.cs:10`, `:15`, `:20`). `OverrideNativeParameter` and `ReloadNativeParameters` have **no public wrapper anywhere in the tree**. That asymmetry is the most useful fact on this page and is verified by reading the whole wrapper file, not inferred from its size.

## Mental Model

### What it is / which layer

- It sits at the **rendering edge**: each render method takes a `UIntPtr scenePointer` and passes it straight to native, because the shapes are drawn into a scene the managed side cannot draw into itself. The three renderers are a circle, an arc (a circle with a start and end angle), and a line — the minimum set needed to visualise a range, a cone, or a ray.
- The two parameter members are a different job entirely. `OverrideNativeParameter(string paramName, float value)` pushes a named value into the engine's own parameter system, and `ReloadNativeParameters()` asks it to re-read that system's defaults. Neither touches the scene; they change how the engine reads its own configuration.
- Read the interface as **two small tools sharing one seam** because both happened to be implemented natively. There is no shared model behind them, and no guarantee they stay together.

### The consequence that matters

**Two of the five members are unreachable from a mod, permanently.** Not "internal so awkward" — *no public wrapper exists*. `DebugExtensions` is the only file in the module that forwards to `IMBDebugExtensions`, and it forwards only the three render methods. So a mod can draw a debug circle and cannot override a native parameter. If you were looking for the sanctioned way to tune a native parameter from a mod, this page's answer is: there is none, and that is a deliberate gap rather than a missing one.

The second consequence is a per-call cost that is easy to miss. These are immediate native render calls, not queued geometry: `RenderDebugCircleOnTerrain` (`IMBDebugExtensions.cs:10`) draws when invoked. A mod that calls it every frame from `OnMissionTick` is issuing a native draw per frame, per call, which is the classic way to make a battle stutter.

### When to use / when not

- **Use** the renderers from a `MissionBehavior`'s tick while debugging geometry — placement, ranges, formation offsets, path traces.
- **Do NOT** ship debug rendering. Gate it behind your own `Debug` flag and remove it for release; these calls have no "persistent debug layer" semantics, they redraw every frame while called.
- **Do NOT** try to reach `OverrideNativeParameter`. It has no public path, and a reflection hack against an `internal static` field in a shipping game is not a technique worth documenting.

## How to use

**How to obtain it.** You cannot reference the interface: it is `internal` (`IMBDebugExtensions.cs:7`), the `MBAPI` field is `internal static` (`MBAPI.cs:54`), and `TaleWorlds.MountAndBlade` grants `InternalsVisibleTo` only to `TaleWorlds.MountAndBlade.AutoGenerated`, `TaleWorlds.MountAndBlade.Multiplayer` and `TaleWorlds.Generator.Bannerlord` (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`).

The door out is [`DebugExtensions`](../../mission-ext/DebugExtensions), `public static class` at `DebugExtensions.cs:6`. Note what that door does **not** include: `OverrideNativeParameter` and `ReloadNativeParameters` are simply not in the file, so "use the public wrapper" is only true for the three render members.

**A typical use.** Draw a range indicator from a mission behavior, gating it behind your own debug switch:

```csharp
using TaleWorlds.Engine;
using TaleWorlds.MountAndBlade;

public class RangeDebugBehavior : MissionLogic
{
    public override void OnMissionTick(float dt)
    {
        base.OnMissionTick(dt);

        if (!MyMod.DebugEnabled)
            return;

        Agent me = Mission.Current.MainAgent;
        if (me == null || me.IsHumanoidPlayerControlled == false && me.Origin == null)
            return;

        // DebugExtensions.RenderDebugCircleOnTerrain is public static
        // (DebugExtensions.cs:8) and forwards to
        // MBAPI.IMBDebugExtensions.RenderDebugCircleOnTerrain at DebugExtensions.cs:10,
        // which the bridge declares at IMBDebugExtensions.cs:10. Each call draws
        // immediately, so this runs once per frame.
        DebugExtensions.RenderDebugCircleOnTerrain(
            Mission.Current.Scene,
            me.GetEntity().GetFrame(),
            8f,
            0xFF00FF00,
            depthCheck: false,
            isDotted: true);
    }
}
```

**What to watch out for.** Two traps, in order of how often they bite. First, the missing members: there is no `DebugExtensions.OverrideNativeParameter`, so the "just tweak the native value" plan does not compile and no amount of trying will find one. Second, the per-frame cost — every one of these three renderers is an immediate native draw with no batching and no lifetime, so calling them in a tight loop or from many agents simultaneously is a frame-time problem, not a correctness one.

## Examples

A range indicator drawn every frame while a flag is on — the shape above, kept minimal here:

```csharp
using TaleWorlds.Engine;
using TaleWorlds.MountAndBlade;

public static class RangeDebug
{
    private static uint Green => 0xFF00FF00;

    public static void DrawRange(Scene scene, MatrixFrame origin, float radius)
    {
        if (scene == null)
            return;

        // Public wrapper at DebugExtensions.cs:8 -> IMBDebugExtensions.cs:10.
        DebugExtensions.RenderDebugCircleOnTerrain(
            scene, origin, radius, Green, depthCheck: false, isDotted: true);
    }
}
```

A facing cone, which is the arc member's actual purpose:

```csharp
using TaleWorlds.Engine;
using TaleWorlds.MountAndBlade;
using TaleWorlds.Library;

public static class ConeDebug
{
    public static void DrawFacingCone(Scene scene, MatrixFrame origin,
                                       float radius, float halfAngleRadians)
    {
        // DebugExtensions.cs:13 -> IMBDebugExtensions.cs:13. beginAngle/endAngle
        // are in radians, so a 90-degree cone is +/- 45 degrees = +/- 0.7854.
        DebugExtensions.RenderDebugArcOnTerrain(
            scene,
            origin,
            radius,
            -halfAngleRadians,
            halfAngleRadians,
            0xFFFF0000,
            depthCheck: false,
            isDotted: false);
    }
}
```

A line with a real duration, so it does not have to be redrawn:

```csharp

}
```

## Risks and crash boundaries

- **A mod cannot name the interface.** `internal interface` (`IMBDebugExtensions.cs:7`) plus `internal static MBAPI` field (`MBAPI.cs:54`) plus `InternalsVisibleTo` limited to three TaleWorlds assemblies (`TaleWorlds.MountAndBlade/Properties/AssemblyInfo.cs:8-10`). Compile-time failure.
- **Two members have no public path at all.** `OverrideNativeParameter` (`IMBDebugExtensions.cs:19`) and `ReloadNativeParameters` (`IMBDebugExtensions.cs:22`) are not forwarded by `DebugExtensions.cs` (verified: the file is 22 lines, forwarding only at `:10`, `:15`, `:20`). This is the concrete difference between "internal, use the wrapper" and "internal, nothing to use".
- **Every render call is an immediate native draw.** There is no batch and no lifetime beyond `time` on the line variant. Calling a renderer per agent per frame is a frame-time problem.
- **No return values anywhere.** All five members return `void`; nothing here can tell you whether a draw succeeded, or what a native parameter currently is.
- **Raw scene pointer.** Every render method takes `scenePointer` from `Scene.Pointer` (`DebugExtensions.cs:10`, `:15`, `:20`). A `Scene` from a finished mission is a freed native handle; passing it is a use-after-free with no managed guard.
- **`depthCheck` defaults to `true` in the wrapper.** The engine's own defaults are `false` and `false` (`IMBDebugExtensions.cs:10`), but the public wrapper flips depth checking on. A debug marker drawn under terrain will be hidden unless you pass `depthCheck: false` explicitly.
- **Not a save participant.** No `[Serializable]`, no state; debug geometry is presentation and is never persisted.

## Cross-Version Notes

The v1.4.5 file is 23 lines with five `[EngineMethod]` bindings — `render_debug_circle_on_terrain`, `render_debug_arc_on_terrain`, `render_debug_line_on_terrain`, `override_native_parameter`, `reload_native_parameters` — and the same file name and five-member shape appear under the same `Bannerlord.Source/bin/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/` layout in the `bannerlord-1.3.0` and `bannerlord-1.3.15` trees. The three render symbols and their parameter lists are the stable part. The two parameter symbols are the ones to watch: `override_native_parameter` takes a `string` name and a `float` value, which is a very narrow channel, and it is the most plausible candidate in this file for a wider signature (more value types, or a scoped reset) in a later version. Also note the public wrapper's defaults — `depthCheck = true`, `isDotted = false`, `time = 0f` — live in `DebugExtensions.cs`, not in the bridge, so they can change without the native symbols changing at all. **VERIFIED MEASURED for v1.4.5** (23 lines, 5 members, complete `DebugExtensions.cs` read at 22 lines); the sibling version trees were not read member-by-member for this page.
